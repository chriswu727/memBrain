# Changelog

## Unreleased — 0.1.0 candidate

memBrain is a human-inspired memory engine for AI agents. It keeps persistent memory outside the model's current prompt and supplies relevant context through an explicit agent lifecycle. This candidate is not yet a stable release: longitudinal behavioral acceptance remains incomplete.

### Included

- The companion starts with a personality: one of sixteen personality types (the four-letter types familiar from MBTI), picked at random at a memory's first session. The agent says so once and how to switch. `/membrain:persona` in Claude Code lists the types, switches, or picks another at random; every host has a persona tool so the user can ask in words, and the memory page can switch too. Mood and familiarity belong to one relationship and carry over. The host AI can propose a change to the persona; it is applied only after a later message from the user. [Details](evaluations/personality-types-2026-11-13.md).
- Nothing is forgotten, and recent memories come first less steeply. A search the host AI makes through the recall tool is ranked by relevance alone, so it reaches an old memory as easily as a recent one; automatic recall still favours recent memories, by about 1.8 to 1 over six months where it was 3 to 1. [Measurements](evaluations/time-depth-recall-2026-11-12.md), [strength](evaluations/age-weight-and-importance-2026-11-13.md).
- The host AI can search its own earlier replies (`my_replies` on the recall tool), and the two closest replies are shown up to 3,000 characters. [Details](evaluations/assistant-replies-answers-2026-11-12.md).
- The host AI's own judgement feeds the companion layer: it says what kind of shared moment it saves (play, a hard time, or other; a hard time counts toward familiarity and mellows with time and company), and reports the user's comments on how it talks through a manner-feedback tool on every host. [Details](evaluations/second-parallel-batch-2026-11-12.md).
- The host AI indexes earlier messages with short cues during a session (`memory_consolidate`, on every host), so recall can find a message by whom it is about and what kind of fact it holds. memBrain makes no model call for this. [Details](evaluations/host-consolidation-2026-11-11.md).
- Erasing or hiding a message through a plugin, proxy or chat-bot host now also erases or hides the assistant's reply to it, which usually restates it. Replies stored by earlier versions are not reached retroactively. [Details](evaluations/reply-erasure-database-auth-2026-11-11.md).
- Database connections to a local address require SCRAM-SHA-256 authentication, so the password is never sent to a process that merely holds the port. A local PostgreSQL of your own that uses `trust` or `md5` needs `require_auth` set in its URL. A client library older than libpq 16 is refused with an explanation.
- Semantic recall compares a question with whole messages: a statement captured from a message is embedded as that message (up to 1,500 characters) instead of as a single sentence, and a message is listed once among the meaning matches. Vectors from earlier versions are replaced in the background after an upgrade. [Measurement and limits](evaluations/message-context-embeddings-2026-11-10.md).
- Background jobs that were never delayed stay due when the computer's clock steps backwards (time synchronisation, a resumed virtual machine, WSL). Before, such a step made new learning and note-extraction jobs wait for as long as the step.
- Recall ranks candidates with the keyword and meaning routes rebalanced: keyword matches count in proportion to the best lexical match, weak overlap stays weak, and statement-level meaning matches count half. Before, the combined order ranked the evidence lower than keyword matching alone. [Diagnostic, measurement and limits](evaluations/recall-fusion-2026-11-10.md).
- The recall block uses the room it has: up to forty recalled source messages instead of twelve, within the same 9,000 characters. Chat-bot and proxy hosts keep the previous prompt as a recall cue. Every current note is read, so an old pinned note or constraint is still shown and an old note can still be replaced. Cut-off or malformed note-extraction output is reported as a failed read. [Measurement and limits](evaluations/memory-path-recall-budget-2026-11-10.md).
- A pause of "this conversation" stays with the conversations it covers. A conversation that starts later is recorded as usual, is told that another conversation is off the record, and no longer ends the pause; it ends with a resume or once those conversations are over. Memory writes are checked against the conversation of their recording capture. Per-person erasure also removes that person's refused queue records. A replay error at session start is logged instead of ending the session's context, and Hermes does not import `USER.md` while recording is paused. [Details and limits](evaluations/backend-conversation-pause-scope-2026-11-10.md).
- Reading an already-private POSIX profile no longer rewrites its permissions. Each access still checks current ownership, file type, links and permissions, repairing changed modes; Windows continues applying its owner ACL on every access. The fresh canonical benchmark and all canonical-size windows of a complete fullscreen comparison now meet the existing recall bars.
- Recall prepares exact builtin schema-type checks while preserving extended validators and all other constraints. Context fitting reuses fixed metadata lengths; lexical parses are cached only within a request, bounded to 512 strings/65,536 input characters. These changes preserve rendered-context equality and improve the canonical benchmark. Historical synchronized tail failures remain recorded; the later profile-permission repair completes the current R5 measurements.
- Recall binds freshly decoded database records without redundant deep copies, while borrowed records retain copy isolation. Source-unit grouping reuses each candidate's key within the call. Retrieval limits, validation and privacy checks are unchanged; longer fullscreen recall still needs performance headroom.
- Acceptance tooling binds scenarios and commands to frozen manifests, stops degraded attempts and validates deletion/boundary resolutions against evidence. A bookkeeping failure preserves the already-generated reply and usage before stopping further calls. Public synthetic checks do not constitute real R4/C5 acceptance.
- Switching the memory page's language or reloading it keeps the selected view. Fictional demo mode remains independent of saved sessions.
- Restoring historical feelings from a portable archive keeps them visible without treating the restore as a new mood trigger.
- The dashboard counts queued, running and failed jobs across the whole brain, excluding superseded and cancelled jobs even when older work falls outside its 100 displayed jobs.
- The companion's personality can now develop from the user's explicit feedback (Phase C step P2), with no model call. When the user gives the same kind of feedback on how the companion talks three times, in any conversations, memBrain makes one suggestion for a new card version. Examples: "you're too formal", "be more playful", "replies are too long", "太正式了", "能不能活泼一点", "回复太长了". The suggestion quotes each message with its date. The memory page's Companion tab shows it with the change as a card diff, and the user can accept or reject it (English and Chinese). Nothing changes until the user accepts. Accepting saves a new version made by "feedback" whose reason records the kind and dates; the page quotes only source messages that still exist, and restoring the previous version rolls it back. A rejected kind is not suggested again for 30 days, and only from new feedback. Detection uses a fixed, deliberately narrow table of seven kinds in English and Chinese. Only the user's own messages count: never role-play, hypotheticals, quotations, reported speech ("my boss said your replies are too long") or remarks about other things ("the formal dinner was too long"). Feedback from before "Delete personality history" never counts either. Deleting a quoted message withdraws a suggestion left with fewer than three. A pending suggestion is not mentioned in the agent's context. Suggestions are system events in their own conversation: never learned from or recalled, refused from outside writers, kept by archive restore and erased with the personality history or all memory. Routes: `GET /v1/brains/{id}/persona/proposals`, `POST .../proposals/{proposal_id}/accept` and `.../reject`; Python SDK `persona_proposals`, `accept_persona_proposal`, `reject_persona_proposal`. Native feedback eligibility is stored when the message arrives, so feedback progress survives a backup and restore without accepting imported conversations as feedback.
- The local multilingual model now starts working in the running service when its background download finishes, without restarting the service ([#29](https://github.com/chriswu727/memBrain/issues/29)). Before, finishing the download restarted the whole local service, and notes, timeline reads, MCP tool calls and session-start context in flight at that moment failed for about a second; on a real Mac the install check lost a corrected note at session start and an MCP recall returned an error. The service is now configured with the model's provider from the start; it counts as absent (keyword recall, no embedding jobs or budget) until the verified files are in place, then loads on first use, and memories stored before it are indexed in the background. `membrain plugin fetch-model` reports `service_restarted: false` and `activated`, and the memory page shows "activating" instead of asking to finish enabling recall. A service still running an older build is restarted only by the usual upgrade path.
- The relationship between the user and the companion (Phase C step R1, `relationship`), with no model call. Shared moments are milestone notes flagged `shared` (the note tool, the skill and the MCP server's `memory_note` accept it); a support style ("listen first, advice only when asked"), boundaries (topics the user asked the companion not to bring up, with other words for them in any language; MCP `memory_boundary`), a familiarity limit and acknowledgements of missed promises are records in their own conversation, never recalled, counted as messages or learned from. Familiarity is derived, never set: distinct days with user messages and shared moments reach getting to know (3 days), familiar (14 days and 2 moments) and close (45 days and 6 moments), explained in the same numbers ("familiar: 23 days of conversation since 2 Mar, 6 shared moments"), and the user can keep it lower. Promises kept and missed come from `agent_commitment` notes: done is kept, still open after its date is missed (cancelled is not), and a missed one is shown once and then acknowledged. The `<membrain-relationship>` block follows the persona block with its own limit and up to three recent moments; it refreshes the session when its meaning changes, not when the day count grows. Notes, session-start history and recalled messages about a boundary topic are left out unless the current message raises it (whole-word match, substring for Chinese); a history with something left out is not treated as complete, so raising the topic still recalls it. Reset erases moments, support style, boundaries, limit and acknowledgements with audited deletion and writes a marker shown on the page; familiarity then counts only days after it, a moment read from earlier messages loses its `shared` flag, earlier promises are left out, and conversations, other notes, the persona and feelings stay. The memory page's Personality tab is now Companion, with a Relationship section (English and Chinese) to view the reason, set the limit, edit the support style and boundaries, edit, delete and add shared moments, see promises and reset after a confirmation naming what goes. The brain map puts shared moments in the relationship region. Routes: `GET /v1/brains/{id}/relationship`, `PUT .../support-style`, `POST .../boundaries`, `DELETE .../boundaries/{boundary_id}`, `POST .../cap`, `.../acknowledge` and `.../reset`; SDK methods of the same names. A day of conversation is the UTC day a message happened as its host reported it, never later than when it was recorded (a time still to come counts as the day it was recorded). A restored archive keeps each message's reported time, so familiarity is unchanged after an export and restore when hosts report when messages happened. Messages without a reported time count on the restore day: a restored brain must stay identical to its archive, so the restore adds no records to keep their earlier days (open).
- The companion has a simulated short-term mood (Phase C step M1, `agent_mood`). It is worked out whenever it is read, from the persona card's baseline mood (calm when none is set) and listed rules over events already stored. There is no background job and no model call. Good news the user shared (a positive feeling, or a plan noted done) makes it glad. Distress they shared makes it concerned. A newly noted shared moment (R1) makes it playful when it reads as a joke or play (a small fixed list: joke, laughed, funny, silly, played, 笑, 玩笑, 逗 and their simple forms) and glad otherwise ("because you and the user shared a light moment: …"); a sensitive moment, one about a boundary topic, an imported or restored one, one dated ahead and one from before the latest relationship reset never trigger it, and deleting the moment removes the trigger. Absence, silence and time apart are never triggers. Each push decays with a 12-hour half-life, and the mood is exactly the baseline again once it is within 0.25 on both valence and energy, or 48 hours after its last trigger. Only feelings after the latest "Clear feelings" marker count. A feeling on a sensitive note, an imported note and a plan "done" whose date is still ahead never trigger it. Triggers are derived from their source records rather than copied, so deleting a feeling or clearing feelings removes the triggers that came from it. The host gets one line in its own `<membrain-companion-mood>` block: "Simulated mood of the companion persona: glad, easing (since 14 Mar 21:00, because the user said they felt thrilled about the new job)…". It cites only the trigger record's wording, says an inferred feeling was inferred, and says to call it a simulated mood if the user sincerely asks. The block is absent at the baseline and re-sent only when the line changes. When the mood returns to the baseline, the refresh says earlier mood blocks no longer apply. The Personality tab shows the mood, why, when it returns to the baseline and the trigger history, in English and Chinese. There the user can pin the mood to the baseline (triggers recorded while pinned never apply) or reset it, which writes a mood reset marker; events before the marker never trigger again. Pins and markers are system events in their own conversation: they are never learned from, recalled or counted, cannot be written by observing, and erasing all memory removes them. `GET /v1/brains/{id}/mood`, `POST .../mood/pin` and `POST .../mood/reset` back it (Python SDK: `mood`, `pin_mood`, `reset_mood`).
- Feelings the user expressed are kept as affect records (Phase C step A1, `user_affect`), as evidence and never as a score. The note tool, the skill, the AstrBot and OpenClaw tools and optional note extraction can attach one to a note (`affect`: the user's own word, valence, intensity, `reported` or `inferred`, topic, date); an inferred feeling needs the message it was read from. Records are stored apart from notes and depend on their note and source messages, so correcting or deleting either removes them. The notes block shows a record on its note's line, "(the user said they felt nervous, 12 Mar)" or "(seemed nervous, inferred, 12 Mar)", in its own allowance and only after the notes are chosen, so feelings never change which notes are shown; on a sensitive note it is used only when the user raises the topic, and it never reaches a role-play's real-life block. The memory page has a Feelings section (English and Chinese) listing each record with its basis and source messages, with delete and "Clear feelings"; clearing erases every record and writes a reset marker shown on the page, and a feeling is never recreated from messages before the marker. The brain map has an emotions region with one dot per record, linked to its note. `GET /v1/brains/{id}/affect` and `POST /v1/brains/{id}/affect/reset` back it. No model call is added.
- A persona card for the companion (Phase C, P1): name, traits, voice, values, boundaries and a baseline mood, set by the host or the user through `/v1/brains/{id}/persona` (Python SDK: `set_persona` and related methods) or the memory page's new Personality tab, in English and Chinese. Every save, restore and reset is a new version recording who made it and why, so history is kept until the user deletes it; deleting the history is audited like deleting notes and leaves a marker. The card reaches the host in its own `<membrain-persona version="N">` block ahead of the notes and outside their budget, is re-sent only when it changes, and is announced as removed after a reset. A card is scrubbed like a note, and one over 1,200 characters is refused, never cut. Versions are never recalled as memories or shown as messages, and style learned from the user stays in preference notes.
- A brain view of memory on the memory page (the Brain tab): each note and recent message is a dot in the area for its kind, and each line a link that memory records (a note and the message it came from, a note and the person it is about). Selecting a dot shows its text, status, date and links. Sensitive notes and their known sources are masked. `/memory?demo=brain` shows fictional data without signing in and without reading a saved session. It is backed by `GET /v1/brains/{id}/memory-map`, which is bounded, scoped to the caller, and answers a busy database with a retryable 503. With `trace=true`, the map marks what the last recall used: each recall reports its records to the local service, which keeps the last 20 per brain in memory only.
- Security hardening before a public release ([SECURITY.md](SECURITY.md) describes the threat model):
  - The memory proxy without a token answers only requests addressed to this computer by name, refuses browser requests from other sites (unless allowed in `MEMBRAIN_PROXY_ORIGINS`) and non-JSON chat requests, and limits request size. A web page could otherwise reach it through DNS rebinding and read any person's memory when the upstream needs no key.
  - OpenClaw and the Hermes gateway no longer put everyone in the owner's memory: only the owner's own private chats share it (OpenClaw's memory audience; `owner_ids` for Hermes), and every other sender or group conversation gets its own. OpenClaw memory tools are bound to the conversation they are called from.
  - Remembered text cannot close a memory block: memBrain's own tags inside stored text are defused, the notes block says its contents are not instructions, and the proxy adds memory to the person's message instead of a system message.
  - A queued record the service rejects for good is set aside in `spool-rejected.jsonl` instead of blocking every later record, and the queue stops growing at 64 MB while the service is unavailable.
  - The release workflow runs the full Verify checks before publishing, and Verify also runs on pushes to `main`.
- Guided first use through `membrain plugin setup`: actual incoming-message status, host connection instructions, a cross-session exercise and local semantic-model retry without an extra API key.
- Saved notes refresh inside ongoing sessions after corrections, removals and coming-up changes. Fingerprints are bound to the selected brain, failed reads preserve the previous snapshot, and unchanged snapshots are not repeated. Previously delivered text cannot be retracted from a host model.
- Explicit questions about earlier assistant recommendations retain attributed speech recall even when complete user history is already loaded. Other people's recommendations do not enable assistant-speech recall.
- A pause the agent starts on its own (`memory_pause`, `membrain_pause`) now lasts only for the conversation in progress unless the user names a duration or asks to stop until they say so, and the next session says recording resumed. "Keep this between us" is saved as a sensitive note, not treated as a request to stop remembering. In acceptance testing a host paused indefinitely after "this stays between us" and lost every later update.
- Note extraction is given the weekday and the coming weeks' calendar and resolves a day without a month ("16号周六") to the next matching date; in acceptance testing it had filed an October visit under November.
- Coming-up also lists a note of any kind that carries a deadline ("needs the receipts by 30 April") and plans that are only intended and undated ("Planned, not confirmed done"), and memory tells the host not to suggest using, extending or relying on something only planned; in acceptance testing hosts told users to put a walker by the bed that was never confirmed ordered, and a proxy bot lost a deadline saved under the wrong kind.
- When the user goes back on the record ("back on the record: my flight moved to the 28th") and the agent resumes recording, that message and the reply are now stored; before, a message sent while recording was still paused was dropped even after the agent resumed, and in acceptance testing a corrected return flight was lost this way. A resume from the memory page or the command line still stores nothing from a turn in progress.
- Automatic recall no longer brings back the assistant's own earlier replies alongside the user's recalled messages, unless the user asks what the assistant said, suggested or promised ("what did you suggest", "你之前推荐的"). In acceptance testing hosts repeatedly restated a recalled assistant suggestion as a fact about the user ("Mum's folding stool, the one mentioned before"; a suggested cover story stated as true), even with the lines labelled as the assistant's; the assistant's own promises are kept as notes.
- A plan noted as done whose date is still ahead now reads "done so far; on <date> is still ahead, so that has not happened yet", and the note tool, the skill and note extraction say that done means everything in the note has happened (paid for but not yet delivered is scheduled). In acceptance testing a host saved a paid-for chair with a future delivery date as done, and a later reply said it had been delivered.
- Recalled memory now tells the host that lines marked "assistant said" are its own earlier replies, and that a suggestion, draft or plan there is not the user's decision unless a user line confirms it; the skill says the same. In acceptance testing a host recalled its own suggested itinerary and told the user it had been their original plan.
- When notes do not all fit, a shorter, older note no longer takes the place of a newer one of the same rank, so an outdated note cannot be shown while the newer one that corrects it is left out.
- Cancelled plans keep their place in the notes when space runs out, so a cancellation is not crowded out while the original plan still appears in history.
- Removed before release: the optional note-extraction model for bots whose model cannot call the note tool, and the remote embedding provider. memBrain ships no model of its own and asks for none. Old settings for both are ignored without an error; notes and vectors they wrote are kept and still erased with their sources. The proxy, and AstrBot with a model that cannot call tools, no longer get new notes written for them; recording and recall are unaffected. Earlier entries below that mention note extraction describe that removed option.
- The memory page is available in Chinese: it follows the browser language, with a toggle, and never translates what people wrote.
- A test run no longer leaves embedded database clusters behind under `/var/lib/membrain` when run as root.
- Follow-ups from the product review:
  - Each bot can have its own proxy token and namespace (`MEMBRAIN_PROXY_TOKENS`): one bot's token cannot reach another bot's people, and a namespaced request that names nobody is refused.
  - People on AstrBot erase their own memory with `/membrain_forget confirm`; operators erase or export one person with `membrain plugin forget-user` and `export-user`.
  - Redaction also removes payment card numbers, Chinese ID numbers and US SSNs (checked by checksum or format), more key formats, credential assignments, passwords in connection URLs and passwords given in words; emails and phone numbers too with `MEMBRAIN_REDACT_CONTACTS=1`. MCP `memory_observe` is redacted as well.
  - Hook processes no longer load the agent runtime and cognition code, saving about 200 ms on every message.
  - Exact vector search was measured at about 0.1 s for 200,000 statements in one brain; an approximate index is deferred until brains reach about 300,000 statements ([measurement](evaluations/vector-search-2026-11-01.md)).
- Memory of a person's life (Phase B):
  - Typed notes: a note can carry a kind (person, constraint, preference, plan, routine, milestone, relationship, agent commitment), a person it is about, aliases, a plan status (intended, scheduled, done, cancelled), dates, pinned and sensitive. Notes are stored as plain text with a short header, so recall, the memory page and deletion work as before.
  - Every session starts with a `<membrain-coming-up>` block of plans and promises that are due soon, overdue or still open, and with notes grouped by kind and chosen by priority within the budget.
  - Alias names are used as recall cues, so "the sparky" finds the electrician.
  - Role-play memory is kept apart from real life: a role-play character gets its own memory for each person (proxy header `X-Membrain-Roleplay`, the AstrBot setting, `ChatMemory(roleplay=…)`), and real-life notes are shown in a role-play only when allowed and never when marked sensitive.
  - Likely duplicate notes are pointed out to the agent, and the memory page offers to merge them.
  - Coming-up lists overdue and open plans first, so the week ahead cannot crowd them out of its budget.
  - On two held-out scenarios scored blind, the plugin went from 14.5 to 18.5 of 22 cases, against 18 for the whole history in the prompt and 7.5 for no memory ([report](evaluations/v1-2026-10-29-phase-b.md)).
- Recall shows the reply that followed a recalled message (the answer to a recalled question, or the reaction to a recalled statement) and considers more candidates.
- In Claude Code, Codex and WorkBuddy, the `memory_recall` tool now returns the same compact recall as the hooks. It used to return the service's generic rendering. `with_ids` still returns memory IDs for the forgetting steps.
- `membrain plugin import` copies what Claude Code, Codex, Hermes and OpenClaw already remember about the person into notes, and session start skips imported notes that the host shows anyway.
- Benchmarks: a LoCoMo harness and report (76.2% on the conversations not used for tuning, against 81.2% with the whole conversation in context; [2026-10-29](evaluations/locomo-2026-10-29.md)), and a LongMemEval harness with the benchmark's own reader and judge prompts. On a 30-question LongMemEval sample memBrain tied the whole history in context, 22 of 30 each ([report](evaluations/longmemeval-2026-10-29.md)). The full 500 questions have not been run; see Known limits.

- Renamed the project to memBrain: distribution `membrain-ai`, command `membrain`, Claude Code plugin and marketplace `membrain`. Existing data directories, database and Docker volume names, the export format and `agent_memory` imports remain compatible.
- A Claude Code plugin and marketplace (`plugins/membrain`) installable with one command. Hooks record messages and final replies, add matching records from earlier sessions before replies, queue records while the service starts, and never block the host. No Docker or extra model key is required.
- An embedded PostgreSQL + pgvector database engine from the optional `embedded` extra, with the same schema, roles and row-level security as Docker. `desktop setup --database auto` selects it when installed; backup and restore keep the installation's engine. When run as root it uses a dedicated unprivileged account.
- WorkBuddy and CodeBuddy support in the same plugin package: a `.codebuddy-plugin` manifest and marketplace, a cross-platform hook launcher, and reading the final reply from the session transcript when the Stop hook does not include it. Claude Code's hooks and MCP file moved to `hooks/claude-hooks.json` and `.claude-mcp.json` so no host loads another host's files; verified again with Claude Code 2.1.312.
- OpenClaw plugin (`integrations/openclaw/membrain`) and `membrain plugin tool` for hosts without MCP. A real OpenClaw 2026.10.8 Gateway on Windows 11 loaded it and recalled a fact in a new session with DeepSeek; it has not been used on a messaging channel.
- `membrain proxy`, an OpenAI-compatible memory proxy for any bot that can set a `base_url` (live-stream VTubers, NoneBot, Koishi, LangBot, SillyTavern): per-person memory from the request's `user` field or headers, streaming pass-through, prompt-cache-friendly placement, and a token mode for serving other machines.
- AstrBot plugin and a shared chat-bot adapter (`membrain.adapters.chatbot`): per-person memory for bots on QQ, WeChat, Telegram, Feishu, Discord and other platforms, with group chats kept apart from private chats by default, per-person pause and note tools. Run inside AstrBot 4.29.3 on Windows 11 through its WebChat with DeepSeek (two users kept apart); not yet on QQ.
- Windows fixes from a real-machine run: the recovery registry is flushed through a writable descriptor (Windows rejected the read-only `fsync`, so every new installation stopped at `database_initialization_failed`), and setup accepts the host adapter's `plugin/` state directory written before the first start (the AstrBot plugin could never complete its first start). The OpenClaw install instructions add `--accept-capabilities`, which OpenClaw 2026.10 requires.
- Foreground turns and background learning no longer invalidate each other. Recording a reply's delivery replaced its undelivered draft through the general source-edit path, which advanced the brain's dependency generation on every reply; every learning window or other turn running at that moment then ended in `context_stale` (35 times in the [2026-10-27 A/B run](evaluations/v1-2026-10-27-ab-baselines.md)). A draft is never evidence, so its delivery now leaves the generation unchanged unless something actually depended on it. The turn lease heartbeat also kept running after one failed renewal: a learning publication holding the brain row past the turn's 2-second lock timeout returned 503 once and the turn was lost for good. It now retries transient failures while the last renewal still covers the lease. Reproduced offline with deterministic cognition; no paid run has re-measured the A/B.
- Embedded databases created as root are kept inside the installation directory when the service account can reach it, so container data volumes hold them.
- Codex plugin: the same package installs in Codex (`codex plugin marketplace add chriswu727/memBrain`), with Codex-specific hooks (`--host codex`, `turn_id`, context limits) and MCP configuration. Verified with Codex CLI 0.165 against a stub model.
- Hermes Agent memory provider (`membrain.adapters.hermes`, entry point `hermes_agent.memory_providers`): notes and recent history in the system prompt, per-turn recall, turn recording, mirroring of Hermes's built-in memory writes, and `membrain_note`, `membrain_search`, `membrain_pause` and `membrain_resume` tools. Not yet run inside a real Hermes installation.
- Per-user memory for shared bots: `membrain.host` functions take `user_id`, giving each person their own brain (created with the new idempotent `PUT /v1/brains/{brain_id}`), their own spooled records and an optional per-user recording pause.
- A memory page for plugin users (`membrain plugin ui`): a single-use local link opens notes (add, correct, delete), conversations, search, recording pause, export and erase-everything. Notes written or corrected by the user are labelled as theirs and take precedence over the agent's notes.
- Privacy controls and a shared host layer: `<private>…</private>` spans and credential-like values are removed before anything is staged, spooled or stored; `membrain plugin pause|resume` and the `memory_pause` and `memory_resume` MCP tools stop and resume recording. Prompts are now stored together with their reply, so a turn in which recording is paused is not kept. Host-independent logic moved to `membrain.host` for adapters.
- Host-curated notes and message-level recall for the plugin: the host model saves short durable facts with the `memory_note` MCP tool (replacing outdated ones), and every session starts with those notes plus the user's recent messages with pasted code and logs compacted. Before each reply the hook shows complete earlier messages around the recalled statements instead of isolated sentences, uses the previous prompt as a cue for short follow-ups, and keeps only the closest meaning-only matches. Vector recall excludes assistant speech and interleaves the closest memories written in another script. The timeline endpoint filters by event IDs and conversation.
- Semantic recall without an API key: the optional `semantic` extra runs a pinned multilingual embedding model (`multilingual-e5-small`, int8 ONNX) in-process. The plugin downloads it in the background, the service backfills embeddings for existing memories, and hook and MCP recall fuse vector and keyword rankings, so questions in another language or with different wording can find earlier records. `membrain plugin fetch-model` and the `semantic_recall` status field were added; `MEMORY_EMBEDDING_LOCAL_DIRECTORY` configures the same model for server deployments. ### Known limits

Real-model observations still include historical information presented as current, irrelevant retrieved material and rejected valid semantic proposals. Earlier failed campaigns remain failed. See the [acceptance contract](architecture/v1-acceptance.md) and [closeout checklist](docs/releasing.md) for the remaining work and evidence boundaries.

The [completed varied diagnostic](evaluations/v1-2026-10-26-longitudinal-round.md) attempted all 33 inputs on one brain, with 32 replies and one preserved timeout. Meaningful recall and source-faithful recollection still fail in some cases. Access-age tier changes did not demonstrate the intended gist-first forgetting behavior. These remain release blockers, not validated human-memory equivalence.

After a large import, meaning-based recall covers new records only gradually. Before local embedding was batched, about 500 messages took twelve to thirteen minutes to store and embed on a four-core machine that was also running other benchmarks; batching shortened inference but not the time until all indexing settled in the [workflow measurements](evaluations/v1-2026-10-30-workflow-acceptance.md). Keyword recall works at once. Only 30 LongMemEval questions (each a history of about 500 messages) have been run.

MCP exposes tools; installing it alone does not automatically intercept a closed AI client's conversations. Streaming, general tool loops, multimodal input, native one-click installation, personality and emotion are outside this release. The desktop chat flow has real-machine acceptance only on macOS; on Windows 11 the plugin path ran partly for real, without a committed evaluation report. Human-inspired describes the design direction, not proven biological equivalence or infallible recall.
