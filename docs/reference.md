# Runtime and integration reference

[English overview](../README.md) | [简体中文概览](../README.zh-CN.md)

Latest verification: [historical feedback use and remaining acceptance work](../evaluations/v1-2026-10-25-preference-use.md). The detailed history and earlier failures below remain preserved; full longitudinal acceptance has not passed.

A model-independent, headless memory runtime for agents. The goal is to let a host integrate once, then let the runtime continuously manage the agent's working memory, long-term beliefs, and recall. Users should be able to converse normally; memory must form and be used even when the main agent does not explicitly call save or search tools.

See the [architecture and acceptance specification](../architecture/architecture.html) for the complete target, and the [autonomous runtime contract](../architecture/autonomous-runtime.contract.json) for product boundaries and host responsibilities. The current implementation provides the underlying memory service, host lifecycle integrations, and optional situation understanding, semantic consolidation, and semantic recall: it uses recent conversation to identify the current goal, creates beliefs and episode structures with traceable sources, and searches and selects memories within a budget. Complete host integration and long-term memory quality still need validation. This is not yet a complete autonomous brain.

First-release work is bounded by the [finite acceptance and stop criteria](../architecture/v1-acceptance.md). Memory quality now requires [longitudinal evaluation](../architecture/longitudinal-memory-evaluation.md) of realistic use across multiple sessions: continuity in daily life and ongoing tasks, and whether remembered information helps the user. The new runner supports sixteen irregular sessions, answer-dependent user choices, normal recent context and durable continuation. Its [verification report](../evaluations/v1-2026-10-25-longitudinal-harness.md) separates executed checks from unassessed memory quality. Simulated story time does not prove real elapsed operation or aging, and the release gates have not yet all passed.

## Product and integration goals

The unit of integration is an agent with a stable identity. Its brain identity is independent of the model, process, or chat window; participants, relationships, and tasks separately constrain memory scope. The host delegates management of the message lifecycle and memory context through an adapter. The adapter invokes the underlying operations, so application code does not manually orchestrate `observe / prepare / commit` on every turn.

On each turn, the runtime should automatically receive actual inputs and tool results, understand the current goal and references, activate relevant memories, continue searching when needed, and assemble a budgeted working context for the model. Once actual delivery or an actual outcome is confirmed, it should update working state and long-term memory candidates. Background processing should trigger consolidation, association updates, and activation changes based on new evidence, conflicts, and task outcomes.

The current context still has a capacity limit, and temporary content may be compacted. Long-term memory rests on original sources and versioned cognitive state rather than repeatedly overwritten rolling summaries. Successful integration requires more than injecting a retrieved passage: it must demonstrate persistent state, spontaneous associations, revised understanding, and continuity after a restart.

Complete integration must work even when the main agent's memory tools are disabled. MCP is a supplementary operations interface; connections that only support tool calls must report that actual capability. A host without control over the message, reasoning, or context lifecycle cannot be labeled fully integrated. A model/API proxy that cannot confirm final delivery must not treat generation completion as proof that the user received the response.

The product does not require an administration UI. Authenticated status, metrics, and structured runtime log interfaces provide development diagnostics: which memories and sources a turn used, why recall continued or stopped, which versions changed, costs, and failure reasons. Logs do not copy conversation bodies by default and do not record hidden model reasoning. The existing local workbench is a removable development aid, not the product entry point or an acceptance prerequisite.

### Independent product and optional integrations

The primary audience is agents that access models through API keys. Direct integrations and third-party bot plugins share the same memory core. AstrBot, LangBot, NapCat, and similar projects are optional entry points, not prerequisites for installing, running, or developing core capabilities. Dependencies flow in one direction: **host adapter → public API / SDK → memory core**. The core does not import chat frameworks or fork memory algorithms for individual frameworks. Framework-specific dependencies belong in optional adapter packages.

The core owns persistent memories, provenance, identity and scope, recall, learning, decay, and recovery rules. Adapters translate actual events, map stable identities, connect lifecycle hooks, and supply delivery receipts. They access memory through public interfaces rather than accessing the database directly or maintaining another authoritative memory store. Each turn should have one lifecycle orchestrator, avoiding duplicate capture, injection, or generation by a plugin and a model proxy.

Changing models, channels, or chat frameworks should allow the agent to retain its existing brain. Trusted configuration must explicitly map participants and conversations across platforms; display names or model guesses must not merge identities, and private-chat memories must not automatically enter group chats. Uninstalling an adapter should not delete core data. Independent operation and adapter replacement both require acceptance checks for restart recovery, retry deduplication, scope isolation, corrections, and deletion. These goals must not be presented as completed capabilities.

The core and HTTP API operate independently of these chat frameworks. (The bundled desktop chat and the `open_agent()` session entry point, which connected directly to a configured Chat Completions model, were removed; see [bundled chat and Python sessions](#bundled-chat-and-python-sessions-removed).) External hosts still supply actual delivery and stable message identities. A model-compatible gateway and QQ framework adapters have not been delivered. MCP remains supplementary and cannot replace missing lifecycle integration.

## Desktop setup

Install [uv](https://docs.astral.sh/uv/) and start Docker Desktop, then run:

```sh
uv tool install --python 3.12 'membrain @ https://github.com/chriswu727/membrain/archive/refs/heads/main.zip'
membrain desktop setup
```

This installation does not require Git or a repository clone, or separate startup commands for the database, API, and worker. If installation reports that the command directory is not in `PATH`, run `uv tool update-shell` and reopen your terminal. Setup asks for no model and no API key, and makes no model calls.

**Removed:** background learning with a cognition model of memBrain's own (configured with `desktop setup --base-url --model --api-key-env [--thinking] [--cognition-preset reasoning]` or the `MEMORY_COGNITION_*` variables, and inspected with `desktop learning-status`, `retry-learning`, `budget`, `configure-budget`, `cognition-policy` and `configure-cognition-policy`) was removed after runtime `2600219b`; the host's own AI does every model task. Setup no longer accepts those options and the commands are gone. An installation that configured a model keeps loading: the `cognition` section of `profile.json`, a `cognition-policy.json` beside it, and a `MEMORY_COGNITION_*` variable are ignored (the variables with one warning in the log that names them, never their values), and status no longer reports a `cognition` line. What that learning stored stays readable and erasable; see [what the removed learning left behind](#what-the-removed-learning-left-behind).

Setup creates a stable brain identity and local credentials, prepares a dedicated database, applies migrations, and starts the memory service and worker in the background. Repeating setup does not recreate the brain or clear its memories. The default API address is `127.0.0.1:8788`, and the database defaults to `127.0.0.1:55433`. On first setup, occupied ports are replaced with available ports and saved. An existing installation reports a port conflict rather than stopping another process or silently switching to a different brain.

Setup prints an MCP configuration containing no secrets and saves it as `mcp.json` in the local configuration directory. You can retrieve it again with:

```sh
membrain desktop mcp-config
```

Add this configuration to a host that supports stdio MCP to connect the memory tools. Configuration locations vary by host; setup does not currently modify external client configuration automatically. Starting this MCP connection automatically starts or connects to the local service. Closing the MCP connection leaves the service processing background tasks. After a computer restart, the next MCP connection or SDK `open_client()` call starts the service again with the same brain; no new setup is required.

**The MCP connection is still `tools_only`.** It does not automatically read all host conversations, take over compaction, or confirm message delivery. Agents that need automatic memory should use a host plugin or adapter that supplies the host message lifecycle ([plugin mode](#plugin-mode)); memBrain's own chat runtime was removed (below). Successful installation and automatic host integration are distinct states.

### Bundled chat and Python sessions (removed)

**Removed:** the bundled chat mode and the Python session SDK built on it were removed after runtime `ba70e7cd`: the commands `membrain desktop configure-chat`, `desktop chat` and `desktop turn-status` (argparse now refuses them as an invalid choice), `membrain.agent_session.open_agent`, `membrain.runtime.BrainRuntime` with its on-demand orientation, its answer reviewer (`membrain.answer_review`) and its model-driven recall controller (`membrain.recall_control`, `membrain.recall_provider`), the chat model adapter (`membrain.chat_provider`), `membrain.runtime_client.RuntimeClient`, the turn lifecycle API they used, and the temporary (unrecorded) chat turns with the direct chat's own recording controls (`/off-record`, device capture for direct chat). Importing a removed module raises `ModuleNotFoundError`. In that mode memBrain called a reply model itself. It is fitted to agent hosts instead, through [plugin mode](#plugin-mode), the OpenClaw, AstrBot and Hermes adapters, [MCP](#mcp) and the [proxy](#openai-compatible-proxy), where the host's AI replies. Profiles, backups, turns and archives an older runtime left keep working; see [what the removed runtime mode left behind](#what-the-removed-runtime-mode-left-behind).

The Python `MemoryClient` retries a bodyless GET once if the connection resets or closes with a protocol/read error. It preserves the same destination, authentication, recovery acknowledgement and request options, and emits a warning without request content. A second failure propagates. Each attempt retains the configured HTTP timeout; this is not a total wall-clock deadline. Writes, GET requests with bodies, timeouts, HTTP error responses and invalid JSON are not automatically retried. This does not authorize repeating a model call or an uncertain delivery.

### Local status and configuration

```sh
membrain desktop status
membrain desktop logs
membrain desktop stop
membrain desktop start
membrain desktop restart
```

`status` checks the authenticated service, database, brain identity, and worker; it does not verify memory quality. `logs` returns bounded, structured service events without conversation bodies or API keys. `stop` and `restart` retain the database volume and configuration; they do not delete memories. Shutdown is requested through the authenticated service instance rather than by killing a process using a stale PID. When the saved configuration differs from the running service's, `setup` restarts the service. With `--no-start`, setup only saves configuration; run `restart` later to apply it. After updating the installed program, also run `desktop restart` so the background instance loads the new code.

To update the source-URL installation above to the current `main` branch, reinstall the package and restart the service:

```sh
uv tool install --python 3.12 --force --reinstall-package membrain 'membrain @ https://github.com/chriswu727/membrain/archive/refs/heads/main.zip'
membrain desktop restart
```

`--reinstall-package` refreshes the source archive even when the package version is unchanged. Keep using the same `--directory` for a non-default installation; there is no need to create a new profile or brain. If a separate Python host imports the SDK, update that environment before reconnecting it too, replacing the interpreter path below with the host's actual interpreter:

```sh
uv pip install --python /absolute/path/to/host/python --reinstall-package membrain 'membrain @ https://github.com/chriswu727/membrain/archive/refs/heads/main.zip'
```

The service freezes a content-based build identity at startup, covering runtime code, contracts, and migrations. A changed build reports `restart_required` even when the package version is unchanged; `start` will not silently reuse the old daemon. Startup and migration reject unknown or non-prefix schema histories, and a downgrade check runs before stopping a live service. These checks do not prove that historical migration SQL was unmodified. The real two-build Docker test verifies retained brain identity and sources, plus refusal to stop a newer service during an incompatible downgrade.

The default configuration directory is `~/Library/Application Support/memBrain` on macOS, `%LOCALAPPDATA%\memBrain` on Windows, or `$XDG_DATA_HOME/membrain` on Linux (`~/.local/share/membrain` when unset). An installation created before the memBrain rename keeps using its existing `Agent Memory` or `agent-memory` directory. All desktop subcommands accept `--directory <absolute-directory>`; use the same directory consistently for one installation. This directory contains local credentials. Memory content is persisted in the installation's Docker data volume, so copying the configuration directory does not back up the database.

Use `desktop backup --output PRIVATE_DIRECTORY --request-id STABLE_ID` for a streamed full-database checkpoint. Supported recovery requires that bundle and the independently current deletion registry; it restores into a fresh quarantined installation and needs explicit checkpoint activation. Old pending work does not automatically resume. The [backup and recovery guide](../architecture/desktop-recovery.md) explains current-authority preservation, sensitive plaintext artifacts, new credentials, and the required external-host recovery epoch.

For automated deployment, save configuration first and start the service later:

```sh
membrain desktop setup --non-interactive --no-start
membrain desktop start
```

Setup takes no model options (see [desktop setup](#desktop-setup)). The desktop service uses its own configuration; it does not automatically read the repository's `.env` or migrate brains from the development database into the new installation.

The current delivery provides local command-line installation and service management and still requires uv and Docker Desktop. There is no native one-click installer or complete lifecycle adapter for a specific host yet. The implementation includes Windows and Linux path and process handling, but desktop end-to-end acceptance currently covers macOS; the other operating systems have not been tested on actual machines. See [desktop installation and recovery acceptance](../evaluations/desktop-2026-10-24.md) for coverage and limitations.

### Development setup

Existing development environments can continue using the following workflow. It requires Python 3.12, uv, and a working Docker installation. Run these commands from a cloned repository. The development database has its own project volume, separate from the desktop installation above.

```sh
uv sync --frozen
uv run membrain init
docker compose up -d --wait
uv run membrain migrate
uv run membrain serve
```

Run the persistent worker in another terminal:

```sh
uv run membrain worker
```

The service runs at <http://127.0.0.1:8787>, with its access token saved in `.local/access-token`. The development workbench is available at the same address for manually inspecting underlying behavior; the target product does not require opening it. Run `init` once; it does not overwrite existing configuration. `.env` and `.local/` contain local credentials and are excluded from version control.

`init` only creates configuration. A development integration must also create a brain after the API starts and persist the returned `id`. Reuse that ID thereafter rather than creating a new brain on every startup. For example, create it once with:

```python
from pathlib import Path
from membrain.client import MemoryClient

with MemoryClient("http://127.0.0.1:8787", Path(".local/access-token").read_text().strip()) as memory:
    brain = memory.create_brain("My Agent")
    Path(".local/brain-id").write_text(brain["id"] + "\n")
```

The database binds to `127.0.0.1:55432` by default, and HTTP binds to `127.0.0.1:8787`. The workbench, API, and worker share the same core. Use `uv run membrain worker --once` to process one pending job per brain manually. `docker compose down` stops the database while retaining its volume; do not use `down -v` unless you intend to delete the entire database.

`MEMORY_DATABASE_URL` and `MEMORY_MIGRATION_DATABASE_URL` are libpq connection strings. Every connection the runtime opens to a loopback address (`localhost`, `127.0.0.0/8` or `::1`) requires SCRAM-SHA-256 authentication (`require_auth=scram-sha-256`), so the client does not answer a cleartext or MD5 password request and a process holding the port cannot obtain the password. The embedded database and the Docker databases from `compose.yaml` and desktop setup authenticate with SCRAM, so their connections, including the URLs written by `membrain init`, already meet this requirement. A URL that sets `require_auth` itself is used as written, for example for a local server that offers only another method; remote hosts and Unix-socket paths are not changed. This needs libpq 16 or later, which the psycopg binary package bundles; with an older libpq the runtime refuses to connect instead of dropping the requirement. The embedded database's backup tools receive the same requirement through `PGREQUIREAUTH`.

## What leaves your machine

memBrain's own processes (the service, its database, the hooks, the tool server, `membrain doctor` and the other commands) and the memory page talk to each other over loopback (`127.0.0.1`) and to nothing else, with the exceptions below. This was observed on Linux x86_64 on 2026-11-19 by running each of them in a network namespace that records every name looked up and every connection attempted ([record](../evaluations/network-audit-2026-11-19.md)); `tests/test_no_outbound_connections.py` repeats the check. macOS and Windows were not observed.

ONNX Runtime, which runs the local model, reports to Microsoft by default from version 1.29 (August 2026) in its Linux and macOS wheels: every process that loads it sends a description of the computer and the program (operating system, CPU, virtualisation, network type, the Python program's full path, device and process identifiers; no memory content was seen in it) to `mobile.events.data.microsoft.com` about ten seconds later, or, if it ends sooner, queues it for the next one, and keeps a device identifier and the queue in `~/.cache/Microsoft/DeveloperTools/.onnxruntime` on Linux. In memBrain that was the service at each start and the commands that check the model's state (`plugin start`, `setup`, `ui`, `status`, `desktop restart`, `doctor`), not the hooks or the tool server. memBrain sets `ORT_DISABLE_TELEMETRY=1`, ONNX Runtime's documented switch, before anything can load it, and calls `onnxruntime.disable_telemetry_events()`, the switch its Windows wheels document for their reporting through Windows event tracing. With the switch nothing is sent and no identifier is written (observed on Linux; on macOS and Windows only read in the wheels' contents and documentation). The switch is set when `membrain` is imported, so a program that loaded ONNX Runtime itself before importing memBrain (a host using the Python package as a library) has already started that reporting. Earlier memBrain builds did send these reports; the directory above can be deleted if no other program on the computer uses ONNX Runtime.

The memory page loads its scripts, styles and the 3D view's library from the local service only, and its Content-Security-Policy (`default-src 'self'`) stops the browser from loading anything from elsewhere. What your browser does by itself is up to the browser.

## Automatic integration

Automatic memory, recording each exchange and recalling before each reply without the main agent calling memory tools, comes from a host's own lifecycle: [plugin mode](#plugin-mode) for Claude Code, Codex and the other plugin hosts, the [OpenClaw](#openclaw), [AstrBot](#chat-bots-and-astrbot) and [Hermes](#hermes-agent) adapters, and the [proxy](#openai-compatible-proxy). memBrain's own Python turn runtime (`BrainRuntime`), with its on-demand orientation, its answer review before delivery and its model-driven recall controller, was removed with the [bundled chat](#bundled-chat-and-python-sessions-removed). Applications that drive the memory operations themselves use the [low-level interfaces](#current-low-level-interfaces).

`open_client()` starts or connects to the local service and returns a `MemoryClient` bound to the stable `brain_id`. Pass `directory=Path(...)` to select an installation directory, or `start_service=False` to connect only to an already-running service. It does not require copying an access token and does not read `.env` from the current working directory. Development deployments can still construct `MemoryClient` manually and retain the brain in their original database.

Historical user feedback may guide a reversible suggestion for the same task without certifying a permanent current rule. The host shares this [bounded permission](../architecture/historical-suggestions.md); current changes, false applicability and unresolved conflicts still constrain use. An earlier assistant proposal does not establish user adoption.

The host interpretation protocol, `memory-consumption-v5`, distinguishes a natural conversational acknowledgment from a claim that storage has completed. Without trustworthy completion evidence for the corresponding operation, the host must not claim that something has already been saved or permanently remembered. Capturing the original message does not establish that semantic consolidation is complete. This is a semantic constraint, not a word blacklist.

Assistant speech exposed for an explicit speech, quotation, episode or commitment request carries `assistant_speech_not_user_experience`; it cannot prove details of the user's life or external outcomes. An older literal's optional `source_act` explains a corrected speech-act interpretation while preserving its original statement. New events explicitly record their segmentation version. New cognitive jobs use `recall-resolution-v1`, inheriting `source-act-boundary-v1`; older frozen requests retain their prior contract. See the [source and recall repair architecture](../architecture/longitudinal-repairs.md) for scope and ranking, and [source-preserving recall resolution](../architecture/recall-resolution.md) for verified short expressions and compatibility.

`recall` accepts optional `detail_level="auto" | "summary" | "full"`; MCP exposes the same option. Auto can use a verified short expression for an older memory. Concrete detail cues and explicit recollection intents keep full detail. `summary` is a preference, not permission to omit necessary qualifications. `inspect(memory_ids=[...])` returns the full assertion and original sources. Compact context marks short expressions as `summary_expandable`; raw results retain complete memory documents and presentation diagnostics. Use the SDK context helpers for model injection rather than dumping that raw result. Existing assertions without a verified summary remain detailed, and upgrade performs no automatic paid archive rewrite.

### Recall workers, embeddings and lexical retrieval

The HTTP service runs recall and context-preparation transactions in four local worker processes by default. Each worker owns its database transaction, including current scope/deletion checks, scoring, response validation, traces and request receipts. The API validates the returned envelope as well. Model providers and their billing remain in the API process; workers receive query vectors and provider identity without loading another local model or receiving provider credentials. Query embedding retains its existing provider budget and snapshot checks.

Passive `candidate_hit` diagnostics are returned with the response, without duplicate rows in the learning trace table. Actual context selections, quotations and external feedback retain their durable trace records. The combined `recall`/`inspect` response cache retains at most 128 responses and 16 MiB of JSON-encoded content per brain, for at most 24 hours. Older responses are evicted as necessary. A response larger than that byte limit is returned normally but not cached. Request fingerprints remain durable: repeating an expired, evicted or invalidated read returns `version_conflict` and requires a new request ID; changing its original content still returns `idempotency_conflict`. A retained replay returns its original response without recomputing recall. Source changes and erasure invalidate all cached responses for the brain. Prepare receipts and feedback bindings have their separate existing lifecycle.

Schema 027 adds empty private cache and maintenance tables without rewriting old history at startup. An idle background-worker pass clears at most 256 legacy read-response bodies and 256 historical candidate diagnostics, using durable cursors and short transactions. It preserves request fingerprints, source memories and actual selection/feedback traces. Restoring a backup clears response caches and cleanup cursors while quarantined, before activation. The default desktop worker runs this maintenance automatically; self-managed services must run their worker. These limits bound live cached response content, not total PostgreSQL files: fingerprints, real history and indexes still grow, and PostgreSQL vacuuming reuses or releases dead-row space asynchronously. Maintenance does not run `VACUUM FULL` or promise immediate filesystem reclamation.

The worker queue is bounded to four admitted requests per worker, including running requests. Queue, database and computation time share the dispatched transaction's wall-time budget. An expired transaction rolls back its trace and receipt writes; a timed-out task keeps its admission slot until it ends. Overload and worker failure return retryable errors without automatically replaying a request. Workers become ready during API startup and consume additional memory. Set `MEMBRAIN_RECALL_PROCESSES` to `0` for inline execution or `1`–`4` for a worker count, then restart the service. Desktop startup also reads this environment variable. Embedded `MemoryService` instances stay inline unless explicitly given a runner.

#### What the removed learning left behind

**Removed:** background learning with a cognition model of memBrain's own (situation understanding before each runtime turn, and consolidation of messages into semantic claims, episodes, associations, belief relations and recall summaries, with its own budgets) was removed after runtime `2600219b`, for every installation, including those that configured a model. memBrain calls no model of its own; the host's AI writes notes and message cues. The [cognition policy](../architecture/cognition-policy.md), [cognitive budget](../architecture/cognitive-budgets.md) and [learning monitoring](../architecture/learning-monitoring.md) pages, and the other architecture pages about that pipeline, are kept as a historical record.

What an older runtime's learning stored stays in the database (no table or migration changed), and the runtime still handles it:

- **Recall** still reads stored semantic claims, episodes, belief relations and recall summaries: a stored exception or supersession still governs the old rule while it applies, and a claim with a recall summary is still shown short and expanded by its detail cues. It no longer follows stored associations between memories (nothing writes them), and it judges a conditional memory's applicability against no context observations, since only the removed orientation of runtime turns supplied them: such a memory is shown as conditional data with unknown applicability. Associations stay stored, are shown on the memory page and are erased with their sources. Episodes are still followed, because a host may write them again.
- **Correcting, forgetting and erasing** a message or memory still clears every row derived from it, also in archives the server holds: claims, episodes and their members, associations, belief relations, pattern views, learning jobs (result cleared, state `superseded`), feedback contributions and the access state recomputed from them (`legacy_erasure.py`).
- **Archives** that carry cognitive views and belief relations still export and restore (a local archive with its views; an uploaded one with its interpretations quarantined), and what is restored is erasable.
- **Learning jobs** (`orient`, `consolidate`) left queued, failed, deferred or running are never claimed again, whatever kinds a caller asks for, and are not counted as pending or failed in the status the plugin and the memory page show; they stay listed with the other jobs. Model-call reservations and budgets stay in their tables for recovery and erasure; nothing reads them otherwise.
- Orientations stored for runtime turns are no longer read: `prepare` no longer reads runtime turns (see [what the removed runtime mode left behind](#what-the-removed-runtime-mode-left-behind)).

Pattern views, which grouped facts that several episodes shared into one definition with per-episode differences, have been removed. The runtime no longer builds or reads them. Rows that an older runtime stored in `memory_pattern_views` stay in the database: correcting, deleting or erasing their sources, memories or episodes still clears them (`legacy_erasure.py`), and the memory page still shows the ones that remain valid. Exported archives never contained them, and restoring an archive no longer rebuilds them. `prepare` presents each selected fact on its own, with its own sources and applicability.

Archives retain an episode's organization information and complete source dependencies, remapping source versions during restoration. `organization_source_version` records only the episode identity before the transition and cannot serve as independent evidence; the archive does not guarantee inclusion of that older organization snapshot. It is not misinterpreted as a source-event version. Older formats remain compatible, and externally uploaded episodes remain quarantined initially.

Semantic embeddings in an environment-driven deployment, including the development setup above, use the same local embedding model as desktop profiles (see **Semantic recall without a key** below). Set `MEMORY_EMBEDDING_LOCAL_DIRECTORY` to an installation directory containing it, the same for the service and the worker:

```dotenv
MEMORY_EMBEDDING_LOCAL_DIRECTORY=/path/to/installation/models
```

The metered remote embedding provider (`MEMORY_EMBEDDING_BASE_URL`, `MEMORY_EMBEDDING_API_KEY`, `MEMORY_EMBEDDING_MODEL`, `MEMORY_EMBEDDING_MODEL_VERSION`, `MEMORY_EMBEDDING_DIMENSIONS`) has been removed. These variables are ignored: the service and worker start as usual and log one warning naming them, never their values. A deployment that set only them runs with keyword recall until `MEMORY_EMBEDDING_LOCAL_DIRECTORY` is set. Vectors such a provider stored stay in the database but are never compared with the local model's, because recall reads only vectors of the configured model, version and size; the worker's idle backfill embeds every current memory with the local model, and editing or forgetting a memory deletes its vectors of every model. Erasure still clears the query vectors that its `query_embedding` jobs kept; none are written now. Background processing creates vectors for newly published memories. Queries embed their text only when their request budget explicitly sets `max_embedding_calls > 0`. The default is zero; environment variables alone do not enable embedding calls on every query. For example:

```python
from membrain.client import default_budget

budget = {**default_budget(16000), "max_embedding_calls": 1}
result = memory.recall(
    "Which scents did I used to prefer?",
    conversation_id=conversation_id, branch_id="main", budget=budget,
)
```

Lexical retrieval combines the original feature-hash route with a bounded PostgreSQL word-match route for normalized ASCII query terms. Each route retains at most 512 candidates for recall or 256 for learning, often fewer under the request budget; each query reads one extra row to detect truncation. The combined pool is deduplicated and ranked by actual lexical overlap. The source bridge below remains a separate bounded route, and final source, dependency, and context budgets are unchanged. This reduces hash-collision misses without making recall exhaustive or database work constant-time.

Candidates can come from lexical retrieval, configured semantic vectors and episode structure, then undergo common source and applicability checks. After a lexical hit on a retained original source, retrieval also follows supporting evidence to the corresponding semantic belief. For example, even if the source is Chinese and its generalization is English, a query matching a valid supporting fragment can still find that belief. The bridge checks exact source versions, content hashes, scope, branch, and deletion status; counterexamples or background citations cannot masquerade as support. Complete dependencies and current applicability are still checked afterward. The source bridge reads at most 64 source events and retains at most 512 linked beliefs for recall or 256 for learning, with actual budgets potentially lower and one extra candidate row used to detect truncation. Reaching a limit reports restricted coverage. This does not establish arbitrary cross-language understanding or recover every paraphrase from sources with no lexical match. Representations use different access-decay policies: details move into deeper tiers sooner, while generalizations and key beliefs remain accessible longer, and explicit cues may still recover details. Decay parameters are adjustable engineering policies, not yet calibrated against long-term conversation and not biological laws of human forgetting. Access decay does not automatically erase original sources; permanent deletion still uses `forget`.

Internal retrieval hits and model claims that a memory was helpful do not increase external-use counts. External feedback credits a memory only through the `recall_feedback` of the `commit` action: a received original user message with a complete explicit confirmation or correction, such as “correct” or “wrong”, credits a memory only after a runtime turn delivered an answer containing one unique exact selected statement or quotation, with the current memory version and all supporting sources intact. Runtime turns are no longer created, so only turns an older runtime left can establish that; otherwise the feedback is kept as a trace that credits nothing. The runtime's automatic attribution of the user's next message to its previous answer was removed with it. Paraphrases, added questions or claims, ambiguous identical statements, imported feedback, and tool observations without outcome linkage remain trace-only. The binding such a turn stored (the final server-issued packet, exact context hash, selected versions and source hashes) is what the check reads; custom contexts opted out of it.

Each attributable feedback event/version contributes once to a separate provenance ledger. Correction or erasure invalidates affected contributions and rebuilds access from surviving evidence. Processing an older feedback event does not make it recent. Negative outcomes lower utility without increasing activation or refreshing reinforcement time. Migration 014 clears older access aggregates because they cannot establish exact delivered-use provenance; original sources and memories remain. These metrics describe utility, not truth probabilities, and do not promote an assistant's earlier statements into facts about the world.

The [first-release foundations report](../evaluations/v1-foundations-2026-10-25.md) records upgrade, feedback-provenance, semantic-outcome, provider-boundary, and interrupted-call verification. It is not the final first-release acceptance.

The fresh [October 25 lifecycle smoke](../evaluations/deepseek-2026-10-25-lifecycle-smoke.md) completed all five short scenarios with source-consistent delivered answers, known usage for 24 calls, and a correctly resolved preference change. It retains a minor unsupported detail in one stored episode and substantial `always`-mode latency. Sustained-history and first-release acceptance remain separate gates.

### What the removed runtime mode left behind

What an older runtime's chat mode and session SDK stored stays where it was (no table or migration changed), and the runtime still handles it:

- **Turn rows** (`memory_runtime_turns`, `memory_runtime_turn_transitions`), the working states their commits saved, and the feedback contributions and access state an attributed confirmation wrote stay in the database. A brain holding them starts, recalls, shows on the memory page, exports and restores as before; turns were never part of archives.
- **Nothing creates or advances a turn any more.** Pausing recording still stops every unfinished old turn (`recording_control.py`), and restoring an installation backup still quarantines them (`recovery.py`), both with plain SQL.
- **`prepare`, `commit` and `checkpoint` stay**, with the MCP tools `memory_prepare` and `memory_checkpoint`, and need no runtime turn. `prepare`'s `turn_id` is only the packet's identifier; it no longer reads the turn it names or adds an orientation stored for it. Working state is still written by `commit` and `checkpoint`, and `prepare` still shows it; `recall` no longer reads it. `assess_orientation`, which always needed a runtime turn, is refused with `unsupported_capability`. `commit`'s `recall_feedback` can still credit a memory that an old turn delivered, so access state can still change, and recall keeps reading it.
- **Erasing** a message an old turn recorded (`erase_content`, by event, memory, conversation or the whole scope, a reply with the message it answered) leaves neither its text nor a digest of it on any turn row. Turn rows never held message bodies, but older runtimes stored SHA-256 digests beside the references: of the input (`input_fingerprint`, over the message id and text), of the delivered answer (`delivery_receipt.content_sha256`), of a reviewed draft (`response_review.draft_sha256`) and of each selected memory's statement (`prepared_memory_selection.memories[].statement_sha256`). Erasure replaces those of erased events and memories with 64 zeros, the content-free marker temporary turns already used; the rows, their stages and every id stay, for recovery quarantine (`legacy_erasure.redact_runtime_turns`). Hiding a message (`suppress_recall`) keeps them. A backup taken before the erasure is erased the same way when it is restored, because the restore replays the erasure.
- **Profiles and backups**: `chat.json` (the chat model's address, model and key) and `sessions/` (pending chat turns) beside an old profile are ignored. A backup carries them unread, as older runtimes wrote them; a restore writes `chat.json` back unchanged and keeps the sessions only as recovery evidence, as before.
- **Removed interfaces fail plainly**: the CLI commands are an invalid choice for argparse, the HTTP paths answer `404` like any unknown path, the Python modules raise `ModuleNotFoundError`, and the TypeScript `activeScope()` method no longer exists.

## Current low-level interfaces

The Python client is in `membrain.client`, with an underlying workflow example in [examples/connect.py](../examples/connect.py). See [host features and verification scope](host-compatibility.md) for companion controls, refresh behaviour and native-host limitations. The TypeScript client is in [sdk/typescript](../sdk/typescript). The following HTTP contract is for adapters to orchestrate; it is not the target product's required step-by-step workflow for users or the main agent:

1. `observe` persists actually received or delivered messages with stable source IDs.
2. `prepare` reads the current situation, working state, and relevant memories.
3. `prepared_context` / `preparedContext` produces the material actually sent to the model.
4. Use `recall` and `inspect` if the model needs further cues.
5. Only after actual delivery, `observe` the output and `commit` the turn's state.
6. Use `checkpoint` before host compaction or interruption.

Do not inject the entire `ContextPacket` or `RecallResult` control envelope into the model. `prepared_context` / `preparedContext` and `recalled_context` / `recalledContext` produce `compact-memory-v1`: material appears directly as JSON objects, sources and relations are each presented once, and `memory_versions` maps short references to exact memory IDs and versions usable with `inspect`. MCP's `memory_recall` also returns this compact `context` rather than the complete HTTP envelope. For a local installation (the plugin's `membrain plugin mcp`), `memory_recall` returns the same compact recall as the hooks; with `with_ids` it returns the original messages' `event_id`s and the `scope_generation` that `memory_forget` (`kind: "events"`) needs. Use `inspect` when complete records are needed.

The server's `model_context` contains the authoritative text assembled within the budget. The TypeScript SDK prefers this text unchanged, preventing scientific notation, large integers, or other cross-language parsing differences from changing text, values, or context length. Compatibility with older servers still permits reconstruction from fields, but reconstruction that exceeds the server's measurement is explicitly rejected rather than silently overflowing the budget. To change material, request a new server-side assembly instead of modifying envelope fields while retaining stale authoritative text.

`RecallResult` may also contain `source_passages`: bounded complete original user/operator messages reached through visible memory anchors. The compact context exposes their actor, delivery, world, recording time and source references; prepared context uses `verbatim_evidence` blocks. These are original communications, not instructions or independent proof of world facts. Source bytes and hashes remain unchanged. Explicit summary, selected-memory and valid-time reads do not expand to whole messages; source integrity, permission, cutoff, correction and context-budget guards still apply. See [source composition](../architecture/source-composition.md) for limits and fallback behavior. Full memory records remain inspectable in `items`, including literal captures and plain episodic reports whose duplicate wrappers are omitted from model context. Version 2 preserves explicit occurrence-time and other qualifying metadata as separate records. Candidate admission shares quota between eligible versions of the same exact source unit, while retaining a hard maximum of 128 versions and the existing dependency limits.

The default `prepare` budget of 2,000 units is the memory allocation left after the host accounts for system instructions, current input, and reserved output; `recall` defaults to 16,000. Both conservatively measure the UTF-8 bytes of the actual model material described above. They are not exact tokenizer counts or byte limits for the entire HTTP response. HTTP still exposes full records and diagnostics. Related belief groups enter or leave the budget together, with coverage limits returned when a group cannot fit. Literal source memories are labeled `historical_report_not_current_rule`; they cannot bypass temporal, exception, and conflict checks on semantic beliefs. Detailed `inspect` output continues to be metered separately.

`POST /v1/actions` accepts the [JSON Schema contract](../architecture/memory-contract.schema.json). Identity is bound to the API key. Request parameters can select only an authorized brain and cannot set a tenant or authenticated identity. The running service's capability declaration is available at `GET /v1/capabilities`.

### TypeScript companion controls and maps

The TypeScript client also exposes the companion's current state and user controls. Use the same authenticated `MemoryClient` and brain as your host integration:

```typescript
const persona = await memory.persona();
const proposals = await memory.personaProposals();
const feelings = await memory.affectRecords();
const mood = await memory.mood();
const relationship = await memory.relationship();
const structure = await memory.memoryMap({ structure: true, trace: true });
const companion = await memory.companionMap();
```

`setPersona(card, { madeBy: "user" })`, `personaVersions()`, `restorePersona(version)` and `resetPersona()` manage the versioned card. `hostDefault: true` on `setPersona` sets the card used by reset. `personaProposals()` returns pending and decided proposals; call `acceptPersonaProposal(id)` or `rejectPersonaProposal(id)` only after the user's decision. `deletePersonaHistory()` erases versions and proposals. Accepting proposals must not be an automatic response to conversational sentiment.

`clearAffect()`, `pinMood(true)` / `pinMood(false)` and `resetMood()` control feelings and simulated mood. Pinning holds the mood at its baseline. Relationship controls are `addBoundary(topic, aliases)`, `removeBoundary(id)`, `acknowledgeCommitments(noteIds)` (at most the first 50 IDs per request), and `resetRelationship()`. Explain each reset's scope to the user: relationship reset clears its shared moments and acknowledgements, while preserving the persona and, since 2026-11-18, the boundaries (the user removes those one by one; `removed.boundaries` is always 0). The support style and the familiarity cap, with `setSupportStyle` and `capFamiliarity` and their routes, were removed on 2026-11-18 (see [retired relationship records](#retired-relationship-records)). These are the existing server operations, with the server's validation, authorization and erasure rules.

Each method defaults to the client's brain. Read/control methods accept an explicit final `brainId`; persona changes and maps accept `brainId` in their options. An override cannot bypass the API key's ownership scope. Requests retain the client's recovery acknowledgement and timeout, and a failed request does not fall back to another brain or retry a write. Maps default to 200 nodes/400 edges, omit sensitive content unless `includeSensitive: true`, and obey the server's hard limits of 500/1,000. They return bounded stored records and relations; the optional trace covers recorded message recall only. These methods do not add an automatic TypeScript chat runtime or make model calls.

#### When the runtime cannot run

Host launchers need only uv. The hook commands, `bin/membrain-hook` (and `membrain-hook.cmd`) and the OpenClaw plugin run the installed runtime with `uvx` when it is on the path and with `uv tool run`, the command `uvx` stands for, when it is not; the MCP entries (`.claude-mcp.json`, `.codex-mcp.json`, `.codebuddy-mcp.json`) always start the tool server with `uv tool run`, with the same options as before. Because the runtime cannot report that it is missing, the launcher itself gives the host's AI one line at session start, in the hook output format the runtime uses (`hookSpecificOutput.additionalContext`), and nothing on any other event:

- Neither `uvx` nor `uv` found: "memBrain is installed but cannot run: uv was not found on this computer, so nothing is remembered or recalled. In your first reply, tell the user this once and ask them to install uv from https://docs.astral.sh/uv/ and then start a new session."
- uv found, but the installed runtime does not run (the first session, while the background installation is still running, or an installation that failed): "memBrain is installed but its runtime is not ready yet, so nothing is remembered or recalled until it is. It installs in the background; the first time needs an internet connection and takes a few minutes. Memory then starts by itself; no new session is needed. In your first reply, tell the user this once, and that if they see it again in a later session the installation is failing, for example without an internet connection." (429 characters; until 2026-11-19 it said "nothing is remembered or recalled in this session", which was false when the installation finished during the session.)

The hooks still exit 0 and write nothing. While the background `uv tool install` is running, `uvx` (and `uv tool run`) would wait for the lock uv holds on its tool directory for the whole installation, until the host stopped the hook at its timeout (10 seconds at session start, 15 per message, 10 after each reply) with no line given ([record](../evaluations/first-run-2026-11-19.md)). Every synchronous launcher therefore sets `UV_LOCK_TIMEOUT=2` (the Claude Code and Codex hook commands with `export UV_LOCK_TIMEOUT=2;`, `bin/membrain-hook` and `membrain-hook.cmd` for the hook call only): uv gives up after 2 seconds, the session start gives the line above, and a message waits 2 seconds instead of 15. The installation itself (the asynchronous start hook, `membrain-hook start`) still waits for the lock. uv 0.9.30 and later honour the variable (checked with 0.9.30, 0.10.0, 0.11.0 and 0.13.6); 0.4.30, 0.6.17, 0.8.0 and 0.9.0 ignore it and wait as before. A message sent before the runtime can run is not kept: the shell never stores hook input. Once the runtime runs, its own session notice applies (for example "memBrain is starting or unavailable" while the service cannot start). OpenClaw adds only the first line, once per session, and only for the owner's own conversations. A host that does not run the plugin's hooks at all (Codex before `/hooks` trusts them, or a Windows host that falls back to PowerShell) shows neither line; see [host features](host-compatibility.md#when-the-runtime-cannot-run).

#### While the service starts

A first start holds the profile for 10 seconds to over a minute while it prepares the embedded database (see [the record](../evaluations/first-run-fix-2026-11-19.md) for where the time goes). A hook waits at most 1.5 seconds for the profile lock (and 0.1 seconds for any later read in the same hook), then treats memory as starting: the message is staged and queued, the service records it once it runs, and the hook returns in about 2 seconds instead of being stopped by the host with nothing staged. The host is told, with each message while the service is not ready (and at the end of the session notice), what it can act on:

- starting: "memBrain is starting, so nothing can be recalled yet; new messages are queued for memory meanwhile." (99 characters)
- a restart after an update: "memBrain is restarting after an update, so nothing can be recalled yet; new messages are queued for memory meanwhile."
- the saved API port taken: "memBrain cannot start: another program is using port N, which it needs. New messages are queued, but nothing can be recalled until that program is closed; tell the user once."
- otherwise (for example a recovery that has not finished, or a recording state the service could not report): "memBrain cannot confirm its recording state right now; new messages may be queued for memory."

These replace "Current server recording state is unknown. Messages may be queued locally; server persistence is not confirmed. Reconnect to confirm it; local resume does not change server recording controls." (192 characters). None claims that a message is kept: a queued message is still checked against the recording state when it is delivered. When the last known state is a pause, or that state cannot be read, the earlier fail-closed wording is unchanged.

When the first message memBrain sees in a conversation comes after earlier ones it never saw (the runtime was not installed yet, or uv was updating it), that message's context says so once: "memBrain was not running yet for this conversation's 3 earlier messages, so they were not kept; tell the user if it matters." The count comes from the host's transcript (`transcript_path`, Claude Code's format): user messages before this one, dated within the 14 days a session's state is kept, while the runtime has staged no message of that conversation; slash commands and interruptions are not counted. Hosts whose transcripts are in another format (Codex) or that pass none are not told.

The service restart after an update is decided under the lifecycle lock, so the session's own start and a tool server's start no longer both restart it.

#### The host AI's pause quotes the user

Every pause tool a host AI calls (`memory_pause` over MCP, `membrain plugin tool pause` and OpenClaw's `membrain_pause`, Hermes's `membrain_pause`, `ChatMemory.pause` and AstrBot's `membrain_pause`) requires `request`: the user's own words asking not to be remembered, copied from their current message. All of them go through `host_recording.agent_pause`, which pauses only after `host_recording.pause_refusal` allows it:

- `request` missing, not a string, or shorter than two characters once surrounding quotes and punctuation are removed: refused with `code: "pause_request_missing"`.
- When the user's current message is known, the words must be part of it: refused otherwise with `code: "pause_request_not_in_message"`. Both sides are compared after Unicode NFKC normalisation, case folding and collapsing whitespace; the quotation also loses surrounding quotes and punctuation. The current message is the newest unfinished turn the host staged in each of this person's conversations within the last six hours (`host.messages_in_progress`; an older unfinished turn of the same conversation was left by an interrupted host). It is the text as staged, with `<private>` parts and credentials already removed, and a quotation is also compared after the same removal.
- When no current message is known (the host staged none, or the turn has finished), or one of them was not kept because its turn was excluded from recording when it arrived (for example a message that itself began "Off the record:"), the words are accepted as given.

A refusal is `{"error": "Pause only when the user asks you not to remember or store something. Pass request: their own words, copied from their current message. Nothing was paused.", "code": ...}` and changes no state; the turn is recorded as usual. A successful pause answers with the usual recording state plus `note`, asking the AI to tell the user in a few words that the conversation is no longer recorded (or for how many hours, or until they say so), so a pause the user did not ask for is visible to them. The user's own controls (`membrain plugin pause`, the memory page, the local and server recording APIs, `host.pause` and `host_recording.pause`) take no quotation. The check exists because a host AI once paused, with no arguments and no reasoning, after its answer was written ([record](../evaluations/maturity-sixth-attempt-stop-2026-11-16.md#why-the-host-paused-found-after-unsealing-the-turn)); it does not judge whether the words really ask for a pause, only that they are the user's.

#### Off-the-record dates

When a user message is left unrecorded because recording was paused (any pause: the host AI's pause tool, the product's own pause on the user's words, the user's own local controls, or the server recording policy), the host side remembers the user's local date of that turn and nothing else: no text, topic, conversation or session id. It is written where every host's turn is settled (`host._take_turn`, for a turn excluded with `local_pause`, `pause_requested` or `server_paused`), where an abandoned turn is settled on a later session start (with the turn's own start time), and where a replay finds a queued user message refused because server recording was paused. A turn recorded as usual, one resumed at the user's request, a refused pause, an erasure or a turn-identity conflict writes nothing. The dates sit beside the pause state, `plugin/off-record.json` for the installation's own memory and `plugin/off-record-users/<user brain>.json` for each user of a multi-user host, at most the 10 most recent distinct dates, written under the same session-state lock. A role-play's dates are its person's, as its pauses are. The date is taken from the same clock as recorded times (`helpers.now()`, which in an evaluation process is the scenario clock) in the display zone (`helpers.local_date`).

While the list is not empty, the session notice of that person (every host that gets a session notice: the Claude Code, Codex, WorkBuddy and OpenClaw hooks, Hermes, `ChatMemory` and so AstrBot and the proxy, also while the service is starting) adds one sentence naming the 5 most recent dates, oldest first: "At the user's request, part of your conversation on 2026-04-29 and 2026-05-12 was off the record and nothing of it was kept. If the user asks about something from then, or about something they say they told you that you find no record of, tell them it may have been in that part and that you kept nothing of it because they asked; do not say it was not said, and do not guess." Without it, hosts asked later about the stretch denied it had been said ([record](../evaluations/maturity-seventh-attempt-2026-11-16.md#what-the-run-showed-about-the-product)). Another person's dates are never shown. Erasing a person's whole memory removes their file: through the host (`host.erase_user`, `membrain plugin forget-user`, `ChatMemory.forget`), and also on the memory page ("Erase everything") or through the API, with a `forget` of selector kind `all_authorized_scope` and mode `erase_content`, when the installation's own local service carries it out. Once that erasure has completed, the service removes the brain's file from the same installation (`host.erase_off_record_dates`, under the session-state lock): `off-record.json` for the installation's own brain, `off-record-users/<brain id>.json` for a user's brain; any other brain, a role-play's among them, has no dates of its own. A conflict (for example a stale `expected_scope_generation`), a rejection or a failure leaves the file, and so does every other forget: single messages, a conversation, or `suppress_recall`. A date recorded after the erasure is kept as usual; a request sent again with the same idempotency key is answered from its stored response and removes the file again. A service that is not the installation's own (a remote deployment) cannot reach the host's files: an erasure there leaves the dates until the person's memory is erased through the host. The dates are not part of an export or a backup. A legacy bootstrap queue imported by `plugin start` (`host.deliver`) writes none.

`GET /v1/brains/{brain_id}/timeline` returns current, non-deleted, non-suppressed messages newest first, each clipped to `max_item_characters`, with `complete: true` only when nothing was omitted. Optional filters: `role` (repeatable), `exclude_conversation`, `conversation_id`, and `event_id` (repeatable, up to 100). The Python and TypeScript clients expose this as `timeline()`. Since 2026-11-18 a note that replaced others carries `replaced`: every note it replaced, directly (`depth` 1) or through earlier replacements, newest first, each with its `event_id`, the `source_event_ids` it rests on itself and, while its content exists, its `recorded_at`, `text`, `actor_role` and `producer`; once erased only `erased: true`. A user message overruled by a current note carries `superseded_by` (`note_id`, `recorded_at`, `actor_role`): it is a message a replaced note was saved from (not one that note kept from its own predecessor), the replaced note's content exists, and the current note heading its chain has a source message of its own. Both are read from the records on each request (`note_lineage.py`: one query for the notes and one for the messages of a response), never stored. With `erasure=true` (since 2026-11-19, for the memory page's delete questions) every item also carries `erased_with`: the records that deleting that item alone would erase as well, oldest first, found by the same walk of the dependency table that the erasure itself takes (`erasure.py`), limited to records whose content still exists. Each has `event_id`, `recorded_at` and `kind`: `note` (with `text`), `earlier_note` (a note that a note in the walk replaced), `hidden_note`, `feeling` (`label`, `topic`), `message` (`actor_role`, `conversation_id`, `text`), `suggestion` (a personality suggestion) or `record`. It is read on request, never stored.

At session start the plugin injects, in this order and within about 8,500 characters:

1. `<membrain-notes>`: notes saved by the host model with the `memory_note` MCP tool, oldest first, each with its ID. Notes are short durable facts (health limits, people, dates, budgets, preferences, unconfirmed plans); a note that replaces another suppresses it. The replacing note is linked to the replaced one by a dependency row (since 2026-11-18): the current note's line names the day of the note it replaced ("(replaces your note of 2026-11-02)", never its sentence), a user message the current note overruled is marked "superseded by your note of …" in the history, recall and search lines, and deleting or hiding the current note reaches every note it replaced. The recall tool lists up to three matching current notes first, marked "note". They are stored as assistant-authored events in the reserved `membrain-notes` conversation, so attribution, deletion and backup apply as usual. For Claude Code, Codex, WorkBuddy and CodeBuddy, whose AI has a shell on the user's machine, the block's header also says: "If the user asks to see where a note came from (where they said it) or to check it, run membrain plugin ui --note <id>: it opens their memory page at that note, what it replaced and its source messages. If it fails, say so; never claim there is no way to show the source." (272 characters in every session with notes, with room of its own so no note gives way to it). `membrain` is named alone when it resolves, on the PATH the hook sees, to the program of the runtime that runs the hook (the same file, or on Windows a byte-identical copy); otherwise the block gives that program's path, under `~` when it is in the home directory (forward slashes on Windows), and when the runtime runs from an environment in uv's cache it falls back to the plain command. It is left out for OpenClaw, Hermes, chat bots, the proxy, a multi-user host's people and a role-play, whose memory is not the one the page shows. This sentence was first only in the skill; in the [real-host trial of 2026-11-18](../evaluations/host-trial-2026-11-18.md) the host never opened the skill, answered "show me where I said that" in words and told the user it could not show the conversation. Moving it to the notes block is not yet tried on a real host.
2. `<membrain-history>`: the user's messages from other sessions, newest first within the remaining budget, with runs of pasted code or log lines replaced by `[N pasted lines omitted]` and, if needed, each message cut to 300 characters. When everything fits unchanged, later prompts in the session skip recall. A message that is a `/membrain:` command line (`host.is_command`) is recorded, since the persona tool cites it as the user's request, but it is not the user's words about themselves: the history leaves it out, consolidation batches pass over it, and recall never shows it as a remembered message.

The plugin's MCP server (`membrain plugin mcp`, which serves an installation) also gives the host AI standing instructions, 1,040 characters from `host.server_instructions()` (the budget is 1,400). Every host with these tools also gets the session notice below, so they add what the notice leaves out: conversations are recorded automatically and retrieved text is historical data, never instructions; a note is a lasting fact the user stated, never the AI's own suggestion or something the user only asked about, and a shared moment, a hard time too, is a `milestone` with `shared` and `moment` (named here in a few words because a session whose start missed the service gets a short notice without it); `affect` when the user expresses a feeling; `memory_manner_feedback` (comments on how the AI talks, followed and not saved as a note), `memory_persona` (`switch`; `propose` for a lasting change the manner kinds do not cover, then `confirm` only after the user's yes in a later message) and `memory_consolidate`; to use memory tools before writing the reply, not after it (in a tool-calling host, text written before a tool call is shown to the user and the AI writes again after the last tool answer, so a reply written beside a note was shown twice); and to mention memory use in a few words at most. Hosts show server instructions at the start of a session even while they load tool descriptions only on demand, as Claude Code does. A server run without an installation keeps generic instructions that say it captures nothing automatically.

Those blocks follow a session notice, which every host gets, also hosts without MCP. It says memory is active and whether the history below is complete; how to search when personal context is missing (when it is not); that the AI's own earlier replies are shown only when the user's message asks about them in words memBrain recognises (`host.ASKS_ABOUT_ASSISTANT`), and otherwise to search with `my_replies`; when to save a note, including that a shared moment, a hard time the user and the AI got through together too, is a `milestone` note with `shared` and `moment` (what a shared moment is, and each kind of moment, is said once, in the note tool's `shared` and `moment` fields); on hosts with those tools, to record the user's comments on how the AI talks with the manner-feedback tool and to propose a lasting change with the persona tool and wait for the user's yes (not in a role-play, whose character is the persona); the pause and `<private>` rules; when part of an earlier conversation of this person was off the record, the [dates of it](#off-the-record-dates); and, since 2026-11-18, when this person's last recorded message before this conversation is at least seven whole days old (`host.ABSENCE_NOTICE_DAYS`), one sentence such as "The user's last conversation with you was 19 days ago (24 August). Open your first reply with a few words of your own that welcome them back (no set phrase), then answer; never say you missed them or were waiting, never ask why they were away, and do not make them feel they should come more often." The gap is counted between the user's local dates (`helpers.display_zone()`) on the clock of recorded times (`helpers.now()`, the scenario clock in an evaluation), and only when that many full days have passed too; notes, the other reserved conversations, messages typed on the memory page and imported conversations are not a conversation. Only a message that still exists as a current, readable record counts: when the user deletes the last one (on the memory page or by any erasure), the one before it is used, and with none left there is no sentence. Whether there is one is decided at the session's first context and waits in the session's state until the session's first prompt, like the persona intro; a chat bot, which asks for the session context before every message, gets it with the first message only. The session's state keeps only that decision, never the sentence or its date: each time the sentence is shown it is worked out again, so a message deleted in between is never named (since the outside review of 2026-11-18; a sentence an earlier runtime kept is dropped unread). A first conversation and a role-play get none. With the default tools it is about 1,140 characters with a complete history and 1,420 without; session start reserves room for the longest notice before fitting the history.

**The companion on a coding host** (owner's decision, 2026-11-19). The plugin's hooks on Claude Code, Codex and WorkBuddy (`plugin.CODING_HOSTS`) start every session quiet (`host_context.snapshot` with `quiet`): the `<membrain-persona>` block holds only the card's voice and the traits, values and boundaries the user's personality type does not have (what the user agreed to or wrote, `persona.render_manner`), with one clause that it is the agent's own manner; the `<membrain-relationship>` block holds only the topic boundaries and missed promises; there is no mood block, and shared moments are left out of the notes. The first persona's introduction and the absence sentence wait in the session's state. The prompt hook hands the rest once, when the user's message is casual or emotional by a fixed English and Chinese rule (`conversation_tone.companion_cue`: the user talking about the agent, a heavy feeling in any message, or a greeting, small talk, a lighter feeling, a hard day or a sigh in a message that holds no task) or when the host used a companion tool in the session (a note with `shared`, `moment` or a reported `affect`, manner feedback asking for more warmth or play, or the persona tool): a `<membrain-companion>` line, the full persona, mood and relationship blocks, the introduction (only to a greeting, small talk or a question about the agent) and the absence sentence (only at the session's first message), without the notes again; the companion then stays for the session. Everything is still recorded and computed as before, and the memory page shows it all. Other hosts, OpenClaw and role-play are unchanged. Measured in the [record](../evaluations/quiet-companion-2026-11-19.md).

Dates written for the host AI are the user's calendar dates in the computer's time zone (`helpers.local_date`), as the mood line's time is: on notes, history and recalled messages, consolidation batches, the records `memory_recall` returns with `with_ids`, the relationship block's "since" and its shared moments. Stored records and API fields keep UTC, a date the user gave (`due`, `occurs_at`) is shown as given, and familiarity still counts distinct UTC days.

**Typed notes, people and coming up.** Every note tool (`memory_note`, `membrain_note` and `membrain plugin tool note`) accepts optional fields besides `text` and `replaces`: `kind` (`person`, `constraint`, `preference`, `plan`, `routine`, `milestone`, `relationship`, `agent_commitment`, `other`), `about`, `aliases`, `status` (`intended`, `scheduled`, `done`, `cancelled`, `superseded`), `due` and `occurs_at` (`YYYY-MM-DD`, or `YYYY-MM` when the day is unknown), `pinned`, `sensitive`, `shared` (with `milestone`: a moment the user and the agent shared) and `moment` (with `shared`: `play` for a joke, a game or play together, `hard` for a difficult time the two went through, `other` for any other shared moment). The tools' text says that `person` also covers the user's family, friends and pets, that `relationship` is only about the user and the AI, that `constraint` is a limit on what the user can do, eat, afford or use (not their job), and never to note something the user did not state. The simulated mood reads `moment`: a shared moment is playful when it is `play` and glad when it is `other`; a `hard` one does not move the mood (what the user felt is recorded as affect when they expressed it). A hard time counts toward familiarity like any shared moment. Since 2026-11-18 the tools also say that something the user only tells the agent about (a quarrel with someone else, a success at work) is not a shared moment: shared means the two did it or went through it together in conversation; and that news which plainly carries a feeling the user does not name is saved with an inferred `affect`. The relationship block's list of shared moments opens with one sentence (`relationship.SHARED_MOMENT_CUE`): "You may refer to one of these when what the user says makes it relevant, in your own words: lightly for a hard time that has mellowed, gently for a recent one. Never recite the list." In the relationship block it is marked to be left alone unless the user brings it up while it is recent, and once 30 days have passed and the user has talked on 5 later days (`relationship.HARD_MELLOW_DAYS`, `HARD_MELLOW_CONVERSATION_DAYS`) it is marked as something the two came through together; the relationship response then carries `mellowed: true` for it. A shared moment saved without `moment` is still read with a small fixed English and Chinese word list (`mood.PLAY_WORDS`), which misses paraphrases and other languages. A typed note is stored as plain text with a header, `[plan · intended · due 2026-11-14 · about Mei] Book a sesame-free restaurant.`, so recall, the memory page, replacement and deletion treat it like any note; plain notes stay valid. At session start notes are grouped (People, Health and constraints, Plans, Your commitments, Milestones, Preferences, Routines, Your relationship, Other); plans and commitments show their status ("intended, not confirmed done"), and sensitive notes are marked to be mentioned only if the user brings them up. A `<membrain-coming-up>` block, with today's local date, lists open plans, commitments and milestones due within 14 days, open plans whose date has passed, and undated open commitments. Month-only dates keep their precision: a current month is shown with the day unspecified, and plans or commitments become overdue only after the entire month has passed. When there are more notes than fit (about 4,000 characters), session start keeps pinned notes, the user's own, constraints and people, and open plans and promises before the newest of the rest, says how many were left out, and names likely duplicate pairs for the agent to merge. When a message mentions a person's alias, recall also searches by their name, so "the sparky" finds what was said about Dave.

Before each reply, `user-prompt` recalls up to about thirty ranked statements (keywords, plus meaning when the local model is installed; only the three closest meaning-only matches are kept) and shows the up to eight messages they came from, oldest first, each as a window of about 700 characters around the match.

When recall needs current topic boundaries, Python hosts use `GET /v1/brains/{brain_id}/relationship/boundaries` (`client.relationship_boundaries()`). It returns `{"boundaries": [...]}` with the same IDs, topics, aliases and recording times as the full relationship response, under the same authentication, brain lock, reset and erasure rules. This avoids computing familiarity, shared moments and commitments for a boundary check. Each recall reads current state; boundaries are not cached between requests. A missing older route (404/405) falls back to the full relationship route; other failures and malformed boundary responses stop recall.

**Semantic recall without a key.** With the `semantic` extra (ONNX Runtime, `tokenizers`, NumPy), `plugin start` downloads `multilingual-e5-small` (int8 ONNX export of `intfloat/multilingual-e5-small`, MIT licence, about 135 MB) into `models/` in the profile directory, pinned to a revision and verified by SHA-256. `HF_ENDPOINT` selects a Hugging Face mirror; `MEMBRAIN_SEMANTIC=0` disables the download. ONNX Runtime's reporting to Microsoft is switched off ([what leaves your machine](#what-leaves-your-machine)). Once the files are present the desktop service sets `MEMORY_EMBEDDING_LOCAL_DIRECTORY` internally, embeds every current memory (memories written earlier are backfilled when the worker is idle) and embeds each recall query in the same process, about 4 ms per short text on a laptop-class CPU. Hook and MCP recall request one query embedding (`max_embedding_calls: 1`); keyword and vector rankings are fused. Without the extra or before the download finishes, recall stays lexical. Server deployments can set `MEMORY_EMBEDDING_LOCAL_DIRECTORY` to an installation directory containing the model; it is the only embedding model.

**Turn lifecycle and privacy.** Host adapters share `membrain.host`. Each prompt is staged independently by owner, producer and source event key in the session's state file, and stored together with its matching reply. Pausing during a turn keeps that turn out as well. A new prompt or context refresh does not finish other active turns; any session start stores unanswered inputs older than 30 minutes on their own. Before anything is staged, spooled or stored, `<private>…</private>` spans become `[private]` and values that look like credentials (provider API keys, GitHub and Slack tokens, AWS access keys, JWTs, private keys, `password=`-style assignments) become `[secret removed]`. Scrubbing is pattern based and can miss unusual formats.

**One memory per person for shared bots.** Adapters for group and multi-user hosts (QQ, Telegram, Discord bots, proxies) pass `user_id` (for example `qq:12345`) to `session_context`, `prompt_context`, `finish_turn` and `pause`. Each user gets their own brain, `user-` plus a stable digest of the ID, created on first use with `PUT /v1/brains/{brain_id}` (`{"name": ...}`; idempotent, and never takes over a brain owned by another identity; `ensure_brain()` / `ensureBrain()` in the clients). Notes, history and recall never cross between users. Spooled and staged records keep their user, and `pause(user_id=...)` stops recording for that user only; a pause without a user applies to everyone. Without `user_id` the installation's own brain is used, as in single-user hosts.

Completed host turns first append both scrubbed messages to `plugin/spool.jsonl` and synchronize the file before marking the staged turn complete. Online callers replay one bounded batch: at most 16 records with a one-second budget checked between requests. A request already in flight retains its existing timeout, so this is not a strict end-to-end deadline. The local service independently drains pending records in batches of at most 64, with a separate two-second HTTP timeout and bounded retry backoff; another host callback is not required. Recovery preserves the original source identifiers, owner and recording revision, so a lost server response does not duplicate events or refresh permission. Abandoned inputs use the same queue-before-completion ordering. Erasure serializes with queue admission and replay, preventing an already staged turn from repopulating an erased brain through this path.

A synchronized `plugin/spool.cursor.json` stores only the confirmed byte position and a prefix checksum. Confirmed progress survives a later transient failure, and a missing or invalid cursor falls back to idempotent replay. Queue reads take at most 256 KiB per batch, except that one oversized record can extend the batch up to the queue limit. Acknowledged prefixes are compacted at 1 MiB, half the file, or completion rather than rewriting the whole backlog after each small batch. Policy-rejected content is compacted before returning; user erasure clears the cursor and pending content together. Pending-record counts exclude acknowledged prefixes.

The queue has a strict 64 MiB UTF-8 byte limit, including the entire new turn. A full queue returns no accepted receipt and leaves the staged turn available for a callback retry; a partial append or synchronization failure also cannot mark it complete. A reply that never entered the queue still requires the host to retry its callback; later abandoned-input recovery cannot reconstruct that reply. `finish_turn` receipts mean stored **or durably queued**, not successful learning. Server-policy and permanent rejections observed during the current replay are excluded from its receipts; queued records can still be rejected by later background replay. Previously queued content remains subject to the documented local-pause rules; server pause/revision changes are checked again during replay. These guarantees cover process interruption after queue admission, not arbitrary hardware corruption or a transaction spanning both the local filesystem and server database. Hook failures are written to `plugin/hooks.log`; each exchange's recording result can be [looked up afterwards](#looking-up-a-recording-outcome). The Claude Code packaging lives in `plugins/membrain`; see [plugin mode](../architecture/plugin-mode.md).

### Host memory

Hosts keep their own memory files, and memBrain is meant to sit beside them: keep the host's memory for project and environment conventions, and let memBrain hold what matters about the person across hosts.

| Host | Its own memory | Recommended setup |
| --- | --- | --- |
| Claude Code | Auto memory (`MEMORY.md` index plus topic files per project) | Keep it for project facts; run `membrain plugin import` once so `user` and `feedback` memories reach every host. Imported notes stay visible in Claude Code, which loads only the index at session start. |
| Hermes | `USER.md` and `MEMORY.md` in the system prompt | Nothing to do: the provider imports `USER.md` when it changes and mirrors new `USER.md` writes; `MEMORY.md` stays in Hermes. Notes imported from Hermes are not repeated in Hermes's own prompt. |
| OpenClaw | Workspace `USER.md`, `MEMORY.md` and daily notes | Keep them; run `membrain plugin import --from openclaw`. Notes imported from OpenClaw are not repeated in OpenClaw sessions. |
| Codex | `memories/` summaries | Mostly about repositories; import with `--all` only if they hold personal facts. Notes imported from Codex are not repeated in Codex sessions. |

To use memBrain alone, turn the host's memory off in its settings; nothing in memBrain depends on it.

### Chat bots and AstrBot

`membrain.adapters.chatbot.ChatMemory` serves every user of a bot from one installation. Bot frameworks call `context(speaker, text, session=...)` before a model request (session notice, the user's notes and earlier days, related messages; refreshed from the service for each request) and `record(speaker, reply, session=..., prompt=...)` after the reply, and expose `note`, `search` (with `replies=True` for the bot's own earlier replies), `consolidate`, `manner_feedback`, `persona` (not for a role-play bot, whose character is the persona), `pause` (with `request=`, the person's own words; see [the host AI's pause](#the-host-ais-pause-quotes-the-user)) and `resume` as tools; a bot whose notices should ask for consolidation passes a `tools` mapping with a `consolidate` name, as the AstrBot plugin does. A `Speaker` is a platform, a user ID and an optional group; each maps to its own user brain. With `group_memory="separate"` (default) a person's group messages use a brain per group, apart from their private chats. `session()` is one calendar day of one chat or framework conversation, because bots keep a single conversation for months while recall leaves the current session out.

The AstrBot plugin in `integrations/astrbot/astrbot_plugin_membrain` maps `on_llm_request` to `context` (appended to `req.system_prompt`, which AstrBot does not persist, rather than to the user message, which it does), `on_llm_response` to `record`, and registers `membrain_note`, `membrain_search` (with `my_replies`), `membrain_boundary`, `membrain_consolidate`, `membrain_manner_feedback`, `membrain_persona`, `membrain_pause` and `membrain_resume` with `llm_tool`. Memory is kept in `data/plugin_data/membrain`.

When the embedded database runs as root, as in AstrBot's Docker image, a new cluster is created inside the installation directory if the database's service account can traverse it, so it lives on the same volume as the rest of the data; otherwise, and for clusters that already exist, it stays under `/var/lib/membrain`.


### Server recording control

Host pause/resume tools (plugin CLI and JSON tools, local MCP, Hermes and ChatMemory/AstrBot) now report the effective recording state after changing their existing local control. `recording` is `on`, `paused`, or `unknown`; `local_recording` describes only the requested local mutation. `controls.server` identifies the whole-brain scope, current/cached/unknown availability, revision and last known pause. `controls.local` lists installation, user or active-conversation scopes, including timed expiry. Multiple controls can remain paused: resuming one never resumes the others. These are separately read snapshots, not a cross-store transaction or a promise about an in-flight write.

An offline, stale or unreadable server policy is reported as `unknown`, even when its last known pause still blocks local capture. `capture_blocked` reports that protective gate; it is not proof that recording is off at the server. A known local pause still makes the effective state `paused`, while the server's own state remains unknown. Malformed local metadata also blocks capture but reports an unknown local state. Plugin status/setup uses the same reporting path. Legacy direct `host.pause`/`host.resume` calls keep their local-only result contract; new integrations can use `host_recording.pause`, `host_recording.resume` and `host_recording.control_status`.

These control results do not acknowledge message storage or external delivery. `host.finish_turn` still returns records accepted for storage **or** queued replay; callers must not label that list as server-persisted. The runtime's external `DeliveryReceipt` separately describes sending to a chat destination.

#### Host recording receipts

Pass a dict as `receipt=` to `host.finish_turn` to receive one entry per message of the completed exchange (`host-recording-receipt-v1`, see `membrain.host_receipts`). `ChatMemory.record` returns this receipt; the AstrBot plugin logs a warning when a message is `failed` or `unknown`. Each entry carries `role`, an exact `source` reference (`producer_ref`, `source_event_key`, `source_revision`, or `null` when this call never knew the key), `state` and, unless recorded, a `reason`. Receipts never contain message text. `states` counts entries by state, so a partial exchange stays visible.

| State | Meaning | Reasons |
| --- | --- | --- |
| `recorded` | The service's observation receipt names exactly one accepted or duplicate event (`event_id`, `duplicate`) | — |
| `queued` | Admission to the durable local journal was confirmed; server storage is **unconfirmed**. A request whose answer was lost may already be committed, and another replay worker may drain the journal before the callback returns | `service_unavailable`, `replay_not_observed` (this call's bounded replay did not reach it, or another replay held the journal), `server_outcome_unknown` (an attempt was interrupted after it may have committed) |
| `excluded` | A policy kept it out; `scope` is `brain`, `installation`, `user`, `conversation`, `turn`, `adapter` or `local` (unreadable local metadata). Local controls add `applies_to` (`installation` or `user`); server causes add `evidence` (`current_policy`, `cached_policy`, `unreadable_policy`, `write_rejected`) | `server_paused`, `capture_stale`, `local_pause`, `pause_requested`, `turn_identity_conflict`, `erased`, `group_recording_disabled`, `speaker_unidentified` |
| `failed` | A definite recording or admission failure, with `retryable` saying whether calling again with the same turn can succeed. It does not claim no journal copy ever existed | `queue_full` (journal admission refused; nothing queued, the stage is kept), `queue_write_failed` (the journal write failed and was rolled back; that callback raises, so this reason appears only in a [retained outcome](#looking-up-a-recording-outcome)), `rejected` (`code`; admitted, then permanently refused by the service and set aside; a failed checkpoint write can leave the journal copy until the next replay), `message_unavailable` |
| `unknown` | This call cannot tell | `turn_not_staged`, `turn_ambiguous`, `turn_already_finished`, `turn_mismatch`, `confirmation_missing`, `admission_unconfirmed` (a journal write failed and could not be rolled back, so its records may still be replayed; that callback raises `JournalAdmissionUncertain`, an `OSError`, and the reason appears only in a retained outcome) |

A conversation pause reports `scope: "conversation"` with the owner of its control, including the installation's own memory. A successful answer without one confirmed event ID is `unknown` with `confirmation_missing`; replay still releases that queued copy, as before. A receipt records what this call observed; it is not a live queue-membership query, and a `queued` message may be confirmed by another or later replay without a new receipt. It never reports whether a chat platform delivered the reply. A whole-turn callback (no earlier staging) whose own message asks not to be kept is `excluded` with `pause_requested`, like a staged one. Wrappers of `finish_turn` must forward `receipt`; otherwise `ChatMemory.record` returns `None`. The independent `AgentRuntime` turn and delivery receipts are not merged into this vocabulary.

#### Looking up a recording outcome

A receipt is returned to the caller of `finish_turn` and then gone. The same observation is also kept, so a user or host can ask later whether an exchange reached memory, including after the host, the hook process or the service restarted. Plugin hooks, the OpenAI-compatible proxy, Hermes and `ChatMemory`/AstrBot all record through `finish_turn`, so all of them are covered by one lookup (`membrain.host_outcomes`):

| Path | How an exchange is named | How to look it up |
| --- | --- | --- |
| Plugin hooks (Claude Code, Codex, WorkBuddy/CodeBuddy, OpenClaw) | The host's session ID and turn ID (`prompt_id` / `turn_id`) | `membrain plugin outcome --session <id> --turn <id> [--host codex]`; `membrain plugin outcome` lists the most recent exchanges. Hook output is unchanged; a `failed` or `unknown` message also adds one line of states and reasons to `plugin/hooks.log` |
| OpenAI-compatible proxy | The `X-Membrain-Exchange` response header on each chat completion (the body is unchanged; the header is absent when the adapter records nothing for that speaker) | `GET /v1/membrain/recording-outcomes/{exchange}` with the same token and person (`X-Membrain-User` or `?user=`, plus `X-Membrain-Roleplay` when used); `GET /v1/membrain/recording-outcomes` lists that person's exchanges in the current session (send `X-Membrain-Session` when the chat did). These two paths are answered by the proxy and never forwarded upstream |
| Hermes | The session; turns have no host ID | The `membrain_recording_status` tool, when the user asks whether something was kept, or `MembrainProvider.recording_outcomes()`; `membrain plugin outcome --host hermes --session <id>` for the operator |
| Python hosts | `ChatMemory.exchange(...)`, or session and turn ID | `ChatMemory.outcome(...)` / `recent_outcomes(...)`; `host_outcomes.lookup(...)` / `recent(...)` |

`membrain plugin outcome` also accepts `--exchange <handle>`, `--producer`, `--roleplay` and, for one person of a bot, `--platform/--user/--group` or `--user-id`. It prints JSON and exits 1 when a single lookup is `not_found` or `unavailable`.

A lookup returns `host-recording-outcome-v1` with one `status`:

| Status | Meaning |
| --- | --- |
| `observed` | A completion callback was seen. `messages` has one receipt entry per message (the states and reasons above) plus `observed_at` and `observed_by` (`callback`, a later journal `replay`, or abandoned-turn `recovery`). `completed` is false when the turn is still staged (a refused admission is kept for a retry) or when the callback matched no turn |
| `awaiting_completion` | The message was staged and no completion callback has been seen; `staged_exclusion` names the pause that will keep it out, if any |
| `erased` | The owner's memory was erased through the host; the outcome was removed with it |
| `not_found` | Nothing is retained under this identity for this owner and recording target: never observed here, expired, or another owner's. These cases are deliberately indistinguishable |
| `unavailable` | The local record could not be read (`store_unreadable`, `outcome_unreadable`, or `store_busy` when a writer held the ledger lock for more than two seconds) or was never kept (`outcome_not_retained`: completed before this feature, or the outcome write failed). It is never reported as missing or as success |

What a result means:

- **It is the last observation, not the present state.** `observed_at`, `age_seconds` and `basis: "last_observation"` say when it was seen. `recorded` means the service confirmed storage then; a later deletion or correction made in the service is not reflected, and current recording controls are a separate question (`membrain plugin status`).
- **`queued` is not saved.** Journal admission was confirmed and server storage was not; an answer that was lost may already be committed. When a later replay reaches the record, in any process, including the service's own background replay, the outcome is replaced by what the service answered: `recorded` with its event ID, `excluded` for a policy rejection, `failed`/`rejected`, or `unknown`/`confirmation_missing`. If no replay observes it, the earlier observation stays, with its age.
- **A confirmation is never downgraded**, and a later interrupted attempt only refines a message that was still `queued`. A retried callback keeps what a replay already confirmed.
- **A failed journal write is only called a failure when nothing was left behind.** If the partial append could not be removed, the outcome is `unknown`/`admission_unconfirmed` and the turn stays unfinished; a replay that stores those records turns it into `recorded` while `completed` stays false until the host's retry.
- **Unmatched, repeated and ambiguous callbacks are never a success.** They are kept as `unknown` and listed under `unsettled_callbacks` of the exchange they named, without changing its outcome; a callback that named no turn is listed with `exchange: null`.
- **A lookup only reads local files.** It does not contact the service or the model provider, replay or retry anything, or change a recording control. It says nothing about whether a chat platform delivered the reply.

Outcomes are stored inside the session's existing turn ledger (`plugin/sessions/*.json`), in the entry of the turn they describe, not in a new store. They therefore share its owner-only files (POSIX modes and the Windows ACL of `plugin/`), its lock, and its bounds: the last 256 finished exchanges and 16 unsettled callbacks per session, in session ledgers that are removed 14 days after their last write. A listing without a session reads at most the 32 most recently written ledgers. Nothing is added per message beyond roles, states, reasons, scopes, an event ID, a fixed error code and timestamps: no text, no exception message, no credential. `host.erase_user` removes the erased owner's outcomes with their turns, keeping only the target digest that scopes the `erased` answer, and replay cannot add an outcome to an erased or expired exchange.

Each ledger entry is bound to the owner whose turn it was (the installation's own memory, one user, or one role-play character), its producer, and a recording target: service address, account key, brain and recovery epoch, as the digest already stamped on captures, or computed from the local profile when a capture has none. A lookup returns anything about an entry only for that owner while the profile still resolves to that target. Switching the directory to another account, brain or recovery epoch therefore hides earlier exchanges entirely (`not_found`), including that one was erased or is still awaiting completion, and a replay under the new target leaves them untouched. The proxy derives the owner from the token's namespace and the named person, so a handle guessed by another bot or person finds nothing; the handle is an address, not a credential. Outcomes observed before any installation exists carry no binding, like the rest of `plugin/` at that point.

Limits: a deletion, correction or reset made directly in the service or memory page does not update these local records. Adapter-level exclusions that never reach `finish_turn` (`group_recording_disabled`, `speaker_unidentified`) are returned in the receipt only and are not retained. Records queued outside a host turn (legacy bootstrap imports) have no exchange to attach an outcome to. An outcome written before a crash between the service's answer and the journal checkpoint is replayed idempotently and observed again; one lost to a failed ledger write stays at its previous observation. This is local to one installation directory; it is not cross-device status.

`GET /v1/brains/{brain_id}/recording` returns `{"paused": false, "revision": 0}` for a newly created or upgraded brain. `PUT` accepts exactly `{"paused": true, "expected_revision": 0}`. Read the latest revision before a deliberate change; a stale revision returns HTTP 409 and does not override a newer decision. Changes persist across service restarts. A repeated request after an uncertain response should be reconciled with `GET`, not retried with an automatically refreshed revision. The policy is scoped to the authenticated owner and one brain, until explicitly changed; it has no automatic timeout.

Python: `client.recording_status()` and `client.set_recording(paused=True, expected_revision=state["revision"])`. TypeScript: `client.recordingStatus()` and `client.setRecording({paused: true, expectedRevision: state.revision})`. These require the same authenticated brain access as other memory operations. The memory page's **Pause memory recording** and **Resume memory recording** controls use this server policy for the selected brain, including when opened from a remote service. They submit the displayed revision; conflicts refresh the state without automatically retrying the change. Local conversation pause tools retain their narrower capture scope.

The local page also exposes **Chat capture on this device**, including the existing timed pause. It does not change the server policy, and server resume does not clear a device pause. Other clients may still write while only device capture is paused. `GET /v1/local/recording` returns the effective `recording` value plus `brain_id`, `server: {paused, revision}` and `local: {paused, revision}`, with `local.scope` (`installation` or `conversations`) while paused; by default the server state belongs to the installation's home brain. An authenticated `brain_id` query selects another authorized brain without changing the installation-wide local scope. These are two separately read states, not one cross-store transaction. User-specific conversation controls still apply separately.

`POST /v1/local/recording` changes device capture only and returns the same combined state for the home brain. It accepts `paused`, optional numeric `hours` when pausing, and optional `expected_revision` from the **local** state (an opaque string, not the server's integer revision). The page always supplies that revision. A stale token returns 409 without changing either control; omission remains supported for legacy callers and provides no compare-and-set guarantee. Every new local pause carries a fresh nonce, and expiry cleanup shares the state lock with pause/resume so an expired snapshot cannot erase a newer pause. If the final server-state read fails, the local change may already have succeeded: read the state before another deliberate change rather than blindly reversing it. No local command automatically resumes the server.

The page shows unavailable status and hides mutation controls when state cannot be confirmed. Responses arriving after a newer status read cannot overwrite it. Corrupt local control metadata is reported as unavailable rather than displayed as recording on; the host also keeps capture paused when a pause file is unreadable, malformed or has an invalid expiry. Only a missing file means no local pause. Inspect a damaged control file before explicitly clearing its device pause with `membrain plugin resume`; that command cannot resume the server. The page refreshes periodically and before showing its privacy view; it is a snapshot, not a real-time subscription. A disconnected device still cannot discover a remote pause immediately.

The policy change and source ingestion serialize on the same PostgreSQL brain lock. A write already holding that lock completes before pause is acknowledged; a write obtaining it while paused is rejected with non-retryable `recording_paused`. This covers observations, notes, event-backed companion changes and archive upload/restore. Unfinished runtime turns an older runtime left are closed and release their scope reservations; a turn whose generation or delivery was in progress is marked uncertain, not cancelled, and resume does not revive them. Source history written before the pause remains. Reading, exporting and core memory erasure remain available, and processing of existing memories is not a global shutdown.

Background cognitive learning also obeyed this policy until it was removed (see [what the removed learning left behind](#what-the-removed-learning-left-behind)); the learning jobs an older runtime left are never claimed, paused or not.

Hosts read the server policy before staging input and retain its revision through the reply and offline queue. A known server pause also excludes new local staging while disconnected; local resume cannot override it. A fresh authenticated read is needed to observe server resume. Policy caches are isolated by user/role-play and cannot regress on an out-of-order response. Capture metadata binds known targets to their brain, endpoint, credential and recovery epoch; changing that binding discards old queued content rather than delivering it to a different target.

An observation can supply `expected_recording_revision` (Python: the same keyword; TypeScript: `expectedRecordingRevision`). The server compares it under the existing ingestion lock, rejecting a mismatch as non-retryable `recording_stale`, even after pause followed by resume. Replay must preserve the capture revision; fetching a fresh revision for an old record defeats the fence. Hosts drop policy-rejected records and their matching local prompt cues without a spool or rejected-record copy. Legacy unversioned host records use revision zero and are accepted only before the server policy has changed. Direct SDK/API calls may omit the optional field for an intentional write under the current policy; the fence is not a permanent tombstone against deliberate resubmission.

**What erasure removes, and what it cannot reach.** `forget` with `erase_content` (by event, memory, conversation or the whole scope; a reply goes with the message it answered, a note or feeling with the message it came from) leaves nothing in the memory database from which the erased text could be read or a guess of it confirmed. It removes the message's text and the rows derived from it (claims and their vectors and passages, cues, notes, feelings, traces, working state, cached responses), rewrites the archives the server holds without it, and replaces every digest of it with 64 zeros, a value no real digest takes: the event row's `content_hash` and `input_hash` (both NOT NULL), the digests older runtimes kept on turn rows, feedback contributions and model-call reservations, and a source key that a host derived from the text when it had no turn id (it is replaced by one naming only the event). Every stored observation request of the brain is removed and every other request fingerprint wiped, because a fingerprint covers the request's text beside values that can be read next to it, and which stored request carried the erased text cannot be told: an observation sent again is matched by its events (one still recorded is a duplicate), any other request sent again is answered as one whose response has expired. A copy of the erased message sent again is refused with `recording_stale` and stores nothing; hosts drop their queued copy without reporting a failure.

Host-owned copies are reconciled after an authenticated contact, using POST /v1/brains/{brain_id}/recording/erasures (Python recording_erasures, at most 128 identities per request). The response confirms erased event IDs or retained source identities; a missing source is not proof of deletion. On the next hook/tool connection or policy read, the shared host path removes confirmed copies from the pending and rejected journals, their prompt tails, turn fingerprints, note-capture nonces and outcomes. It also invalidates the owner's disposable context fingerprint. A content-free marker prevents a concurrent journal admission from restoring a confirmed, stable source identity. Other users, recording targets and unrelated pending messages are preserved. Changes made through the memory page or a remote API therefore have a local cleanup window until the host next connects; unavailable or older services cannot confirm cleanup. The reconciliation checkpoint advances only after the rewrites succeed, so a failed cleanup is retried on a later contact.

There is a legacy identity limit: a source key derived from message text is itself erased by the server. A retained event receipt still identifies it; without one, the host cannot distinguish an erased copy from an unrelated, never-sent message. Such a queued copy remains subject to the existing stale-capture rejection on replay, which removes its text and prompt fingerprint without archiving a refused copy. Unresolvable historical rejected copies require explicit whole-user cleanup. This is not a claim that all old local files are immediately erased. Whole-user erasure also removes prompt fingerprints. Retired desktop sessions/*/pending.json and recovery-sessions.jsonl input fingerprints are conservatively redacted for the authenticated profile after an erasure is observed; their non-content recovery metadata remains.

The shared journal and session cleanup covers Claude/Codex/OpenClaw CLI hooks, ChatMemory/AstrBot and Hermes through host.ready_client and the recording-policy path. Hermes's import marker contains a file path, modification time and size, not imported text. Adapter configuration and hooks' exception-type diagnostics are not message stores. This does not erase a host's own transcripts, USER.md, provider history or files another program keeps. Installation backups and exported archives made before erasure also retain their original bytes until separately deleted; restore/import reapplies the erasure inside memory. suppress_recall hides a message and keeps its content; it does not trigger source-copy erasure.

An identical stored observation whose response cache was invalidated by an unrelated edit is checked again against its source events and current recording fence, then acknowledged as duplicate without adding an event or learning work. A different payload under the same idempotency key, or different content under the same source revision, remains a conflict. An erased or stale capture remains excluded.

Every successful core `forget` operation now advances the brain's recording revision in the same transaction as deletion, without changing its paused state. This applies to both erasure and suppression, including empty resolved selections. The invalidation is deliberately brain-wide even for a selective deletion: old host captures, queued observations, manual notes and claimed cognitive tasks cannot use the prior revision to write after the deletion. A completed deletion retry does not advance it twice. New input obtains the current revision; an old request must not substitute that revision and call itself a retry. Other brains retain their own authority.

Internal note replacement suppresses superseded notes without revoking capture permission for the rest of that turn. Its independent recovery intent retains this distinction, so replay still suppresses the old note without becoming a new recording-policy change. Explicit user erasure or suppression always revokes earlier captures, including a retried note write whose current message survives a selective deletion. A fresh turn obtains new authority.

Durable runtime turns bind their recording revision at `begin`, and generated input/output plus orientation work retain it. Migration 033 gives pre-existing turns revision zero rather than guessing a newer authorization. A legacy turn can therefore become stale after an earlier policy change; new turns bind the current revision. A changed permission prevents further model reservations, renewal of pre-delivery work and new content writes. A delivery callback already in flight may still return a receipt: the service records bounded delivery metadata and a content hash, with `recording_changed` and `content_withheld`, rather than persisting returned text or falsely saying it was never sent. Confirmed delivery remains a fact. Upgrade the Python runtime and service together for the additional turn field and receipt reason.

New independent deletion-log intents persist a minimum recording revision. Reconciliation after restoring an older database applies at least that revision, so restoring an old counter cannot revive a capture from before that deletion. Intent/receipt replay is idempotent. Historical intents without this field remain readable and advance the restored counter, but their missing historical revision cannot be reconstructed. No claim is made that an arbitrary unmanaged database rollback preserves authorization, or that these controls erase external transcripts. Direct writes that intentionally omit capture metadata retain the separate current-policy contract described above.

A disconnected host cannot learn a remote change immediately: input may still be buffered under its last known unpaused policy, but will be rejected on replay if the revision changed. Server control does not remotely erase disconnected files, synchronize local conversation/timed switches back to the server, or erase host/provider transcripts. Whole-turn-only hosts check policy when the completed turn is supplied; they cannot reconstruct a policy change that occurred before that capture. The capture revision fence covers observations and lifecycle-integrated manual note tools. Tools-only MCP and direct custom clients remain caller-managed operations without an original host-turn guarantee. No historical erasure, atomic user/reply pair or crash-atomic ledger-to-delivery guarantee is implied. The following conversation-level controls retain their existing scope.

### Manual tools and original-turn recording permission

A staged public turn supplies `recording_capture` in its `<membrain-source>` block. Plugin `note`, plugin MCP `memory_note`/`memory_observe`, Hermes `membrain_note`, `ChatMemory.note` and AstrBot/OpenClaw note tools require this value for every write, including unsourced notes and replacements. Hosts pass it unchanged from the originating model request; they must not look up a newer turn when executing a delayed call. Missing, malformed, revoked or expired captures produce a recording error. Old pending turns created before this upgrade do not have a capture and cannot gain one by replaying their prompt hook.

The opaque capture contains a session-marker identifier, turn identifier and random nonce. Its local marker binds the memory owner and original server recording target/revision. It is not stored as note content, does not contain the API credential, and does not require another policy HTTP request. A local pause revokes affected owners' captures, including completed turns and their role-plays; resuming never reissues those captures. Another user's captures remain valid. Local user erasure also revokes that owner's unfinished and completed captures; a later public turn can obtain a fresh one. This does not cancel a request that already passed its local capture check. Completed captures are retained only within the existing 256-marker/14-day session bounds; eviction fails closed. Server revision checks run inside the existing write transaction, so a policy change after capture prevents stale note insertion and replacement. The same-turn local resume may still enable the documented raw-message finish path, but note tools wait for a later staged public turn with a new capture.

`membrain plugin mcp` enables this requirement. The standalone `membrain desktop mcp` configuration remains explicitly `tools_only`: it has no prompt hook and continues accepting intentional manual writes under current recording controls. `memory_capabilities` reports `recording_capture_required`. When a tools-only local caller does supply a capture, it is checked; a remote MCP connection without local host state refuses a supplied capture rather than silently ignoring it. Direct SDK/API writes remain separately authenticated operations. Switching to that interface or replacing a rejected capture is not an authorized retry of an old host turn.

This is an operation-lifetime fence, not proof that a model copied the correct turn's text or a replacement for host authentication. A call that passed the local file check before a local-only pause can already be in flight; local controls and remote note transactions are not atomic. The server control serializes with ingestion, but local conversation/timed pauses still are not synchronized to it. Hermes file-import/mirroring callbacks and other non-tool integrations are separate paths. Existing history, search, export and erasure retain their controls. No model-memory-quality or response-speed improvement is established by this change.

### Chat adapter identity compatibility

`ChatMemory` preserves existing brain identifiers when platform, user and group components fit their original limits (40, 80 and 60 characters) and contain none of `:`, `%` or `|`. Other identifiers use a versioned SHA-256 digest of the structured platform/user/group tuple. Sessions also use structured identities, including group and conversation, so reused conversation IDs cannot merge separate groups' pending turns.

Ambiguous or shortened legacy identifiers start with separate memory after upgrading. Old brains are retained but are not automatically copied: a legacy brain may already contain more than one person's data. Inspect affected legacy brains and establish ownership before manually migrating or deleting their contents. This upgrade does not repair historical mixing. Restart bot adapter processes to apply the new identity and cache rules; existing stored history remains available in unchanged brains.

Pausing clears that user's unfinished staged prompts and recall cues, including role-play sessions, and paused turns stay excluded even if recording resumes before the reply arrives. Already committed records and records queued before the pause are retained. Turning off real-life sharing immediately changes the next role-play context instead of waiting for the session cache to expire.

The shared host lifecycle also recognizes a bounded set of direct opening controls before staging a user message: for example `Off the record: ...`, `Don't remember this: ...`, `Pause recording. ...`, and `请不要记录这一段：...`. The full first clause must match; quoted examples, reported speech, and requests merely to keep an existing memory confidential do not trigger it. This is deterministic English/Chinese command recognition, not general privacy-intent understanding. For other wording or languages, use the pause tool or memory controls before sending private content.

A recognized control uses the existing conversation pause: the current exchange and following turns are excluded, including raw staging and offline spooling. The originating session is included even when the first callback is `finish_turn`. The pause belongs to the conversations in progress when it was set: a conversation that starts later is recorded as usual, is told that another conversation is off the record, and does not end the pause, which lasts until those conversations are over or recording is resumed. A memory write that carries a turn's `recording_capture` is checked against that turn's conversation; a write that names no conversation is refused while any conversation pause is in effect. An existing timed or until-resumed pause is never shortened. An explicit exclusion cannot be revived by a resume tool in that same turn. Resuming through the controls can enable later turns; the finish callback does not repeat a pause already handled during staging. No natural-language resume is inferred. Local MCP `memory_observe` and `memory_note` refuse new content while paused.

These controls belong to `host.prompt_context` / `finish_turn` and their plugin, bot and proxy adapters. They are not a server-wide recording policy for raw HTTP/SDK `observe`. The chat host and upstream reply provider still receive the message needed to answer; memBrain cannot erase their transcripts. Previously stored content is not retroactively deleted. See the [backend control-flow review](../architecture/backend-control-flow-2026-11-07.md).

`finish_turn` matches owner, producer and turn ID before taking an input. Shared hosts must pass the owner on every call. Stable turn IDs support overlapping requests and replies in either order. Without a turn ID, a supplied prompt must match exactly after privacy scrubbing; a callback with neither is accepted only for a single input that has not overlapped another input in the same owner/producer scope. Ambiguous callbacks and mismatched prompts are discarded without consuming another turn. Replies retain their matched input's exact parent key, including colons in host IDs. New turn IDs containing colons use an encoded source-key namespace so different session/turn pairs cannot concatenate to the same source key. Ordinary IDs keep their existing keys; legacy staged keys retain their existing links during completion. Historical records are not rekeyed.

A session keeps at most 64 active turns and 256 completed, content-free turn markers. Capacity overflow raises a recording error without evicting active inputs. Unknown finish callbacks in staged sessions are rejected even after completed markers are compacted. Finish-only sessions must supply the actual prompt. Hosts mixing staged and whole-turn reporting, such as Hermes, explicitly use `allow_unstaged=True`; this never consumes another live input. Once a session has excluded or erased content, unknown whole-turn callbacks are refused even with that option: later turns must be staged, or use a new session. This prevents compaction from reviving excluded messages. Session metadata retains the existing 14-day inactive-session expiry; it is not a permanent deduplication ledger. Hosts without stable IDs cannot reliably distinguish identical overlapping prompts.

A resume tool cannot choose between multiple active turns for the same user. It resumes future recording but reports `current_turn_resumed: false` when multiple active turns make selection ambiguous. The proxy hashes supplied `X-Membrain-Session` values together with the effective user, group and role-play identity; authentication namespaces are already part of that user. Existing raw-header session IDs are not reused after upgrading; earlier stored memories remain in the same brain.

### Role-play and real life

`host.session_context`, `prompt_context` and `finish_turn` take `roleplay=<character>`; `ChatMemory` takes it per call or as the bot's own character. A role-play's memory is a separate brain for each person and character (`host.roleplay_user`), and its records are marked with the core's `roleplay` interpretation, so story facts never reach the real-life context and the person's real-life notes never reach the story. With `share_real_life` the person's real-life notes are shown in a separate `<membrain-real-life-notes>` block, without notes marked sensitive. A person's recording pause also covers their role-plays. The proxy reads `X-Membrain-Roleplay` and `X-Membrain-Share-Real-Life`; the AstrBot plugin has `roleplay_character` and `share_real_life` settings.

### OpenAI-compatible proxy

`membrain proxy --upstream URL [--host 127.0.0.1] [--port 8790] [--directory DIR] [--group-memory separate|shared]` (`membrain.proxy`) serves `ChatMemory` without tools. `POST /v1/chat/completions` (also without the `/v1` prefix) gets one system message with the person's memory inserted just before the latest user message; the reply, streamed or not, is stored with the message; other paths and malformed bodies are forwarded unchanged. The person is `X-Membrain-User` or the body's `user`, with optional `X-Membrain-Platform` (default `api`), `X-Membrain-Group` and `X-Membrain-Session`; anonymous requests share the user `default`. Without `MEMBRAIN_PROXY_TOKEN` the client's `Authorization` header is forwarded and only loopback addresses are allowed; with it, clients must present the token and `MEMBRAIN_UPSTREAM_KEY` is sent upstream instead. With no tools, the memory notice tells the model only that memory is active and that `<private>` text is not stored.

The proxy writes no notes: the bot's model has no note tool behind it, and memBrain calls no model of its own. The separate note-extraction model that earlier versions offered (`MEMBRAIN_EXTRACT_MODEL`, `MEMBRAIN_EXTRACT_KEY`, `MEMBRAIN_EXTRACT_BASE_URL`; the AstrBot settings `extract_model`, `extract_base_url`, `extract_key`; `ChatMemory(extractor=...)`) has been removed. These settings are ignored without an error: a proxy environment that still sets them starts as usual, a saved AstrBot configuration that still holds them loads as usual, and `ChatMemory` accepts `extractor` and never uses it. Notes it saved earlier are ordinary notes and stay linked to their source messages. The `plugin/extraction.json` status file it kept is left on disk and no longer read: `membrain plugin status`, `membrain doctor` and `/v1/local/memory-status` no longer report `note_extraction`.

### MCP

MCP uses stdio through the official Python SDK 1.x, with its version pinned by `uv.lock`. Desktop installations should use the secret-free configuration generated by `membrain desktop mcp-config`. The following is a manual client configuration for development deployments:

```json
{
  "mcpServers": {
    "membrain": {
      "command": "uv",
      "args": ["run", "--directory", "/absolute/path/to/membrain", "membrain", "mcp"],
      "env": {
        "MEMORY_BASE_URL": "http://127.0.0.1:8787",
        "MEMORY_API_KEY": "<your local access token>",
        "MEMORY_BRAIN_ID": "<your brain ID>"
      }
    }
  }
}
```

MCP lets a model explicitly recall memories and submit notes with source labels. It does not intercept host turns, automatically read the host's full conversation, determine delivery, or take over compaction. Configuring a server-side cognition model does not change this boundary. Notes submitted through MCP are always marked as assistant-sourced and cannot impersonate user statements. Fully automatic capture and pre-answer recall require the host to integrate lifecycle interfaces.

## Current implementation boundaries

| Area | Current implementation |
| --- | --- |
| Persistence | PostgreSQL source events, source revisions, idempotent submission, and transactional job enqueueing |
| Working state | Branch state, revision checks, and compaction handoff |
| Recall | Multi-route candidate fusion (keywords, the local embedding model, message cues, episode structure), applicability conditions, source rechecks, persistent plans, and budgets |
| Consolidation | Literal capture; notes and message cues written by the host's AI. Semantic claims, episodes and beliefs that the removed learning stored are still read and erased |
| Belief change | Stored conditional exceptions, supersession, equivalence, and contradiction govern recall; nothing writes new ones |
| Access dynamics | Representation- and time-dependent access tiers; trusted external feedback updates use counts and usefulness assessments |
| Correction and deletion | Version updates, synchronous invalidation, derived-dependency cleanup, and deletion-record checks during archive restoration |
| Isolation | Server-bound identity, application query filtering, and forced PostgreSQL row-level security |
| Integration | Host plugins and adapters with automatic capture and recall; low-level HTTP, Python, TypeScript, and MCP operations |
| Desktop operation | Stable local profile, brain, and credentials; automatic database/API/worker startup; automatic MCP and SDK connections; data retained on shutdown |
| Development aids | Authenticated status, background jobs, recall stop reasons and budgets, and a removable local workbench |

Condition-triggered proactive reminders, context for judging a memory's conditions, calibrated decay and association propagation, multimodal understanding, complete tool loops and streaming host adapters, cloud accounts, and shared permissions still need implementation and validation. Procedural candidates are only sourced steps and conditions; they do not execute themselves or prove task success. Only owner-private scope is currently supported; shared-collection requests are explicitly rejected. Without configured semantic embeddings, existing lexical feature hashes are not treated as semantic vectors. With embeddings configured, vectors are used only when model, version, dimensions, and content hash match.

A source-backed original statement does not establish independent verification of its claims about the world. Default recall returns supported candidates and uses `partial` to indicate that semantic sufficiency has not been assessed. Semantic judgments by the host's AI (notes and message cues) can still be wrong, and multi-route search cannot guarantee complete retrieval of relevant history. Quoting a substring from an original source does not establish that it can stand alone as a new conclusion.

A [10,000-record synthetic retrieval diagnostic](../evaluations/retrieval-scale-2026-10-25.md) improved the same 20 labeled-cue queries from 18/20 to 20/20 hits after the candidate and scope-projection changes. Measured median recall time changed from 487.009 ms to 92.3195 ms and p95 from 503.284 ms to 123.173 ms. These are local in-process measurements without HTTP or model latency; the repaired replay reused a warm fixture, and concurrent host load was uncontrolled. The report preserves exact data, the excluded invalid-boundary attempt, and the limits of this comparison.

Only direct statements that preserve original meaning and source attribution can enter `grounded` working state. The generic submission interface for unresolved items currently accepts only `unknown` status. A cited note cannot simply declare an item completed.

Archive import/export is separate from the implemented desktop logical backup and fresh-install recovery. The latter uses an independent current deletion authority, operational quarantine, and explicit activation, with real Docker and installed-package checks. Physical database backups, migration at scale, operational SLAs, and long-term conversation quality require separate deployment and testing. Stopping and restarting the service does not delete committed records.

An archive is currently limited to 16 MB and 5,000 records of each type. Exceeding either limit produces an explicit error, not a silently truncated backup. Sharded export and large-scale restoration remain unimplemented.

A restored event keeps two recording times. `system_time.recorded_at` is when this copy was ingested by the restore. `system_time.restored_from_recorded_at` is when the server first recorded the original: the earliest time across repeated restores, never later than the restore itself. It is a recording time, never an occurrence time; `occurred_time` stays as the host reported it, and the restore writes no extra event. Familiarity counts a restored message without a reported time on its original recording day, so a restore does not fold several days of conversation into one.

Compatibility: archives from runtimes without this field restore as before. An archive exported after restoring carries the field, and a runtime that does not know it rejects that archive as invalid, because the contract does not allow unknown fields. Upgrade the runtime before restoring a newer archive; restoring onto an older runtime is not supported.

### Memory workflow and diagnostics

`membrain plugin setup [--no-browser] [--directory PATH]` starts the local installation and opens its single-use memory page with first-use guidance. No cognition provider is required. The page counts visible recorded user/assistant messages outside the notes conversation, without exposing their contents in status responses. Receiving messages confirms capture, not answer accuracy; users are guided to test a preference in a new session. `POST /v1/local/semantic-model` requires the local credential and retries the pinned local model download or activation in the background. Failed downloads remain visible; a model on disk is not reported enabled until the service has activated it.

Saved-note context is fingerprinted per session and brain. Before replies, changed notes, coming-up dates and explicitly shared non-sensitive real-life notes are rendered within a fixed budget. Updates replace earlier saved-note blocks; failed reads do not publish an empty snapshot. The state file stores the fingerprint and rendering options, not a copy of note text. This does not retract memory already delivered to a host, and does not establish real-model correction compliance. Complete user history does not skip deliberate recall of the assistant's earlier speech.

`membrain doctor [--directory PATH]` checks the installation without starting services or downloading models. Its JSON report lists Python/uv, service and database availability, semantic recall, queued records, disk space and index progress, with a concrete recovery command for each problem. Exit status 1 means an error needs attention; a missing semantic model is a warning because keyword recall remains available. While a start or stop holds the installation's lifecycle lock (the first start prepares its database before the service runs), the service is reported as `starting_or_stopping`, a warning, instead of an error; a port held by another program is named in the fix. During that preparation the doctor itself waits for the profile lock, up to 30 seconds.

The memory page provides People and Plans views of the notes, each with its kind, dates, plan status and tags, the original messages it came from, and Delete. Since 2026-11-18 the page has no text entry for memory content: the user tells their agent to add or correct a note, and the agent saves it with the note tool (`replaces` for a correction, `source_messages` or `source_event_ids` for its source). The note editor, "Merge duplicate", "Save as note" in Conversations and the editor on the brain map are gone. The original bracketed storage format stays compatible. The timeline uses a sequence cursor to load older messages without duplicates while new messages arrive. Readiness distinguishes a functioning keyword index, a downloading or installed semantic model, unfinished indexing and queued or failed background work.

`POST /v1/brains/{brain_id}/notes` accepts `request_id`, `text`, typed-note fields, `role` (`user` or `assistant`), `replaces`, and optional `source_event_ids` or `source_messages`. A source-message reference contains `producer_ref`, `source_event_key` and `source_revision`. Host prompt hooks expose the current message's exact reference in `<membrain-source>`; it can be attached before the turn finishes. The event contract's optional `source_references` field persists these references. Links resolve within the same brain when the original message is recorded, without guessing from timing. Until then the page says the source is waiting; older unlinked notes explicitly say no original message is linked. An ordinary note may wait only while its source identity has not been recorded. If that producer/key is known, the cited revision must be its current eligible original message; otherwise the write fails with `source_unavailable`, without replacing an existing note or saving a feeling. This also refuses speculative future revisions of an already recorded source. If a pending source arrives as a different revision, a draft, a cancelled message or a non-original record, the interpretation and its dependent records are retired and no longer recalled or counted as shared moments. A later version cannot revive them; the host must write a new interpretation. The dependency remains for content erasure, including after archive restore. Source arrival also binds already hidden or replaced interpretations for erasure, without making them visible again. Independent notes keep their own sources. This does not reconstruct identities removed by legacy content-digest erasure; delayed writers must still preserve `expected_recording_revision`. Existing unmatched legacy notes are not retroactively scanned by this write/arrival check. Arrival lookup includes retained note history so hidden bodies keep their deletion dependencies; this JSON-reference lookup can scan the brain's retained events under the application role and has no new scaling guarantee.

`POST /v1/brains/{brain_id}/source-messages` accepts `messages` (1–64 exact source-message references) and returns surviving original messages plus the brain's `dependency_generation`, `recording_revision` and `recording_paused` from the same transaction. Reads require the same authentication and ownership as notes; deleted, suppressed, retired, superseded, draft, cancelled and reserved note/affect records are absent. Pausing recording does not block inspection of existing sources. Python exposes `source_messages`; TypeScript exposes `sourceMessages`.

`POST /v1/brains/{brain_id}/message-cues` attaches retrieval cues to stored messages. A cue is a short phrase naming whom a message is about and what kind of fact it holds ("Melanie hobbies and activities"), in the words a later question would use; it lets recall reach a message whose own wording the question does not share. The body has `items` (1–200), each naming one message by `event_id`, or by `producer_ref` and `source_event_key`, with `cues` (at most six phrases, each cut to 80 characters after secrets are scrubbed), and an optional `model_version` recording what produced them. The response counts `written`, `skipped` (messages that are unknown, superseded, hidden or erased, and items whose cues came back empty) and `embedded`. Writing cues for a message replaces the ones it had; an empty list removes them. Cues are refused while server recording is paused. They are an index, not memory content: recall returns the original message with an `entity` rank signal, never the cue; cues are not exported, and they are deleted with the message when it is hidden, erased or corrected. The local embedding model embeds cues when they are written; without it, cues are matched by their words only. memBrain calls no model to write cues: the host's own AI writes them. `GET /v1/brains/{brain_id}/message-cues/pending` (`limit` 1–100, `max_characters`, and `whole_conversations` to end the batch where a conversation ends when at least ten messages remain in it) returns the user's messages not yet reviewed for cues, oldest first, each with its `sequence`, plus `through_sequence` and `remaining`; nothing is offered while recording is paused. The write accepts `sequence` to name a message and `reviewed_through_sequence` to record how far the messages were read, with or without cues, so they are not offered again; with it `items` may be empty. In hosts with the MCP tools, a new session is told in one sentence once five messages await indexing: once in the conversation, before writing its reply to the user's first message, the AI calls the tool without arguments, does what it returns and then writes its reply. Its last answer asks for the reply once and, when the AI had already written it before the call, not to write it again ("Done. Now write your reply to the user's message, once. If you already wrote it before calling this tool, do not write it again: end your turn with no more than a word and call no other tool. Do not describe the indexing beyond a few words."). The order was "answer first, then index" until the seventh maturity attempt, where in a tool-calling host the text written before the tool calls and the text written after them showed the user two answers in 11 of 124 turns ([record](../evaluations/maturity-seventh-attempt-2026-11-16.md#what-the-run-showed-about-the-product)). `memory_consolidate` without arguments hands the AI a batch of at most 40 messages (8,000 characters), ending with a conversation where it can, with instructions, and its second call, with `cues`, saves them and counts the batch as read (`reviewed_through` is only for callers that keep no connection between the two calls). OpenClaw and AstrBot have the same tool as `membrain_consolidate`, and their sessions are told the same way. OpenClaw runs `membrain plugin tool consolidate`, a new process per call that cannot remember the batch, so its first call also returns the batch's `reviewed_through` and its second call must pass it back; ids beyond it are refused. AstrBot's `ChatMemory.consolidate` remembers the batch handed out last in each person's session, as the MCP tool does, until the bot restarts. The proxy has no tools and does not write cues. Python also exposes `pending_message_cues`; TypeScript exposes `pendingMessageCues`. Python exposes `write_message_cues`; TypeScript exposes `writeMessageCues`.

Note writes accept optional `expected_recording_revision` (Python `save_note`/`write_note`, TypeScript `writeNote` option `expectedRecordingRevision`). The service rejects a new write with `recording_paused` or `recording_stale` under the same transaction lock used by policy changes, before any replacement, affect record or request payload is stored. An identical retry of an already committed note may return its original acknowledgement without writing again; changing its revision while reusing the request ID is an idempotency conflict. Guarded writes cannot fall back to an older client's unguarded observe path. A caller that writes later on behalf of an earlier turn keeps that turn's captured revision and never replaces it with the current one; direct tools that omit the capture revision do not gain a historical-task fence merely by using the note endpoint. Local conversation/timed pause still has a separate control contract; background cognitive learning follows the server policy described above.

A caller that reads its sources before writing a note (with `source-messages`) can guard the write against changes in between. `require_current_sources=true` with `expected_dependency_generation` from the read makes the transaction reject unavailable exact revisions or intervening dependency changes before replacing any note. `context_source_messages` adds dependencies on earlier context to the note while keeping its feeling attributed to the current exchange. At most 64 current and context references combined are accepted. Ordinary note writes retain support for references whose messages have not arrived yet. These guards prevent stale persistence; they cannot retract text the caller already sent elsewhere. A write retried with the same note `request_id` and unchanged generation replays the committed result without duplicating a note or feeling. Python `save_note` accepts an optional `request_id`; clients without idempotent note writes reject that option before observing anything. `require_current_sources` and `context_source_messages` were added for the removed note-extraction model; no shipped host sets them now, and the service and SDKs keep them for callers that write notes later from reread sources.

A note can carry one feeling the user expressed, as `affect`: `label` (the user's own word, at most 40 characters), `valence` (-2 to 2), `intensity` (0 to 3), `basis` (`reported` when the user said it, `inferred` when it was read from their words, which requires `source_event_ids` or `source_messages`), optional `topic` (at most 80 characters) and `felt_at` (`YYYY-MM-DD`, default today). Each reading is an affect record: a `system`-role event in the reserved `membrain-affect` conversation, stored apart from the note and dependent on it and on the messages it was read from, so correcting or deleting the note or the message removes the record through the same audited deletion. Records are never recalled, shown as history or counted as messages. The notes block shows a record on its note's line, "(the user said they felt nervous, 12 Mar)" or "(seemed nervous, inferred, 12 Mar)", within its own 800-character allowance; the notes are chosen before feelings are added, so a feeling never changes which notes are shown or their order. There is no overall score. `GET /v1/brains/{brain_id}/affect` lists the records with their evidence and the reset markers; `POST /v1/brains/{brain_id}/affect/reset` ("Clear feelings") erases every record and writes a reset marker with its time and `applies_from_sequence`. A feeling whose source message was recorded before the latest marker is refused (the note is still saved), so a reset cannot be recomputed from older conversations. Erasing all memory removes the markers too. Python exposes `affect_records` and `clear_affect`.

**Stored memory structure.** `GET /v1/brains/{brain_id}/memory-map?structure=true` and Python `client.memory_map(structure=True)` opt into `memory-structure-v1`; the original API shape remains the default for existing clients. The memory page opts in. Alongside notes, original messages and attached feelings, this bounded projection includes current assertions and directly referenced versions, explicit evidence and derivation edges, current consolidated episodes with exact member revisions, cross-episode pattern inputs, stored association kinds and belief relations. An assertion ID contains its record ID and revision, so revisions cannot silently merge. Association and belief edge `basis` preserves the recorded relationship kind. `details` includes bounded assertion text, representation, lifecycle, evidence status and stored dynamics, without claiming a biological measurement. Sensitive source classification is resolved against surviving sensitive notes before bounding source nodes; dependent content is masked unless explicitly opted in. All reads use one transaction and the brain lock, with the existing timeout, ownership, erasure and invalidation rules. Graph reads do not learn, reinforce or schedule processing. The maximum remains 500 nodes/1,000 edges; `truncated`, sample region counts and coverage limits must be preserved by consumers. Companion development remains a separate graph. Persisted working-state revisions now appear with their stored items and open loops, scoped to their conversation branches. Membership edges represent the stored arrays; evidence edges require a current, visible source with the exact revision, content hash and valid span. Unknown values do not acquire invented evidence, expired items remain labelled expired, and passing a due date never establishes completion. Empty default state that has not been saved is absent. Sensitive evidence masks both the item and its containing state before visible-node bounds are applied. The working-state sample uses the most recently updated branches, up to max(1, max_nodes // 8); documents over 64 KiB are omitted with truncation flagged, and text previews are limited to 2,048 characters. Evidence loading is bounded to at most 1,024 current records; items whose full evidence cannot be checked are omitted. 3D positions derive from the displayed topology and are illustrative; travelling signals remain simulated.

**Companion graph for visualization.** `GET /v1/brains/{brain_id}/companion-map` and Python `client.companion_map()` expose a read-only, authenticated graph (`contract_version: companion-map-v1`). The default window is 200 nodes/400 edges, with hard limits of 500/1,000; `include_sensitive=false` masks sensitive notes and their source messages, including feedback/affect/trigger details that could repeat the hidden evidence. Both graph endpoints also mask another note and its feeling when they share an original source with a current sensitive note, even when that sensitive note is outside the display window. An explicit sensitive opt-in is only for authorized local inspection. The response has `nodes`, `edges`, sample `regions`, `limits`, `truncated`, `coverage` and `limitations`. Each companion node has a stable typed `id`, `kind`, `region`, bounded `label`, `recorded_at`, `sensitive`, `masked` and `details`. A masked node has `recorded_at: null`; notes, source messages, feelings and learned-memory structure nodes follow the same recording-time masking rule. Explicit sensitive opt-in preserves original timestamps where those records provide one. A revealed sensitive node remains labelled sensitive; `masked` says whether its text/details were withheld in this response. IDs refer to software records, not biological or model neurons. Regions `persona`, `mood` and `relationship` supplement the existing memory-map regions.

The companion response includes `familiarity`, a rule-derived summary separate from its stored nodes. It uses all valid, visible user-conversation days and shared moments after the latest reset; nothing caps it (the user's familiarity cap was removed on 2026-11-18). Shared-moment counts are calculated before display sampling; the relationship API exposes `shared_moments_total` and `shared_moments_truncated` alongside the latest 500 displayed moments. Ordinary milestones cannot displace older shared moments from the count. The graph summary includes bounded `evidence.shared_moment_nodes` and `reset_node` references only when those records are present in the returned graph. The reset node corresponds to its actual stored marker; no familiarity neuron or synthetic dependency edge is added. When any contributing conversation day or shared moment has known sensitive evidence, the default summary contains only `{derived: true, masked: true}`; this includes evidence outside the displayed sample. Authorized `include_sensitive=true` reveals the derived summary. The English/Chinese brain sidebar labels this as a calculation, not affection; fullscreen remains the record graph.

**Persona card (Phase C, P1).** `GET` and `PUT /v1/brains/{brain_id}/persona`, `GET /v1/brains/{brain_id}/persona/versions`, `POST .../persona/restore` (`version`), `POST .../persona/reset` and `DELETE .../persona/versions` manage the companion's persona card: `name`, up to 8 `traits`, `voice` (`register`, `length`, `emoji`, `language`), `values`, `boundaries` and an optional `baseline_mood` (`label`, `valence` -2..2, `energy` 0..3). Each save is a new version; restore and reset save a new version too, so history is kept. Saving the current card again changes nothing (`unchanged`). Reset picks the persona again: a named personality type, else the newest card the host saved with `host_default: true`, else a random other type (see personality types below). Cards are scrubbed like notes; one whose rendered text exceeds 1,200 characters is refused with 422 and never truncated. Versions are events in the reserved `membrain-persona` conversation with the `system` role, so they are never extracted into recalled memories, never shown as history or messages, and are covered by export, audited deletion and erasure; observing into that conversation is refused. Host context puts the current card in its own `<membrain-persona version="N">` block ahead of the notes, outside the notes budget; it is sent again only when the snapshot changes, and a removed or reset card is announced on the next turn. **Persona suggestions from feedback (Phase C, P2).** `GET /v1/brains/{brain_id}/persona/proposals` lists suggestions for a new card version, open ones first. Deciding on a proposal that is not open answers 409. A proposal appears when the user's own messages give the same kind of feedback on the companion's manner three times, in any conversations. The kinds are `less_formal` (more casual), `more_formal`, `more_playful`, `shorter`, `longer`, `less_emoji` and `more_emoji`. Since 2026-11-18 `shorter` sets `voice.length` to a limit a reader can check, "one to three sentences unless the user asks for detail" (in Chinese 一到三句话，除非用户要求详细), and `longer` to its mirror image, "four or more sentences unless the user wants a short reply" (至少四句话，除非用户要求简短); before, they set "short" and "detailed". A card accepted before keeps its word (versions are never rewritten), and three more comments of that kind then suggest the limit. Two sources say which messages give them. The host AI reports them through `POST /v1/brains/{brain_id}/persona/feedback` (`kind` plus `source_event_ids` and/or `source_messages`, 1 to 10 messages in all; Python `client.report_manner_feedback`, the MCP tool `memory_manner_feedback`, `membrain plugin tool manner_feedback`, which OpenClaw's `membrain_manner_feedback` runs, and AstrBot's `membrain_manner_feedback` through `ChatMemory.manner_feedback`; each cites messages the way that host's note tool does), in any wording or language. Every cited message that is already recorded must be the user's own message in an ordinary conversation, after the persona reset marker and not deleted; otherwise the report is refused (409, `source_unavailable`) and nothing is stored. A reference to the current message from the host's source block may not be recorded yet: it is kept and counts once the message is recorded and passes the same checks. A report stores the kind and message ids or references only, never words, as a `system` event in the proposals conversation; reporting the same kind for the same message again changes nothing, and the result never says whether a proposal opened. The tools refuse, and send nothing, while recording is paused. The second source is a fixed English and Chinese table of patterns, which are deliberately narrow and miss paraphrases and other languages. There is no model call. A message counts once for each kind it gives, whichever source saw it or both, so feedback the table recognises and the host AI also reports is not counted twice. Thresholds, pauses, consumption by decisions and contradictions are the same for both sources. These never count: messages from before the persona reset marker, deleted messages, role-play, hypothetical, dreamt or quoted messages, reported speech, the assistant's messages, memory-page messages and imported messages. For the host AI's reports, a message recorded with a role-play, hypothetical, dream or quotation interpretation hint is refused by the same rule; telling quotation or reported speech apart inside an ordinary message is the host AI's own judgement. A decision uses up the feedback before it. A proposal whose sources fall below three is withdrawn. A pending proposal never changes the `<membrain-persona>` block and is not mentioned in context. Proposals and decisions are `system` events in the reserved `membrain-persona-proposals` conversation: they are never learned from, recalled or counted, observing into that conversation is refused, they survive export and restore (read back strictly), and "Delete personality history" and erasing all memory remove them. Listing stores any proposal that has become due. Python exposes `persona_proposals`, `accept_persona_proposal` and `reject_persona_proposal`. The memory page's Companion tab shows them with the change as a card diff, in English and Chinese.

Deleting feedback or revising an old source cannot reopen that proposal or bypass a rejection's 30-day pause. A new proposal needs three eligible feedback sources after the decision. **Personality types.** The persona presets (`persona_presets`) are sixteen personality types (the four-letter types familiar from MBTI): `intj`, `intp`, `entj`, `entp`, `infj`, `infp`, `enfj`, `enfp`, `istj`, `isfj`, `estj`, `esfj`, `istp`, `isfp`, `estp` and `esfp`. Each has an `id` (the lowercase code, accepted in any case wherever a user or the AI passes one), a `label` (the uppercase code) and a hand-written one-line `summary` for the user. The cards are composed from the four letters: each pole adds a trait and a value (E outgoing, I reserved and reflective; S practical, details first, N imaginative, patterns and possibilities; T logical and candid, never unkind, F tactful, minding people and values; J organised and decisive, P flexible, keeping options open), E/I and T/F shape the voice, and the resting mood is calm for introverts (warmer with F), calm with more energy for ENTJ and ESTJ, glad for ENFJ and ESFJ, and playful for ENTP, ESTP, ENFP and ESFP. A rendered card is about 320 to 350 characters. Cards leave `name` (the host's own) and `voice.language` (the host AI answers in the user's language) empty. A type is how the companion presents itself, not how well it works: no card asks for less care, accuracy or help, and none overrides the user. An id that is not one of the sixteen (such as one of the five tone presets of an unreleased test build) reads as a custom card. `POST /v1/brains/{brain_id}/persona/first` gives a memory its first persona: only when its persona conversation holds no record of any kind (no version and no "history deleted" marker), it saves a type picked at random as version 1 with `made_by` "host" and `action` "preset" (not as a `host_default`). The check is repeated under the brain lock, so concurrent calls save one version; `assigned` is true only for the call that saved it. A user who deleted the personality history is never given one again; erasing all memory starts over, and the next session gets a new random type. The host layer calls it when a session's memory context is first built, in `session_context` and, when a session's start missed the service (as a new installation's first session usually does), in the first `prompt_context`. It is skipped for a role-play memory, whose character is the persona, and while recording is paused; a failure or an older service without the route never blocks the session. The session in which the first type was picked gets a one-time instruction in its session notice: name the type and its summary once, briefly, in the first reply, and say how to switch (`/membrain:persona` in Claude Code, asking the AI elsewhere). The instruction waits in the session's local state until the session's first prompt, so a session context rebuilt before then shows it again and nothing after it does; it is outside the saved-memory snapshot, so it never changes the context fingerprint or causes a resend. `GET .../persona/presets` lists the types and the current choice: `preset` (the version was saved from that type), `custom` (with `based_on`, the type an edited card started from) or `none`. `POST .../persona/preset` (`preset`, a type or `random` for one other than the current; `made_by` `user` or `host`; at most one `source_event_ids` or `source_messages` entry naming the user's request, checked like a manner-feedback source) saves that type as a new version with `action` "preset"; asking for the current type changes nothing. Resetting the persona (`POST .../persona/reset`, Python `reset_persona`, TypeScript `resetPersona`) now means picking a type again: the type named in its optional `preset` (or `random`); without one, the card the host itself saved with `host_default: true`, for a host that set one (a host default is never a type); otherwise a type picked at random other than the current one. A reset no longer empties the card. Versions record `preset` or `based_on`; restore and a reset to the host's default keep the type of the version they copy, an edit by the user keeps it as `based_on`, and a card the host sets is its own. Switching changes only the card, and keeps the agreements in force on it (below): mood triggers, pins and markers, familiarity, shared moments, boundaries and notes are untouched, and the simulated mood keeps its triggers while its resting point follows the new card's baseline. The memory page shows the current type with its summary, a select of the sixteen with a Switch button, and "Pick another at random"; it no longer has a button that resets to the host's default. Python exposes `persona_presets`, `assign_first_persona`, `switch_persona_preset` and `reset_persona(preset=...)`; TypeScript exposes `personaPresets`, `assignFirstPersona`, `switchPersonaPreset` and `resetPersona({ preset })`.

**Agreements across personality types (since 2026-11-18).** What the user agreed with the agent is memory, not part of a type: a manner suggestion the user accepted (a version with `made_by` "feedback") and a "from now on" change the agent proposed and the user confirmed or accepted (`action` "proposal"). No migration runs: the agreements in force are read from the version history (`persona.agreements_by_version`). Each is exactly what the user accepted, as recorded when they accepted it, never a difference against another version (since the outside review of 2026-11-18: before, deleting the version before an accepted one made the type's own traits, values and mood count as agreed). For an accepted manner suggestion it is the one change its kind states (`persona_growth.KINDS`: a voice field or a trait, with the value the accepted card holds; a card accepted with a kind's earlier value, such as "short", still counts, `persona_growth.EARLIER_VALUES`). For a confirmed or accepted host proposal it is what the accepted version records in `agreed_changes`: the voice fields the proposal set, the entries it added to the card it was accepted onto, and a name or baseline mood it gave. A proposal version saved before `agreed_changes` is read from the stored proposal it names: only the voice fields, name and mood it states. Its added traits, values and boundaries are not carried, since the proposal stored them merged with the card it was made on and an agreement is never read from another version; without the proposal nothing of it is carried. An agreement stays in force while the card still has it, so it can only shrink; deleting or hiding its own version ends it. Every switch of type and every reset, by the persona tool, `membrain plugin tool persona`, a chat bot, the memory page or `/membrain:persona`, named, random or back to the host's default, applies the agreements in force on top of the new card in the order they were made; a type that cannot hold them on one card is refused (422, nothing saved). Only the user ends one: an accepted change of the opposite kind, or a confirmed change of the same field, replaces it; a confirmed or accepted proposal that removes an agreed entry (`changes.remove`) or clears an agreed field shrinks that agreement or ends it, and a card written with `PUT .../persona` keeps only the agreements it still has; a removal is a change to the current card and never an agreement itself, so it is not recorded in `agreed_changes` and is not applied to another type's card: a later switch starts from that type's own card plus the agreements still in force, and an entry the user removed comes back only if it is that type's own entry, or by restoring a version that had it (an emptied voice field or name, or a null mood, is never part of an agreement, also where an earlier runtime recorded one); restoring a version takes the agreements in force at that version, so restoring one from before an agreement ends it and restoring one that had it brings it back; "Delete personality history" erases every version and so every agreement (the card is gone too), as erasing all memory does. A card the host writes with `PUT .../persona` is saved as given; the route stays for SDK hosts, and the memory page no longer uses it. Histories written before this change are read the same way: an accepted change is recognised, and one that an earlier switch already dropped from the card stays ended. `GET .../persona/versions` gives each version its `agreements` (`version`, `made_at`, `source` (`feedback` or `proposal`), the feedback `kind`, `reason` and the `changes` still in force) and its `base_card` (the card without them), and the listing's top-level `agreements` are the current ones. Since 2026-11-19 each agreement also carries `said_in`: the user messages it rests on that still exist (the message that confirmed the agent's suggestion, or the feedback messages of an accepted suggestion; empty when the user accepted it on the memory page), and a version made in a conversation carries `asked_in`, the user message that confirmed it or asked for the switch (`event_id`, `text`, `recorded_at`), or `{"deleted": true}` once that message is deleted or hidden. Both are read from the messages on each request; nothing of a deleted message is returned. The memory page shows the card without them and lists them below it as kept "whatever the personality type"; the `<membrain-persona>` block the host sees shows the whole card as before.

**Persona changes the host AI proposes.** `POST /v1/brains/{brain_id}/persona/proposals` (`changes`: any of `name`, `traits`, `voice` (field by field), `values`, `boundaries` (the three lists are added to the card's, not replaced) and `baseline_mood`, and since 2026-11-18 `remove`, an object of `traits`, `values` and `boundaries` lists naming entries of the current card to take off before the additions, so "replace X with Y" is one proposal; an empty voice field or name, or a null `baseline_mood`, clears it; a `reason` of up to 200 characters; optional `source_event_ids`/`source_messages`, checked like a manner-feedback source) stores an open proposal of kind `host` in the proposals conversation and changes nothing. An entry to remove must match an entry of that field of the current card, ignoring case and surrounding or repeated whitespace (as stored or as the `<membrain-persona>` block shows it); otherwise the proposal is refused (422, `validation_failed`, nothing saved) with a message that lists that field's entries, for example `The card's traits have no entry "sarcastic" to remove. Its traits are: "reserved"; "imaginative"; "logical"; "organised". Ask the user which they mean, or remove one of these as written. Nothing was saved.` The stored proposal keeps the fields it touches in their stored form (a list a removal touches is stored whole, as before), so an earlier runtime still reads it. At most one is open: a newer one withdraws the older (`withdrawn_because: "replaced"`), and a proposal made on an older card version is withdrawn once the card changes (`"persona_changed"`), also when the version it was made on is deleted and a later save takes its number. It must cite exactly one message, and that message must be the user's own message in an ordinary conversation, recorded after an assistant message of the same conversation that was itself recorded after the proposal. A recorded message is checked at once. A reference to the current message that is not recorded yet is refused when no assistant message has been recorded since the proposal (the same turn). Nothing was saved."). `conversation_id` only refuses early a yes that could never pass; the rule is always checked on the recorded message. **The persona tool.** MCP hosts get `memory_persona`, OpenClaw and AstrBot `membrain_persona`, and hosts without MCP `membrain plugin tool persona`, one tool with an `action`: `list`; `switch` with `preset` (a type in any case, or `random`), only when the user asked in the conversation, citing their message (refused without one); a user asking to reset their persona means `switch` with `random` or with the type they name; `propose`, when the user explicitly asks the AI to behave differently from now on or keeps asking for something beyond the manner-feedback kinds, never on the AI's own taste; `confirm` with the `proposal_id` after the user's clear yes, citing that message; and `decline`. The tool's text tells the AI to describe a proposed change in a sentence and ask, and not to propose a declined change again in that conversation. The tool's description tells the AI that `remove` takes card entries off as worded there and that a replacement is one proposal; `propose` answers with the proposal's `changes` and a `summary`, one plain line per change (`Remove from traits: "blunt".`, `Add to traits: "gentle".`, `Change voice.length from "short and considered" to "one sentence".`, `Clear voice.emoji (now "rarely").`), and when the proposal takes anything off the card its note adds: "Say what it removes. When `confirm` cites the current message from the `membrain-source` block, the tool finds that message's staged turn (by its `recording_capture`, or among the 32 most recently written session ledgers when the AI leaves the capture out) and sends its conversation as `conversation_id`, so a yes given in a conversation where the agent has not asked is refused at once. Tell the user briefly that it takes effect from their next message (not that it is already saved), and present yourself this way now." The tool keeps the proposal id and the turn's exchange handle (ids only; `plugin/persona-confirmations.json`, or one file per user under `plugin/persona-confirmations-users/`). At the host's next contact for that memory, the per-message context or the session notice, once the turn's recording outcome is known and the proposal is still open (the message was not recorded, because of a pause or a refused, failed or stale write, or did not pass the rule), the AI is told once: "Your confirmation of the persona change was not applied (the user's answer could not be used as evidence). The proposal is still open: ask again and confirm after their yes." followed by `proposal_id: <id>.`. A confirmation that was saved, or whose proposal was decided otherwise (declined, replaced, withdrawn, accepted or rejected on the page), is dropped without a line; an outcome still unknown after seven days is dropped without one too, and the line is held back while recording is paused. Erasing the person's memory through the host removes the file. A reference that no staged turn of this installation names (a host that records through the API itself) gets the service's own rule only: it is neither refused early nor followed up. Hermes has no persona tool: there the card changes only by switching the type or restoring a version on the page, and the OpenAI-compatible proxy is read-only. Claude Code also has the `/membrain:persona [list|<type>|random|reset [<type>]]` command (`reset` alone is `random`, `reset <type>` is that type) (`plugins/membrain/commands/persona.md`), which calls the tool, with the plugin command line as a fallback; the user typing it is the request. Local embedding inference batches up to 32 leased jobs per call, with each source and fence checked again before publication. Recall chooses sources by rank within the character budget before ordering the selected messages chronologically, so the highest-ranked update is not discarded just because it is newer.

**Affect evidence and reset boundaries.** An inferred feeling becomes visible only after its own reading has a current user-message source. Assistant-only speculation, unresolved references and draft/cancelled messages cannot establish a user's feeling or trigger simulated mood. A reading keeps its own source dependencies, including references that resolve later, across export/restore. Explicit sources on a replacement describe the new reading; they do not borrow older evidence inherited by the note. Without explicit sources, a replacement uses its inherited evidence, and sources older than “Clear feelings” cannot recreate the cleared emotion. New post-reset feelings remain supported. Historical records receive the same user-source and reset checks when read. These checks validate provenance, not whether a model's interpretation is semantically correct.

**Shared-source privacy in companion context.** Automatic mood, shared moments and commitment reminders inherit privacy from any current sensitive note sharing their source. This applies when the source is marked private before or after the derived record is saved. The relationship API retains the records and their actual counts with effective `sensitive` metadata; private missed commitments are neither surfaced nor acknowledged as shown. Mood keeps private readings in its succession logic so they can end an earlier public feeling, but they cannot generate a new mood trigger or expose a replacement reason. The memory graph still presents the underlying stored records with its normal privacy masking and authorized opt-in. These controls do not classify arbitrary text as sensitive or replace the user's explicit privacy settings.
