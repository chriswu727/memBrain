# First install to first value: the Claude Code plugin in a new user's seat on Linux

Launchers at `4fc15455` (pinned runtime `b465c4b7`); the upgrade run starts from runtime `f69d4cda`. Linux x86_64 (WSL2, 16 cores, shared with other test runs: load average about 7), system Python 3.12.3, uv 0.13.6. **No host was started.** A driver played Claude Code's part: it ran the plugin's real hook command lines from `plugins/membrain/hooks/claude-hooks.json` with `sh -c` and the hook's JSON on standard input, in Claude Code's order (the asynchronous start hook, the session-start hook and the tool server together at session start, `UserPromptSubmit` before each message, `Stop` three seconds later), killed each hook at its configured timeout as the host would, and started the tool server exactly as `.claude-mcp.json` says and spoke MCP to it. Every location was redirected into a sandbox (`HOME`, `XDG_*`, `UV_TOOL_DIR`, `UV_TOOL_BIN_DIR`, `UV_CACHE_DIR`, `MEMBRAIN_DIRECTORY`, `CLAUDE_PLUGIN_DATA`); `PATH` held only the system directories and the sandbox's `~/.local/bin` with `uv` and `uvx`, as the uv installer leaves them. The runtime was installed from GitHub and PyPI as a user's would be. Driver, events and logs: `~/.local/state/membrain-setup/runs/first-run-20261119/` (not in the repository).

What is a host's behaviour here (that a `UserPromptSubmit` hook delays the message until it returns or times out, how long the host waits for a tool server) is from Claude Code's documented hook model, **not observed**.

## Why the hooks go quiet: uv's tool lock

`uv tool install` holds `~/.local/share/uv/tools/.lock` for the whole installation. The hooks' `uvx --offline --from membrain-ai …` (or `uv tool run`) opens the same lock and waits, so every hook waits until the host kills it. Shown with a process probe (`futex_do_wait` with both lock files open) and with the session-start command alone while `uv tool install` ran: 10.01 s, killed, no output; with `export UV_LOCK_TIMEOUT=2;` in front, 2.01 s and the not-ready line. Run A's line arrived only because its hook ran before uv took the lock.

## The first database start holds the profile

The first start prepares the embedded database under the profile lock: it preserves a copy of the bundled engine (4 to 28 s here, by load), initialises and starts PostgreSQL three times. From profile creation to service: 11 s (A), 21 s (B), 31–33 s (C, D1, D2, D4). Every hook reads the profile through that lock, which waits up to 30 s:

- **Run C** (warm cache, a message the moment the profile appeared): the prompt hook was stopped at 15 s, so the message was never staged and was lost (`turn_not_staged`); a second session started then was stopped at 10 s with nothing said; the doctor waited 30.02 s.
- **The tool server crashed** with `LocalProfileBusy` when the preparation outlasted its 30 s wait: run D1 (its first session online) and both sessions of run D4. Of the seven fresh installations here, two had a first working session with no memory tools at all; in the others the tool server answered after 29 (A), 32 (D3), 36 (C), 121 (B) and 179 s (D2, the session after the interrupted one).

## Upgrade: runtime `f69d4cda` running, launchers pinned to `b465c4b7` (run E)

The asynchronous hook replaced the tool in about 1.5 s; the service was then restarted **twice** (`service.log`: shutdown at 3.3 s and again at 12.1 s, three seconds after the first new instance started). Which process made the second restart was not recorded; from the code, `host.start` checks for `restart_required` outside the lifecycle lock, so the asynchronous start and a background start triggered by a hook can both restart. Memory was unavailable from 4.4 to 22.3 s. The session-start context was the 586-character starting notice, so that session began without notes or history; they arrived with the first message after the restart (31 s). Messages at 3, 10 and 20 s were queued and recorded: **7 of 7 kept**. The tool server crashed at 3.1 s with `restart_required` ("Configuration changed; run desktop restart to apply it."), so the first session after every runtime update has no memory tools. Nothing tells the user an update happened.

`membrain plugin ui --no-browser` printed a single-use link; headless Chromium showed "Keyword memory is ready", "No agent messages received yet. That command form has not been run on a real host (the real-host trials loaded the plugin with `--plugin-dir`).

## Two observations outside the first-run path

- **The plugin does not install the tested dependency set.** `uv tool install` from the archive ignores `uv.lock`: the sandbox runtime got onnxruntime 1.32.0, fastapi 0.165.0 and numpy 2.5.5 where the lock (and the test suite) has 1.31.1, 0.161.0 and 2.5.4.
- **Importing onnxruntime contacts Microsoft.** About 9 s after `import onnxruntime.capi._pybind_state` (1.31.1 and 1.32.0, Linux x86_64), two or three HTTPS connections go to `mobile.events.data.microsoft.com` (14–22 KB per service start through the proxy); `numpy` and `tokenizers` alone make none, and `onnxruntime.disable_telemetry_events()` did not stop them. The service imports it at start. What is sent was not inspected (TLS).

## Fixed in this change

`membrain doctor` (all with tests in `tests/test_diagnostics.py`):

- A start or stop in progress is a warning, `starting_or_stopping`, "A start or stop is in progress. Run membrain doctor again in a minute.", instead of `error, stopped` with "restart only after inspecting the reported cause"; also when the start holds the profile longer than the doctor waits for it, which read as "Configuration could not be read".
- A port held by another program is named: "Another program is listening on port 58461, the port this installation's service uses. Close that program, then run membrain plugin start; no process was stopped." (checked against run D3's installation with a listener on its port).
- The database engine check ran for no installation: the status it read never carries the engine. It now reads the profile.
- Semantic recall says what each state means and advises only what helps: `ready` without "keyword recall remains available once the service is ready"; `downloading` without "Run membrain plugin fetch-model"; `download_failed` names `HF_ENDPOINT`; `unavailable` says the semantic extra is missing.

`membrain plugin start` and `desktop stop` name the port in their `port_conflict` message. The reference, both READMEs and the plugin README no longer say the not-ready line is given while uv installs, or that the hooks take no extra time.

## Proposed, not made (each changes behaviour, a launcher, or what a host is told)

1. **Launchers: do not wait for uv's lock.** `export UV_LOCK_TIMEOUT=2;` before the runtime command in the three synchronous Claude Code hooks, the three Codex hooks and `bin/membrain-hook`. Measured: the not-ready line in 2.0 s while installing, instead of nothing after 10 s; a message waits 2 s instead of 15. Cost: 26 characters per command line, no change to argv, so `tests/test_launchers.py` and the pin round trip are unaffected; uv releases without the variable behave as now.
2. **Launcher line: true when installation finishes mid-session.** "…not ready yet, so nothing is remembered or recalled in this session" is false within 30 s to 2 minutes; say "until it is ready". Cost: the test constant.
3. **Runtime: hooks wait at most a second or two for the profile**, then treat it as starting: the message is staged and queued instead of lost (run C), and the session-start says memory is starting instead of nothing. Cost: a runtime change and pin.
4. **Runtime: the tool server answers at once and never exits on a busy profile, a pending restart or a port conflict**; its tools say "memBrain is starting" until the service is ready, and a pending restart is applied rather than reported. Cost: a moderate change to `plugin mcp`; it ends three crashes seen here and the 29–121 s wait.
5. **The first start of a new installation** could initialise on the bundled engine directly, without preserving a legacy engine copy and running a transition with three PostgreSQL starts (10–33 s). Cost: migration-critical code; needs its own review.
6. **A smaller archive.** `evaluations/ export-ignore` in `.gitattributes` would take about 130 MB off every installation and every retried one, from the next pinned commit. Cost: confirm that the archive still builds the wheel (`architecture/memory-contract.schema.json` and `migrations/` must stay).
7. **What the host is told while the service starts.** The 192-character unknown-state notice ("Reconnect to confirm it; local resume does not change server recording controls") reaches the host on every message during a start, an upgrade or a port conflict; plainer words when no pause is known, and the cause when it is known ("another program uses port N"), would let the host tell the user something useful. Cost: host text during outages; the fail-closed meaning of an unknown pause state must stay.
8. **Messages lost before memory became active go unmentioned.** The mid-session activation line could say once that earlier messages of this conversation were not kept.
9. **Pinned dependencies for installations**, and a decision about onnxruntime's connection to Microsoft (document it, find a supported opt-out, or keep the model elsewhere).
