## Behavior and limits

Previously, one foreground replay attempted the entire queue. If a later request failed, already confirmed records remained in that queue and were retried next time. Foreground replay now stops after at most 16 records or a one-second budget checked between requests. A dedicated local-service thread drains batches of up to 64 records even if the user sends no further messages. It uses a two-second loopback HTTP timeout, yields 50 ms after progress, backs off transient failures up to 30 seconds, and joins during service shutdown. This thread does not call a model or replace cognitive learning.

A synchronized cursor holds only the confirmed byte offset and prefix checksum. Reading verifies the prefix before skipping it; a missing, malformed or stale cursor causes idempotent replay rather than skipping unconfirmed records. Confirmed progress is saved even if a subsequent request fails. A process exit can still repeat the current uncheckpointed batch, so server idempotency remains required.

Batch reads target 256 KiB; one oversized record may extend the read up to the physical queue limit. Compaction streams remaining bytes at 1 MiB acknowledged, half the file, or completion, instead of rewriting the entire backlog after every small batch. The cursor is cleared before file replacement, so either side of an interrupted replacement remains safe to replay. Recording-policy rejection forces compaction before return. User erasure removes only pending records and clears the cursor; status counts exclude confirmed prefixes. The existing queue/session/write lock ordering and original recording revisions remain intact.

The physical queue remains capped at 64 MiB, including acknowledged bytes awaiting compaction. A request already in flight keeps its timeout and can exceed the between-request budget. Other work in a host callback, abandoned-input recovery, checkpoint I/O and filesystem contention also take time; this is not a strict end-to-end callback deadline. Local files and server observations are not one transaction. User and assistant observations can become visible separately, and a queued receipt is not proof of learning or of successful later replay. Local/server control synchronization, ephemeral durable turns, independent AgentRuntime receipts and server-wide erasure fencing for delayed writes remain open.

## Performance measurements

The public probe compares integration `a9ac456` with this runtime in separate processes, using 3,000 FIFO records, real filesystem writes and a fake observation transport. Each mode runs baseline/candidate/candidate/baseline, with two samples per variant. Python allocation tracing is enabled and affects timings. It does not measure process RSS, PostgreSQL, model calls or end-to-end recall.

| Measurement | Previous implementation | Bounded replay |
| --- | ---: | ---: |
| Foreground median, 0.2 ms injected per observation | 893.23 ms | 5.42 ms |
| Records completed by that foreground call | 3,000 | 16 |
| Foreground peak traced Python allocation | 3,689,875 bytes | 18,458 bytes |
| Complete 3,000-record drain median, no injected delay | 56.03 ms | 110.07 ms |
| Complete drain peak traced Python allocation | 3,689,875 bytes | 184,020 bytes |

The foreground comparison demonstrates returning after a bounded amount of work, not completing the same backlog faster. The complete-drain comparison uses the supervisor's 64-record batch size and excludes its scheduling sleeps; checkpoints add about 54 ms of local processing for these 3,000 records while reducing temporary allocations. The earlier probe used 16-record batches for complete draining and measured approximately 228 ms; its raw samples remain retained, but that is not the supervisor's batch configuration. These are small local descriptive samples, not throughput guarantees or a capacity ceiling.

A separate installed-service exercise queued **1,000 public synthetic records** in one append, then sent no host callbacks. The local service, embedded PostgreSQL and loopback HTTP completed all 1,000 distinct events with exact text equality and zero pending records in **9.220 seconds** (76 polling requests). This includes polling and local indexing contention, has no previous-version baseline and is not a general throughput guarantee. The disposable service was stopped and its 124,819,872-byte test installation removed.

This is a follow-up boundary, not an implemented synchronization contract or a reason to relabel R4/C5.
