SAYS Here's a first sketch. I assumed the columns, since I haven't seen your schema. The server and local databases differ, so there's one version for each.

**PostgreSQL (server)**
```sql
-- up
CREATE TABLE projects (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  name        text NOT NULL,
  description text,
  owner_id    uuid NOT NULL,          -- FK to users once that table exists
  archived_at timestamptz,
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX projects_owner_idx ON projects (owner_id) WHERE archived_at IS NULL;

-- down
DROP TABLE projects;
```

**SQLite (local)**
```sql
-- up
CREATE TABLE projects (
  id          TEXT PRIMARY KEY,       -- uuid generated by the app
  name        TEXT NOT NULL,
  description TEXT,
  owner_id    TEXT NOT NULL,
  archived_at TEXT,                   -- ISO 8601 UTC
  created_at  TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now')),
  updated_at  TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now'))
);
CREATE INDEX projects_owner_idx ON projects (owner_id) WHERE archived_at IS NULL;

-- down
DROP TABLE projects;
```

Decisions I'd like you to confirm:
1. **IDs:** I used UUIDs on both sides, generated by the app. That way a local row can sync to the server without remapping keys. Integer IDs would break that.
2. **Sync:** if local and server will sync, the tables will need a way to detect conflicts. `updated_at` may be enough, or you may want a version column or soft deletes.
3. **Migration tool:** the two dialects differ, so I'd keep separate migration directories for server and local. Which tool are you using?
4. **Other columns:** do you need slug, status, or team/workspace ownership?
