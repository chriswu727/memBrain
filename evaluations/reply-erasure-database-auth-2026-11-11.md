# Deletion that reaches the reply, a lifecycle scenario, and SCRAM-only database connections

Base: pin `b04af871`. Runtime commits `24d50954` (reply erasure) and `933f4d8a` (database authentication); pin commit `4af71af6` points all nine launchers at the latter. No migration. It closes no release gate: **R4 remains failed and C5 invalid/unscored.**

Everything ran on WSL2 Linux with task-owned embedded PostgreSQL 16.15 and pgvector 0.8.6. No model was called. GitHub Verify, native Windows and macOS, the Docker database path, five-platform qualification, the R5 overhead protocol and an independent review were not run.

## One life of a memory, as a test

`tests/test_memory_lifecycle_scenario.py` runs the scenario the project uses to check that its parts hold together, through the plugin path on a real local service:

1. The user says where they live and who they run with. The message is stored and the host saves two notes from it, bound to that message.
2. The memory is recalled three times. Nothing is added and nothing changes.
3. The user corrects where they live. The new note replaces the old one; later sessions show the corrected fact in the notes, and what remains of the earlier statement appears before the correction, as history.
4. The user has the memory of their running partner deleted. The message, the reply to it and both notes drawn from it are gone from notes, history, recall (including a question about what the assistant said) and the memory map. The correction, which came from another message, is untouched.
5. An archive exported before the deletion is restored. Nothing deleted comes back.

Not covered, because the default path has no step that produces them: an inferred statement kept apart from what the user said, and the effect of a deletion on personality, mood or relationship state.

## Deletion did not reach the reply

The scenario failed at step 4 on its first run. **In the plugin path, erasing a user message left the assistant's reply to it in place.** The reply usually restates the message ("Running along the river with Xiao Lin sounds like a good start"), and stayed in history, in exports, and in recall when the user asked what the assistant had said.

A host-recorded reply names the message it answers (`parent_source_event_keys`), and recall used that link to exclude descendants of a cue, but the event was not recorded as *depending* on the message. A reply generated by the runtime already was. The observe path now records the dependency, so a reply is hidden, erased and exported together with its message, by the same mechanism that already removes notes with their source.

Consequences to know:

- A reply whose message is erased goes with it even when the reply also said things of its own.
- Hiding a message (`suppress_recall`) hides its reply as well.
- Replies stored before this change have no such dependency and are not reached retroactively.

## Database connections require SCRAM-SHA-256 on loopback

One of the two credential findings withheld from the [status audit](status-audit-2026-11-10.md): database connections sent a password without constraining how a server may ask for it, and where a port was already open the client authenticated before it checked what it was talking to. A process holding the loopback port while the real database was down could ask for the password in cleartext.

Every connection the product opens now goes through one helper (`storage.connection_info`):

- **The product's own profiles and its administrator connection always set `require_auth=scram-sha-256`.** SCRAM proves knowledge of the password to both sides and never sends it.
- **A configured URL to a loopback address gets the same requirement** unless it sets `require_auth` itself; other hosts and Unix sockets are left as configured.
- **The bundled `pg_dump` and `pg_restore` get it through `PGREQUIREAUTH`.**
- **A client library older than libpq 16, which does not know the parameter, refuses to connect** with a clear message instead of dropping the requirement.

A test server that answers the startup message with a cleartext or MD5 password request receives no password from the administrator connection, a loopback URL, a pooled connection, a profile URL or the real `pg_dump`; a control shows that an unconstrained client does send it.

Consequences to know:

- A developer's own local PostgreSQL that uses `trust` or `md5` on loopback is now refused unless its URL sets `require_auth`. The embedded cluster and the Docker image use SCRAM.
- The installed psycopg bundles libpq 18.6. The pure-Python psycopg uses the system's libpq, which may be older; that case is simulated, not run.
- SCRAM without channel binding still lets a fake server collect material for offline guessing; the passwords are 192-bit random values.

The other withheld finding (how the memory page's sign-in code is handed over) remains open.
