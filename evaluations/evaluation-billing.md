# Billing control for a prospective evaluation

This control grants no permission to call a model. The release remains frozen, and no real R4/C5 run has been approved. The guard has offline tests; its policy and implementation still need independent review before execution approval is requested.

`evaluation_budget.py` wraps the C5 harness's host transport, the only provider transport the harness has (the extraction arm E and its extractor transport were removed before the sixth attempt; this sentence said "host and extractor" until 2026-11-17). All four scenarios, every arm and every retry use the same absolute `C5_BILLING_LEDGER` path, `C5_ATTEMPT_ID` and `C5_BILLING_POLICY_SHA256`. The policy hash binds the run ID, ledger path, limit, endpoint and model bounds/rates. A switched ledger, attempt or policy is refused before HTTP. Live harness runs refuse a missing ledger; the public stub mode needs none and still refuses external sockets.

Before an approved run, the operator calls `create_ledger(path, run_id=..., limit_cny=..., endpoint=..., models=...)` with the frozen policy. The file must be new. The returned metadata includes the initial ledger hash; freeze it, the absolute path and the policy hash in the attempt pre-checks. Never delete, reset or replace that ledger during an attempt. It contains no API key, messages, replies or scenario contents. It records integer micro-CNY, per-request reservations, conservative settled charges and token counts. The policy for each request model has:

- `context_tokens`: the provider's complete supported context bound, not an estimated prompt length;
- `max_output_tokens`: the provider's complete published maximum output bound, including reasoning; this can exceed the smaller per-request limit;
- `input_cny_per_million` and `output_cny_per_million`: decimal strings for the maximum applicable rates;
- optional `response_models`: exact reviewed response model identifiers, if the provider returns a version rather than the request alias.

The endpoint is the exact HTTPS chat-completions URL. Only text, non-streaming completions and client function tools are permitted. Provider search/fetch tools, multimodal content, unknown request options and alternate endpoints are refused.

For each request, the guard reserves the full context bound at the maximum uncached input rate plus the complete published output bound at the maximum output rate. It does not rely on a thinking model applying the requested `max_tokens` only to final-answer tokens. A response beyond the requested limit is still invalid and retains the complete reservation. It does not predict tokenization, cache hits or discount windows. A POSIX file lock coordinates separate processes; atomic replacement and file/directory sync preserve reservations across restarts. This evaluation utility supports the Mac/Linux acceptance runners, not Windows.

A successful response can reduce its reservation only when its model and integer token accounting match the frozen bounds. Cache hits are still charged at the conservative maximum input rate. Every request refusal, including insufficient reservation capacity or a malformed/unsupported request, persists a shared stop. Already reserved requests may complete and settle; this never clears the stop. An unaccounted request left by a crashed process retains its full reservation; it is never automatically reclaimed. Full-bound reservations can stop an attempt before its actual spend reaches the approved cap; leave enough headroom in the reviewed plan.

**Interrupted requests (since 2026-11-17).** A request is settled as *interrupted* at a bound that is true for that request when it:

- ends in a transport timeout or a connection or protocol error (`ConnectTimeout`, `ReadTimeout`, `WriteTimeout`, `PoolTimeout`, `TimeoutException`, `ConnectError`, `ReadError`, `WriteError`, `CloseError`, `RemoteProtocolError`; kind `provider_transport`);
- is answered with HTTP 429, 500, 502, 503 or 504 (kind `provider_http_status`; since the 2026-11-17 review, finding F3, any other 5xx such as 501 or 505 is final, because a resend will not change it);
- is answered with a 2xx whose body is read completely but holds no billing JSON (kind `provider_incomplete_body`, with the status and a fixed `body` reason: `blank` for only whitespace or empty lines, `not_json` for a body that does not parse, `no_usage` for JSON without a `usage` key, such as an error object; since the review, finding F1). The provider's documentation (as quoted in the 2026-11-17 review) says that a non-streaming request under load "continuously return[s] empty lines" while it waits, and that "if the request has not started inference after 10 minutes, the server will close the connection"; it does not say whether that close is abrupt (a `RemoteProtocolError`) or a clean end of a body of blank lines, so both are interruptions. Whatever the service did, no more than one completion of this request can have been billed, which the bound covers.

The rest of its reservation is released and the ledger is **not** blocked: the guard raises `ProviderInterrupted` (a `BudgetStop`), so a caller that does not retry still stops. A body cut short after a final status (any status but the five above and a 2xx) is not an interruption. The bound, from sizes the guard records at reservation (`request_bytes`, the body's bytes as sent, and `tools_bytes`, its tool schemas in shortest JSON form):

```
prompt_tokens_bound = min(context_tokens, 2 × request_bytes + 4 × tools_bytes + 16,384)
charge              = ceil(prompt_tokens_bound × input rate) + ceil(max_tokens × output rate)
```

with the request's own `max_tokens` and the policy's maximum rates.

*Why it cannot undercount the prompt.* DeepSeek's published tokenizers are byte-level BPE (the 2026-11-17 review checked the published V4 tokenizer offline: a ByteLevel pre-tokenizer and decoder, BPE with 128,000 entries, no empty vocabulary entry, an empty normalizer, and at most 1.0 token per byte on 3,000 random mixed-script strings and adversarial ones). Every token stands for at least one UTF-8 byte of the text it encodes (a merge only joins bytes), so a text never has more tokens than bytes, whatever the language: English text is about one byte per character, German umlauts two, Chinese characters three, emoji four, and a script without merges costs at most one token per byte. What the service puts into the prompt is not documented:

- **Message text.** That the service renders message text as sent is an *assumption*, not documented behaviour. The tokenizer archive's `chat_template` is the older V3-style template, which renders neither tool schemas nor reasoning, so it says nothing about what the V4 service adds. The JSON body holds every byte of the message text once (escaping only lengthens it), so the body's byte count covers that text once; the factor 2 leaves a whole further copy of the body as slack, and the 16,384-token allowance covers the template's own text, role markers and any tool or reasoning preamble (the JSON framing of each message, at least 29 bytes, already exceeds a few markers per message). The bound would fail only if the service added more than another copy of the body plus 16,384 tokens plus four times the schemas.
- **Tool schemas.** A template may re-serialize the schemas in any form. An earlier version of this text argued that JSON escaping writes at most six bytes per byte and that `2 + 4 = 6` times the shortest form covers it; that argument does not cover a template that pretty-prints the schemas, because indentation is not escaping and, with deep nesting of short values, can add more than six bytes per byte. The bound still holds for another reason: in a byte-level BPE, runs of whitespace merge into few tokens (the review measured 5,000 spaces as 40 tokens with the published V4 tokenizer), so indentation costs far fewer tokens than bytes, and the schemas are already inside the body, which the factor 2 counts twice, besides the four further copies of their shortest form and the allowance.
- **The cap.** The cap at `context_tokens` holds because a longer prompt is refused by the provider, and a settled prompt above it is already invalid evidence here.

*The completion side* (review finding F2; no code change). The completion bound relies on one provider behaviour the full reservation does not: that `max_tokens` bounds all completion tokens, reasoning included. The provider's documentation, as the review quotes it, implies this but never states it:

- `max_tokens` is "the maximum number of tokens that can be generated in the chat completion";
- its default is "8K in non-thinking mode, 64K in thinking mode (128K with `reasoning_effort` set to `max`)", a larger default in thinking mode that makes sense only if reasoning counts toward it;
- `completion_tokens_details.reasoning_tokens` is a "breakdown of tokens used in a completion", so `completion_tokens` includes reasoning;
- `finish_reason=length` means "the maximum number of tokens specified in the request was reached";
- no page says in words that reasoning counts toward `max_tokens`, and the thinking-mode guide does not mention `max_tokens` at all.

The repository's evidence: the 2026-10-25 pilot's simulated-user call on `deepseek-v4-pro` with thinking on returned 4,096 completion tokens, all 4,096 of them reasoning, with `finish_reason=length` at a 4,096-token bound (`v1-2026-10-25-longitudinal-pilot.json`, `v1-2026-10-25-longitudinal-harness.md`); the v3 invocation's proposal spent all 16,384 completion tokens on reasoning and returned `finish_reason=length` at a 16,384-token bound (`v1-2026-10-25-longitudinal-reasoning-failure.json`, `v1-2026-10-25-longitudinal-followup.md`). Every settled response is checked for `completion_tokens ≤ max_tokens`, and a violation blocks the ledger; the 265 requests attempt `maturity-c5-20261117b` settled ([stop record](maturity-c5-attempt-stop-2026-11-17.md)) all passed that check, since that attempt stopped on a timeout and not on `response_billing`, but with 81,322 completion tokens among them (about 307 each) they never came near the bound and do not test it there. If the assumption were wrong, an interrupted send could be billed up to (393,216 − 16,384) × 27 / 10⁶ = 10.174464 CNY more than its bound. Charging the policy's `max_output_tokens` instead would cost at least 393,216 × 27 / 10⁶ = 10.616832 CNY per interruption on the output side alone (about 11.1 to 13.5 CNY with the prompt side), so that at most two interruptions would fit in the C5 attempt's free headroom of about 10 to 30 CNY, and none at its top; that alternative is not taken. Re-check the provider's limits before approval.

*Charges in the C5 harness* (`max_tokens` 16,384, 9 and 27 CNY per million): an interrupted send costs 16,384 × 27 + 16,384 × 9 = 589,824 micro-CNY (about 0.59 CNY) plus 2 × 9 = 18 micro-CNY per byte of body (0.018 CNY per KB of 1,000 bytes) plus 4 × 9 = 36 micro-CNY per byte of tool schemas. `P`'s 14 tools are 16,425 bytes in shortest JSON at commit `e82ad9d6` (measured offline from the plugin's MCP server; 17,217 is their character count with spaced separators, the figure used earlier), which adds 0.5913 CNY, about 0.59 to 0.62 CNY as the descriptions change. So a 40 KB body without tools is charged 1.31 CNY, a 40 KB `P` body carrying the schemas 1.90 CNY, and a 150 KB body (a late `F` prompt) 3.29 CNY, against the 20.054016 CNY reservation each held while in flight. The absolute maximum is the context cap: 1,048,576 × 9 + 16,384 × 27 = 9,879,552 micro-CNY (9.879552 CNY), reached at a body of 516,096 bytes without tools (about 483 KB with `P`'s schemas). A host call that fails on all three sends costs three bounds (for a 150 KB body 9.87 CNY; at most 29.638656 CNY).

*What the ledger keeps.* Each entry carries, besides the sizes, `seq` (a number increasing in reservation order across every process sharing the ledger, taken under its lock), `reserved_at` and, once its outcome is recorded (a settlement, an interruption's bound or a retained failure), `settled_at` (epoch seconds), since review finding F4. An interrupted entry keeps an `interrupted` object: the cause (as below) and `prompt_tokens_bound` and `completion_tokens_bound`. The ledger version stays 1 and the policy hash is unchanged: the fields are additive. On a ledger written before them, the guard numbers each new reservation after the count of entries already there, so numbers never repeat; an older guard ignores the fields. When the request has no usable `max_tokens` (the guard refuses such a request before HTTP anyway), lacks its recorded sizes (an older ledger), or the bound cannot be computed or exceeds the reservation, the old rule applies: the reservation is kept, the ledger blocked, the run stopped. Retrying is the caller's decision: the C5 host client sends the same request again after 30 and then 120 seconds, three sends at most, and blocks the ledger itself after a third interruption ([`c5-harness.md`](c5-harness.md#harness-events-stops-and-the-log)); each send reserves and settles like any request.

*The ledger check* (review finding F4). After each scenario's validity, the attempt driver runs `acceptance_review.py ledger-check --ledger LEDGER --after-seq N RUN_DIR...`, with N the ledger's highest `seq` read before the scenario started. It compares the ledger's interrupted entries reserved during the scenario with the lines of the run directories' `provider-interruptions.jsonl`, by code (class, `http_<status>` or `body_<reason>`) and request size. A difference (an interrupted send charged but not recorded, or recorded but not charged) is a harness defect, not a host behaviour, and makes the scenario invalid. A ledger whose entries have no `seq` cannot be checked and fails it. The check reads codes, counts and sizes only. It does not touch the ceiling, which the ledger alone bounds.

**Still fatal.** Any other HTTP status (a 4xx other than 429, and a 5xx other than 500, 502, 503 and 504), a 2xx response whose usage is present but cannot be settled (malformed, inconsistent or out-of-bound usage, `completion_tokens` above `max_tokens`, an unapproved response model), a guard refusal for lack of headroom or of a malformed request, `SystemExit`, `KeyboardInterrupt`, and any transport class outside the list above (`DecodingError`, `LocalProtocolError`, `ProxyError`, `UnsupportedProtocol`, unknown classes): the request retains its whole reservation and all subsequent requests are blocked. A refusal or uncertain bill invalidates the affected acceptance unit and stops all new provider work. A request in flight holds its whole reservation until it settles, interrupted or not, so the refusal point counts it in full while it is open and at its bound afterwards.

Provider failures record a content-free object on the reserved request: `failure` when the reservation is retained, `interrupted` when it was settled at its bound; the first global `stop_reason` is preserved. `provider_transport` includes only a fixed allowlist of exception class names (unknown classes become `other`); `provider_http_status` includes the numeric status; `provider_incomplete_body` includes the 2xx status and one of the fixed reasons `blank`, `not_json` or `no_usage`; `response_billing` identifies rejected response/usage evidence. Exception messages, response bodies, headers and unapproved model names are never recorded, nor chained into the raised exception. A sibling's interruption or supervisor cleanup cannot replace the original global cause. A retained `failure` never releases a reservation or permits a retry. Older stopped ledgers without these fields cannot be retrospectively diagnosed from `BudgetStop` alone.

The C5 supervisor checks child completion throughout its 15-second launch stagger and final wait, using polling compatible with macOS Bash 3.2. On a failed arm it reports that arm's original exit status, invokes the policy-bound `--stop` control before terminating siblings, and reaps every active child. SIGTERM raises `SystemExit` in the harness so its cleanup stops only the disposable profiles it started. Its handler blocks the ledger first, except while the harness is inside a guarded section (waiting for the ledger lock or holding it, `lock_held()`): there `stop()` would take the lock again on another descriptor and wait for its own process until a SIGKILL (review finding F7). Then the handler only exits; the request in flight keeps its whole reservation, and the run script's `--stop`, which runs from another process on any failed arm, blocks the ledger. `GuardedTransport.stop()` is idempotent; `allow_stopped=True` permits opening an already-stopped ledger for that control, but cannot admit a provider request or clear its stop. The ledger records a fixed operation reason as well as reservations and usage. A failed attempt never automatically receives a new ledger or allowance.

Live pre-flight refuses unrelated provider/memory configuration. Local service startup gets an allowlist of system variables and the scenario clock, without provider credentials, and cannot reload dotenv configuration. The scenario creates a fresh profile without configured remote cognition or embedding providers.

The monetary bound depends on the reviewed provider rates and token limits actually holding. Re-check the provider's [pricing](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/) and [completion limits](https://api-docs.deepseek.com/api/create-chat-completion/) immediately before approval. Freeze them with the plan and code; do not rely on historical balance estimates. The account balance is a separate reconciliation check and includes any unrelated account use. Subscription scenario authors and judges are outside this API ledger and require their own explicit approval.

`tests/test_evaluation_billing_guard.py` exercises thread/process contention, unknown requests after a crash, failure retention, accounting validation, cache conservatism and protocol rejection using only mock transports. `tests/test_provider_interruption_retry.py` covers interrupted settlements, the host client's retries, the bound against a worst-case tokenizer model over English, German, Chinese and mixed prompts, the refusal point with interrupted settlements, two arm processes on one ledger, the call cap, and what validity and `diagnose` report. `tests/test_billing_review_fixes.py` covers the 2026-11-17 review's fixes: 2xx bodies without billing JSON retried while present-but-wrong usage stays fatal, 502 retried and 501 fatal, sequence numbers and times under two processes and on an older ledger, the ledger check passing and failing, the delay per session, and a SIGTERM inside, while waiting for, and outside a guarded section (with a control that hangs without the lock check). `tests/test_c5_harness.py` covers the live-ledger prerequisite and shared-stop check. A stub or unit result is not a real billing or behavioural acceptance result.
