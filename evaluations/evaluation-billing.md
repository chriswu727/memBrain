# Billing control for a prospective evaluation

This control grants no permission to call a model. The release remains frozen, and no real R4/C5 run has been approved. The guard has offline tests; its policy and implementation still need independent review before execution approval is requested.

`evaluation_budget.py` wraps the C5 host and extractor transports. All four scenarios, every arm and every retry use the same absolute `C5_BILLING_LEDGER` path, `C5_ATTEMPT_ID` and `C5_BILLING_POLICY_SHA256`. The policy hash binds the run ID, ledger path, limit, endpoint and model bounds/rates. A switched ledger, attempt or policy is refused before HTTP. Live harness runs refuse a missing ledger; the public stub mode needs none and still refuses external sockets.

Before an approved run, the operator calls `create_ledger(path, run_id=..., limit_cny=..., endpoint=..., models=...)` with the frozen policy. The file must be new. The returned metadata includes the initial ledger hash; freeze it, the absolute path and the policy hash in the attempt pre-checks. Never delete, reset or replace that ledger during an attempt. It contains no API key, messages, replies or scenario contents. It records integer micro-CNY, per-request reservations, conservative settled charges and token counts. The policy for each request model has:

- `context_tokens`: the provider's complete supported context bound, not an estimated prompt length;
- `max_output_tokens`: the provider's complete published maximum output bound, including reasoning; this can exceed the smaller per-request limit;
- `input_cny_per_million` and `output_cny_per_million`: decimal strings for the maximum applicable rates;
- optional `response_models`: exact reviewed response model identifiers, if the provider returns a version rather than the request alias.

The endpoint is the exact HTTPS chat-completions URL. Only text, non-streaming completions and client function tools are permitted. Provider search/fetch tools, multimodal content, unknown request options and alternate endpoints are refused.

For each request, the guard reserves the full context bound at the maximum uncached input rate plus the complete published output bound at the maximum output rate. It does not rely on a thinking model applying the requested `max_tokens` only to final-answer tokens. A response beyond the requested limit is still invalid and retains the complete reservation. It does not predict tokenization, cache hits or discount windows. A POSIX file lock coordinates separate processes; atomic replacement and file/directory sync preserve reservations across restarts. This evaluation utility supports the Mac/Linux acceptance runners, not Windows.

A successful response can reduce its reservation only when its model and integer token accounting match the frozen bounds. Cache hits are still charged at the conservative maximum input rate. Every request refusal, including insufficient reservation capacity or a malformed/unsupported request, persists a shared stop. Already reserved requests may complete and settle; this never clears the stop. An unaccounted request left by a crashed process retains its full reservation; it is never automatically reclaimed. Full-bound reservations can stop an attempt before its actual spend reaches the approved cap; leave enough headroom in the reviewed plan.

**Interrupted requests (since 2026-11-17).** A request that ends in a transport timeout or a connection or protocol error (`ConnectTimeout`, `ReadTimeout`, `WriteTimeout`, `PoolTimeout`, `TimeoutException`, `ConnectError`, `ReadError`, `WriteError`, `CloseError`, `RemoteProtocolError`), or that the provider answers with HTTP 429 or a 5xx, is settled as *interrupted* at a bound that is true for that request, the rest of its reservation is released, and the ledger is **not** blocked: the guard raises `ProviderInterrupted` (a `BudgetStop`), so a caller that does not retry still stops. A body cut short after a final status (a 4xx other than 429) is not an interruption. The bound, from sizes the guard records at reservation (`request_bytes`, the body's bytes as sent, and `tools_bytes`, its tool schemas in shortest JSON form):

```
prompt_tokens_bound = min(context_tokens, 2 × request_bytes + 4 × tools_bytes + 16,384)
charge              = ceil(prompt_tokens_bound × input rate) + ceil(max_tokens × output rate)
```

with the request's own `max_tokens` and the policy's maximum rates. Why it cannot undercount the prompt: DeepSeek's published tokenizers are byte-level BPE (re-check for the frozen model before approval), in which every token stands for at least one UTF-8 byte of the text it encodes (a merge only joins bytes), so a prompt never has more tokens than bytes, whatever the language: English text is about one byte per character, German umlauts two, Chinese characters three, emoji four, and a script without merges costs at most one token per byte. Message text is rendered into the prompt as sent; the JSON body holds every byte of it and escapes only lengthen it, so the body's byte count bounds those tokens, and the factor 2 doubles that. A provider's template may re-serialize the tool schemas: JSON escaping writes at most six bytes for each byte of the shortest form (`<` for `<`), and `2 + 4 = 6` times their shortest form covers that. The allowance of 16,384 tokens covers the template's own text, role markers and any tool or reasoning preamble; the JSON framing of each message (at least 29 bytes) already exceeds the provider's few markers per message. The cap at `context_tokens` holds because a longer prompt is refused by the provider, and a settled prompt above it is already invalid evidence here. **The completion bound relies on one provider behaviour the full reservation does not:** that `max_tokens` bounds all completion tokens, reasoning included. The repository's records show `deepseek-v4-pro` in thinking mode stopping with `finish_reason=length` after spending exactly `max_tokens` on reasoning (`v1-2026-10-25-longitudinal-followup.md`, `v1-2026-10-25-longitudinal-harness.md`), and every settled response is checked for `completion_tokens ≤ max_tokens` (a violation blocks the ledger). Re-check this with the provider's limits before approval. For the C5 harness (`max_tokens` 16,384, 9 and 27 CNY per million) an interrupted send of a 40 KB body without tools is charged 1.31 CNY, of 20 KB with the 17 KB of `P`'s schemas 1.57 CNY, of 150 KB 3.29 CNY, against the 20.054016 CNY reservation it held while in flight. The ledger entry keeps an `interrupted` object: the cause (as below) and `prompt_tokens_bound` and `completion_tokens_bound`. When the request has no usable `max_tokens` (the guard refuses such a request before HTTP anyway), lacks its recorded sizes (an older ledger), or the bound cannot be computed or exceeds the reservation, the old rule applies: the reservation is kept, the ledger blocked, the run stopped. Retrying is the caller's decision: the C5 host client sends the same request again after 30 and then 120 seconds, three sends at most, and blocks the ledger itself after a third interruption ([`c5-harness.md`](c5-harness.md#harness-events-stops-and-the-log)); each send reserves and settles like any request.

**Still fatal.** Any other HTTP status (a 4xx other than 429), a response the guard cannot settle (malformed or out-of-bound usage, an unapproved response model), a guard refusal for lack of headroom or of a malformed request, `SystemExit`, `KeyboardInterrupt`, and any transport class outside the list above (`DecodingError`, `LocalProtocolError`, `ProxyError`, `UnsupportedProtocol`, unknown classes): the request retains its whole reservation and all subsequent requests are blocked. A refusal or uncertain bill invalidates the affected acceptance unit and stops all new provider work. A request in flight holds its whole reservation until it settles, interrupted or not, so the refusal point counts it in full while it is open and at its bound afterwards.

Provider failures record a content-free object on the reserved request: `failure` when the reservation is retained, `interrupted` when it was settled at its bound; the first global `stop_reason` is preserved. `provider_transport` includes only a fixed allowlist of exception class names (unknown classes become `other`); `provider_http_status` includes the numeric status; `response_billing` identifies rejected response/usage evidence. Exception messages, response bodies, headers and unapproved model names are never recorded, nor chained into the raised exception. A sibling's interruption or supervisor cleanup cannot replace the original global cause. A retained `failure` never releases a reservation or permits a retry. Older stopped ledgers without these fields cannot be retrospectively diagnosed from `BudgetStop` alone.

The C5 supervisor checks child completion throughout its 15-second launch stagger and final wait, using polling compatible with macOS Bash 3.2. On a failed arm it reports that arm's original exit status, invokes the policy-bound `--stop` control before terminating siblings, and reaps every active child. SIGTERM raises `SystemExit` in the harness so its cleanup stops only the disposable profiles it started. `GuardedTransport.stop()` is idempotent; `allow_stopped=True` permits opening an already-stopped ledger for that control, but cannot admit a provider request or clear its stop. The ledger records a fixed operation reason as well as reservations and usage. A failed attempt never automatically receives a new ledger or allowance.

Live pre-flight refuses unrelated provider/memory configuration. Local service startup gets an allowlist of system variables and the scenario clock, without provider credentials, and cannot reload dotenv configuration. The scenario creates a fresh profile without configured remote cognition or embedding providers.

The monetary bound depends on the reviewed provider rates and token limits actually holding. Re-check the provider's [pricing](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/) and [completion limits](https://api-docs.deepseek.com/api/create-chat-completion/) immediately before approval. Freeze them with the plan and code; do not rely on historical balance estimates. The account balance is a separate reconciliation check and includes any unrelated account use. Subscription scenario authors and judges are outside this API ledger and require their own explicit approval.

`tests/test_evaluation_billing_guard.py` exercises thread/process contention, unknown requests after a crash, failure retention, accounting validation, cache conservatism and protocol rejection using only mock transports. `tests/test_provider_interruption_retry.py` covers interrupted settlements, the host client's retries, the bound against a worst-case tokenizer model over English, German, Chinese and mixed prompts, the refusal point with interrupted settlements, two arm processes on one ledger, the call cap, and what validity and `diagnose` report. `tests/test_c5_harness.py` covers the live-ledger prerequisite and shared-stop check. A stub or unit result is not a real billing or behavioural acceptance result.
