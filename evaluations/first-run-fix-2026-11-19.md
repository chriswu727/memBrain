# First install to first value, after the fixes: the same sandbox runs, before and after

Start commit `d45c997c`; the "before" runs are those of [first-run-2026-11-19](first-run-2026-11-19.md) (launchers at `4fc15455`, runtime `b465c4b7`). The "after" runs used the launchers of this change and its runtime, installed from a source archive of this change's tree built as GitHub builds one (`git archive --format=zip` with the tree's `.gitattributes`, one top-level directory), because the launchers' pinned commit cannot contain an unpushed change: the sandbox's `MEMBRAIN_PACKAGE` named that archive, served at `http://membrain-archive.test/…` by the counting proxy with an ETag and `304 Not Modified` on revalidation, as GitHub's archive host answers (checked with `If-None-Match` against the pinned archive). Run E upgrades from the runtime the launchers pin today (`b465c4b7`, from GitHub) to this one. Same machine (WSL2, 16 cores, load average about 9 to 10 from other test runs), uv 0.13.6, system Python 3.12.3, the same driver (it plays Claude Code: the real hook command lines with `sh -c`, each killed at its configured timeout, the tool server started as `.claude-mcp.json` says and spoken to over MCP; every location redirected into a sandbox). **No host was started.** Changes to the driver: every run lives in its own network namespace and reaches the internet only through the counting proxy (so no sandbox service meets another service's ports, and no shared test lock was needed); every run counts its bytes (A, C, D1, D3 and E were not counted before); the driver writes a Claude Code-style transcript; and it polls `memory_recall` every 3 to 4.5 seconds after `initialize` to see when the tools give results rather than a refusal. Driver, events and logs: `~/.local/state/membrain-setup/runs/first-run-fix-20261119/` (not in the repository).

Notes:

- **The not-ready line now arrives while uv installs** (B, D2, D4 at 2.0 to 2.2 s, D1's offline second session at 2.0 s): uv gives up on its tool lock after 2 seconds (`UV_LOCK_TIMEOUT=2`). In A, D1 and D3 it came earlier because the hook ran before uv took the lock. No hook was stopped by the host in any run (before: 36).
- **Lost messages are those sent before the runtime exists** (B, D2, D4: two each). Nothing can stage them; the first message the runtime sees in that conversation now carries, once: "memBrain was not running yet for this conversation's 2 earlier messages, so they were not kept; tell the user if it matters." (B at 77.9 s; D2 and D4 in each affected session, with the singular form). C's message during the database preparation, lost before, is now queued and kept.
- **The tool server no longer crashes** for a busy profile (D1 online, D4 twice), a pending restart (E) or a taken port (D3). Its two remaining exits are D1's offline sessions: `uv tool run` cannot fetch the runtime without a network, before any memBrain code runs. While memory is not ready the tools answer one sentence ("memBrain is still starting; try again in a moment.", or the port sentence in D3); results follow 2.5 to 5 seconds after the service is ready.
- **`initialize` still waits for uv during a first install** (A 24.9 s, B 47.8 s, D4 46.3 s): `uv tool run --from <archive>` waits for uv's tool lock before memBrain's code starts (shown with a held lock: it waits without end), so only a smaller download shortens it. Whether Claude Code keeps waiting that long for a tool server is not known from here.
- **Downloads**: the source archive is 15.6 MB instead of 150.9 MB (B before) and is fetched once per installation; the rest is unchanged (PyPI index 6.5 to 12.5 MB, wheels 98.4 MB, more in D2 where the interrupted installation fetched wheels again: 129 MB, model 135.6 MB). B's installation finished at 46 s instead of 100 s.
- **E**: the service restarted once (before: twice); memory was unavailable from about 1.5 to 8 seconds (before: 4.4 to 22.3); the session notice said why ("memBrain is restarting after an update…"); the hooks' messages were queued and kept.
- Hooks that took longer than 3 seconds after the fixes (A 6.4 s, B 7.6 s, C 5.2 s, D4 3.8 s) ran while the service was ready but busy: the driver's health check timed out at the same moments (the local model being loaded and the machine under load). They are not waits for the start.

## The first database start (not changed)

In the first fixed run A the first start took 78 s from profile creation to a ready service, under load: preserving a copy of the bundled engine 55 s (1,362 files, 37 MB, each copied with an `fsync` and the tree hashed before and after), `initdb` about 9 s, three PostgreSQL starts with two stops, a 7 MB snapshot and two maintenance passes about 9 s, the schema bootstrap about 3 s. A brand-new profile has no earlier engine and no data to roll back to, but the transition journal requires the preserved engine and the snapshot in every phase after observation (`native_transition.Transition._validate`), every later start validates them (`recorded_layout`, `prepare` in phase `admitted`, `native_maintenance._validate` with the snapshot's commitment), and rollback and recovery read them. Skipping them needs a journal variant for "fresh, nothing to roll back to" accepted by all of these; that is migration-critical and left for its own review.

## Installations do not use the tested dependency set (not changed)

The fixed runtime installed in run A had 68 packages: 42 at the `uv.lock` version, 26 different, among them onnxruntime 1.32.0 (locked 1.31.1), fastapi 0.165.0 (0.161.0), numpy 2.5.5 (2.5.4), starlette 1.10.0 (1.9.0), pydantic 2.14.4 (2.14.1), psycopg and psycopg-binary 3.3.9 (3.3.6) and python-dateutil 4.0.0 (3.0.0). `uv tool install` reads neither the package's `uv.lock` nor its `[tool.uv]` settings. A few exact pins in `pyproject.toml` would not cover the transitive packages and would bind every library installation of `membrain-ai` (Hermes, AstrBot) to them; onnxruntime 1.31.1 has no wheel for macOS on Intel or for macOS before 14 and no source distribution, so such a pin would make installation fail there. `uv tool install --constraints FILE` (present in uv 0.6.17, absent in 0.4.30, which would then fail the installation) applies to the tool's environment only; the file would have to come with the launchers (for example from the plugin directory, generated from `uv.lock` with a test that keeps it current), and a pinned version missing for a platform makes the installation fail unless the launcher retries without it. Proposed, not made.

## What a source archive leaves out

`.gitattributes` marks `evaluations/` and `tests/` `export-ignore`. A zip of this tree built with `git archive` is 15.6 MB instead of 147.7 MB (`d45c997c`); of the remaining entries 14.3 MB are `src/`, most of it the bundled native engine description. Built from that archive exactly as the launchers' `uv tool install <archive URL>` builds it, the runtime installed, created its profile and database, ran every hook and the tool server and downloaded its model in all eight runs above, and served the memory page (A, D3). `integrations/` stays in the archive: the OpenClaw and AstrBot install instructions take their plugin from it. GitHub's archive downloads apply `export-ignore`: for `symfony/console` at branch 7.3, whose `.gitattributes` marks `/Tests` and `/phpunit.xml.dist`, the API's tree lists 462 files and the downloaded archive 134, without any of the 323 under `Tests/`. The saving reaches users only from the next pinned commit, since the launchers install the commit they pin.

## Limits

No real host was started: that Claude Code waits for a `UserPromptSubmit` hook until it returns, and how long it waits for a tool server, are from its documented hook model. `UV_LOCK_TIMEOUT` is honoured by uv 0.9.30 and later (checked: 0.9.30, 0.10.0, 0.11.0, 0.13.6); 0.4.30, 0.6.17, 0.8.0 and 0.9.0 ignore it and wait as before. The Windows wrapper was checked by inspection only. The count of earlier messages that were not kept reads Claude Code's transcript format; Codex's transcripts have another format, and that host is not told. Linux only.
