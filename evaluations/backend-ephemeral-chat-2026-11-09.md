## Behavior

Pausing the selected brain's server recording switch previously prevented direct Python chat. BrainRuntime, open_agent and desktop chat now continue using bounded temporary conversation in process memory. Input, replies, drafts, temporary history and optional answer-review contents do not enter the memory service, local pending sidecar or learning queue. Resuming recording starts new durable messages; it never imports the temporary buffer. Existing historical context is restricted to a bounded slice of the exact conversation and branch, without cross-conversation semantic recall or orientation.

The service retains content-free attempt metadata in the existing turn journal: scope, recording/context revision, stage, lease, reserved call counts, optional reviewer-configuration fingerprint and reported delivery-state enum. Migration 034 constrains temporary rows to a fixed zero input fingerprint and absent source references, context/draft/review bodies or hashes, prepared memory selection and ordinary delivery receipts. Existing tenant/owner isolation and scope exclusion remain authoritative. Durable write endpoints reject temporary turns.

A completed temporary ID replays only a completion marker. A crash or uncertain external generation, review or delivery does not silently retry. After the lease expires, the owning session can explicitly cancel a blocked turn, acknowledging uncertainty where required, and use a fresh ID. A restarted process cannot reconstruct temporary content. A policy/dependency change prevents subsequent generation/delivery stages from using stale context. An already dispatched delivery cannot be recalled; its reported state can settle without saving a body, while stale text is withheld from the return value and temporary history.

## Query work and cost

The initial temporary-history query compared branch_id directly and failed to use the full existing expression index. With six requested-branch messages and 20,000 other-branch messages, its actual query plan filtered 20,000 unrelated rows. The corrected predicate matches the existing conversation/branch index, returns the same six messages and filters fewer than ten rows. The regression test exercises the production query against PostgreSQL, rather than asserting a copied query string. No new index or duplicated history is added.

This is a bounded-query-work improvement, not a general recall-latency or capacity benchmark. Mode selection adds one recording-status GET to a new direct turn; its incremental overhead relative to the previous durable path has not been measured. Temporary mode skips durable capture, preparation and learning, but still performs control transactions and configured generation/review. Content-free control rows grow with attempts; they are required for deduplication and are not automatically expired by this change.

A single local sequential probe executes 1,000 temporary turns through real loopback HTTP and pooled PostgreSQL on the current runtime. Each turn has about 1 KB of synthetic input and a constant synthetic reply; there is no answer reviewer, delivery callback, existing memory corpus or paid provider. All 1,000 complete. Observed turn median is 19.72 ms and p95 is 21.53 ms, including recording-status and control requests but excluding real model latency. These are local observations without a baseline comparison, not a production SLO or full memory recall measurement.

After 1,000 turns, there are zero memory events and learning jobs, 1,000 control rows and 6,000 transition rows. The single-scope temporary buffer remains at six messages and 3,471 content bytes. Live control-row payload totals 1,834,000 bytes; allocated control-table/index storage grows by 3,932,160 bytes (3.75 MiB), including allocation/MVCC effects. This is not a complete database/WAL/backup size estimate or a million-turn capacity guarantee. The probe clears the buffer, stops its server/database and removes its 112,437,723-byte synthetic database. The earlier indexed-runtime probe remains archived with its original build ID; these single samples do not establish a before/after speed comparison. Retention or compaction must preserve stable-ID deduplication and remains future database work; silently deleting these markers would change recovery semantics.

## Boundaries and remaining work

This mode follows the selected brain's server pause. Device-wide timed capture and individual conversation switches in other adapters remain separate controls; automatic synchronization and receipt normalization across the independent AgentRuntime remain open. All service processes and Python clients need the upgrade together. A restored checkpoint that predates the content-free markers is outside restart deduplication guarantees. Host transcripts, model-provider retention, operating-system swap and secure memory erasure are outside this feature's promise. Temporary IDs cannot be compared by content because no input digest is retained. Without a delivery callback, completion records preparation for return, not receipt by another system.
